## 今日核心概念
### 1. 软件体系结构评估
定义：软件体系结构评估是依据质量属性需求，对候选架构满足业务目标和技术约束的能力进行系统分析，并识别风险、权衡取舍和改进方向的过程。
关键要点：
- 评估对象包括结构、行为、关键技术选型、质量属性实现机制以及架构风险，不只是检查代码规范。
- 常用方法包括基于场景的评估、基于度量的评估和基于经验的评估；实际项目通常组合使用。
- 质量属性场景应明确刺激源、刺激、环境、制品、响应和响应度量六个要素，例如高峰期请求量、允许响应时间和可用率目标。
- 评估重点关注性能、可用性、安全性、可修改性、可测试性、互操作性和可伸缩性之间的权衡，不能孤立追求单项指标。
- 评估输出应包含风险、非风险、敏感点、权衡点和改进建议，并形成可跟踪的整改闭环。

### 2. 架构权衡与架构决策记录
定义：架构权衡是在多个质量属性、业务目标和技术约束相互冲突时，通过比较候选方案的收益、成本和风险作出选择；架构决策记录用于保存决策背景、方案依据和后续影响。
关键要点：
- 架构决策记录至少包括问题背景、决策内容、候选方案、选择理由、被否决方案、预期后果和验证方式。
- 性能与可修改性常有冲突：缓存、异步化和数据冗余可能提升性能，却增加一致性维护和变更复杂度。
- 安全与易用性常有冲突：更严格的身份认证和权限控制会增加操作成本，应根据业务风险采用分级认证和最小权限。
- 建议优先记录不可逆或代价高的决策，如核心数据存储、通信协议、部署模式和安全边界。
- 架构决策不是一次性结论，应在需求变化、技术验证或运行数据出现重大变化时重新评审。

### 3. 架构治理
定义：架构治理是通过组织、原则、标准、流程和度量，对系统架构的设计、实施、运行和演进进行监督与约束，确保架构持续符合业务战略和合规要求。
关键要点：
- 治理主体通常包括架构委员会、领域架构师、项目团队、运维团队和安全合规人员，职责必须清晰并避免只由架构师单方面决策。
- 治理内容包括架构原则管理、技术标准管理、方案评审、例外审批、架构合规检查、技术债务管理和架构资产沉淀。
- 架构原则应少而明确，例如业务能力复用、数据统一管理、接口标准化、安全内置、可观测和自主可控。
- 例外机制不能简单禁止偏离标准，应说明例外原因、影响范围、补偿措施、责任人和失效期限。
- 架构治理要嵌入项目生命周期，在立项、概要设计、详细设计、上线和重大变更节点设置检查点。

### 4. 演进式架构与技术债务
定义：演进式架构是在需求、技术、组织和外部环境持续变化的条件下，通过小步迭代、持续验证和可逆决策，使系统架构逐步适应未来目标；技术债务是为短期交付而采用的临时方案在未来产生的额外维护成本和变更风险。
关键要点：
- 演进式架构强调增量演进、持续反馈、自动化验证和可回滚，避免一次性设计一个无法验证的大而全架构。
- 架构适应性度量可以把性能、安全、接口兼容、依赖数量和部署时间等约束纳入自动化检查。
- 技术债务分为有意债务和无意债务；有意债务必须登记、定级、设定偿还时间，不能把临时方案伪装成最终架构。
- 架构重构可采用绞杀者模式、分支迁移、双写校验、灰度发布和分阶段切换，降低一次性替换带来的业务风险。
- 技术债务优先偿还高利息债务，即频繁阻塞交付、严重影响安全稳定或导致数据错误的债务。

## 案例分析题
**题目**：某省级政务数据共享平台已运行五年，现有系统由多个项目分别建设，存在接口风格不统一、同一主体数据重复维护、部分服务响应缓慢、权限边界模糊和架构文档缺失等问题。省级主管部门计划在不影响现有业务连续性的前提下，建设统一共享平台，并要求支持未来三年业务快速扩展。项目组提出两种方案：方案一是一次性替换全部旧系统，建设全新的集中式平台；方案二是保留稳定运行的旧系统，通过统一接入层、数据治理、服务改造和分阶段迁移逐步演进。请从系统架构设计师角度回答：
1. 应如何组织本项目的架构评估，至少说明评估场景、评估方法和评估输出；
2. 在两种方案之间进行架构权衡时，应重点分析哪些因素；
3. 如何建立架构治理机制，避免各部门继续建设新的技术孤岛；
4. 针对方案二，给出一套兼顾连续性和可演进性的实施策略；
5. 如何识别、登记和偿还项目中的技术债务。

**参考答案**：
1. 架构评估应先从业务目标和质量属性出发建立场景。性能场景可设定高峰期并发访问量、接口响应时间和数据交换吞吐量；可用性场景可设定单节点故障、网络中断后的服务恢复时间和数据丢失范围；安全场景可设定越权访问、敏感数据调用和审计追溯要求；可修改性场景可设定新增一个部门或新增一种共享服务所需的改造范围和上线时间；互操作性场景可设定异构系统接入和数据标准转换要求。评估方法采用基于场景的评估为主，结合架构走查、原型验证、性能压测、故障演练和风险清单检查。评估输出包括候选方案比较矩阵、敏感点、权衡点、风险项、非风险项、改进建议、验证结论和整改责任清单。

2. 重点分析业务连续性、迁移风险、建设周期、初期投资、长期维护成本、数据一致性、系统性能、扩展能力、安全合规、组织协同和供应商依赖。方案一结构统一、长期治理成本可能较低，但一次性替换范围大，容易出现需求遗漏、数据迁移失败、上线冲击和风险集中；方案二能够保护既有投资、支持平滑迁移和快速验证，但会在一段时间内并存新旧架构，增加接口适配、数据同步、运维监控和一致性治理的复杂度。应结合风险承受能力和业务窗口选择方案，不能只比较采购金额。

3. 建立省级架构治理委员会，统一审定架构原则、数据标准、接口规范、身份权限模型和技术选型目录；设置领域架构师负责数据、应用、技术和安全等领域的专业治理；将架构评审嵌入立项、设计、采购、上线和重大变更流程；建设统一服务目录、数据目录、接口目录、组件目录和架构资产库；所有例外必须经过审批，记录原因、影响、补偿措施、责任人和退出期限；通过架构合规检查、接口复用率、数据标准覆盖率、重复建设数量、故障率和技术债务规模等指标持续度量。

4. 方案二可采用统一接入层加分阶段迁移策略。第一阶段完成现状盘点、数据标准制定、服务目录梳理、统一身份认证和访问审计；第二阶段建设接入层和服务治理能力，对旧接口进行适配，统一协议、鉴权、限流、熔断、监控和日志；第三阶段选择高频、低风险、边界清晰的共享服务试点，采用旁路接入、双读校验和灰度发布验证新平台；第四阶段对重复数据进行主数据治理，明确权威来源，通过增量同步和对账机制逐步收敛；第五阶段按业务域迁移服务，设置回退开关和应急预案，稳定运行后再下线旧服务。新平台负责统一能力建设，旧系统在迁移期间保持最小必要改动，避免继续扩大技术债务。

5. 建立技术债务台账，记录债务来源、所属系统、影响范围、产生原因、风险等级、偿还成本、责任人、计划时间和验收标准。通过架构评审、代码与依赖扫描、接口盘点、数据质量检查、故障复盘和运维反馈识别债务。按照安全与合规风险、数据错误风险、稳定性风险、交付阻塞程度和偿还成本进行排序，优先偿还高风险、高频发生和影响范围广的债务。偿还方式包括接口标准化、重复数据合并、遗留系统封装、关键模块重构、依赖升级、自动化测试补齐和文档完善。每个迭代周期安排固定偿还容量，完成后通过性能、故障、安全和回归测试验证效果，并更新台账状态。

**踩分要点**：
- 架构评估必须从质量属性场景出发，写清刺激、环境、响应和度量指标，不能只写“组织专家评审”。
- 方案权衡要同时覆盖短期建设收益、长期治理成本、业务连续性、迁移风险和数据一致性。
- 架构治理必须落到组织、原则、标准、评审、例外、度量和资产沉淀，不能停留在口号层面。
- 分阶段演进应体现统一接入、试点验证、双读校验、灰度发布、增量同步、回退机制和旧系统逐步下线。
- 技术债务要有台账、分级、责任人、偿还计划和验收标准，且优先处理安全、数据和稳定性类高利息债务。
- 需要体现架构评估与架构治理的闭环：评估发现问题，治理落实约束，度量持续反馈，演进不断修正。

## 记忆口诀
架构评估六要素：源、激、环、物、响、度；先定场景再验架构。
架构权衡三张表：收益表、成本表、风险表；短期交付看收益，长期运行看代价。
架构治理六落点：组织、原则、标准、评审、例外、度量。
演进架构四个小：小步改、小范围试、小风险切、小成本退。
技术债务五要素：识别、登记、分级、偿还、验证；高利息债务优先还。
平台治理三统一：统一身份、统一数据、统一接口；共享服务目录化，新增建设先复用。
迁移实施七动作：盘现状、定标准、建接入、做试点、双校验、灰度切、可回退。
