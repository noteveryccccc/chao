## 今日核心概念

### 1. 云原生架构与Kubernetes进阶

定义：云原生是基于容器、服务网格、微服务、不可变基础设施和声明式API构建可弹性扩展的应用架构方法论。Kubernetes（K8s）是云原生时代的事实操作系统，提供自动化的应用部署、扩缩、运维能力，是PaaS层的工业标准。

关键要点：
- K8s核心组件：Master控制平面（API Server + Scheduler调度器 + Controller Manager控制器 + etcd键值存储）+ Node工作节点（kubelet + kube-proxy + 容器运行时Containerd）
- Pod生命周期：Pending（调度中）→ Running（运行中）→ Succeeded/Failed（终态）→ Unknown（状态失联），含Init Container初始化容器、Readiness就绪探针、Liveness存活探针、Startup启动探针
- 控制器模式：Deployment无状态（滚动更新+回滚）+ StatefulSet有状态（稳定网络标识/PVC持久卷/有序启停）+ DaemonSet守护进程（每个节点一份/日志/监控）+ Job/CronJob批处理
- 服务发现：Service ClusterIP（集群内VIP负载均衡）+ NodePort（节点端口）+ LoadBalancer（云厂商LB）+ Ingress（七层路由/HTTPS/域名/路径）+ Headless无头服务（DNS直连Pod）
- 存储体系：PV持久卷 + PVC存储卷声明 + StorageClass动态供给，支持NFS、Ceph、HostPath、本地存储、CSI驱动
- 配置管理：ConfigMap（明文配置/环境变量）+ Secret（Base64/etcd密文，可对接Vault）+ DownwardAPI（Pod自身信息注入）
- 高级调度：污点taint + 容忍toleration（专用节点）、亲和性affinity（节点/Pod协同）、反亲和anti-affinity（分散部署）、TopologySpreadConstraints拓扑约束

### 2. 微服务架构与服务网格Service Mesh

定义：微服务是将单体应用按业务边界拆分为独立部署、独立演进的小型服务，通过轻量通信协议（HTTP/gRPC/消息）协作。服务网格是将微服务间的通信、安全、可观测、流量控制等横切关注点下沉到独立的Sidecar代理层的网络基础设施层。

关键要点：
- 微服务设计原则：单一职责（SRP/一个服务一件事）+ 独立部署（CD/CD）+ 去中心化数据（每服务独立DB）+ 故障隔离（熔断限流隔离舱）+ 技术异构（语言无关）
- 拆分方法：业务能力拆（Bounded Context限界上下文/DDD聚合根）+ 领域驱动设计DDD + Akka Actor模型 + 新建拆分（绞杀者模式Strangler）
- 通信协议：同步REST/HTTP（OpenAPI 3.0/Swagger）+ gRPC（Protobuf二进制/HTTP2流式双向，高性能首选）+ 异步消息（Kafka/RocketMQ事件驱动）
- API网关：统一入口（路由聚合）+ 鉴权（OAuth2/JWT）+ 限流（Sentinel令牌桶/漏桶）+ 灰度发布（金丝雀蓝绿）+ 协议转换（REST转gRPC）+ 监控日志
- Service Mesh核心：数据面Envoy Sidecar（流量劫持/L4L7代理）+ 控制面Istio（xDS配置下发/服务发现/证书签发），解耦业务与基础设施
- Istio流量管理：VirtualService（路由规则）+ DestinationRule（负载均衡/连接池/熔断）+ Gateway（入口网关）+ ServiceEntry（外部服务注册）
- Mesh可观测：调用链Tracing（Jaeger/Zipkin/OpenTelemetry）+ Metrics（Prometheus/Cadvisor）+ Log（EFK日志聚合），三大支柱支撑可观测性
- 对比API网关：网关是南北向（外部→内部），Mesh是东西向（内部服务间），定位互补

### 3. 云原生可观测性Observability

定义：可观测性是通过系统对外输出的遥测数据（日志、指标、追踪）来理解系统内部状态的能力，是SRE与云原生运维的核心支柱。Metrics+Logging+Tracing三大支柱构成完整观测体系。

关键要点：
- 三大支柱：Metrics指标（数值时间序列/聚合友好，Prometheus时序数据库Pull拉取）+ Logs日志（离散事件/Fluentd采集ELK存储）+ Traces追踪（请求链路/OpenTelemetry标准Jaeger展示）
- 指标体系：RED方法（Rate请求率+Errors错误率+Duration延迟）+ USE方法（Utilization利用率+Saturation饱和度+Errors错误），是黄金信号
- 监控层级：基础设施层（CPU/内存/磁盘/网络节点Exporter）+ 中间件层（数据库连接池/Kafka消费滞后/Redis命中率）+ 应用层（QPS/RT/JVM GC/业务自定义）+ 业务层（订单数/支付成功率）
- 告警分级：P0紧急（核心服务挂/5分钟内响应/电话告警）+ P1高（中件间故障/30分钟响应）+ P2中（一般异常/2小时处理）+ P3低（优化建议/工单）
- 告警策略：阈值告警（绝对值超限）+ 同环比告警（增长率突变）+ 智能告警（异常检测算法/动态基线）+ SLO告警（错误预算Burn Rate燃烧率）
- 链路追踪：Trace（一次完整调用）+ Span（一次操作）+ SpanContext（TraceID+SpanID+ParentSpan传播），W3C TraceContext标准
- 国产可观测栈：Prometheus + Loki（日志）+ Tempo（追踪）+ Grafana展示（PLG云原生套件），阿里云ARMS/华为云AOM/腾讯云CAT
- AIOps智能化：异常检测（孤立森林/LSTM时序）+ 根因分析（RCA图神经网络GNN）+ 日志聚类（Drain算法）+ 告警降噪（聚合关联）

### 4. DevOps与GitOps进阶

定义：DevOps是打破开发与运维壁垒的文化+实践+工具集合，通过自动化CI/CD流水线实现快速可靠的软件交付。GitOps是以Git仓库为唯一事实源，通过声明式配置 + 自动同步实现基础设施和应用的版本化运维。

关键要点：
- CI/CD流水线：代码提交（Git Hook触发）→ 编译构建（Maven/Gradle/npm）→ 单元测试（JUnit/pytest覆盖率门禁）→ 制品归档（Nexus/Artifactory/Docker Registry）→ 部署发布（蓝绿/灰度/滚动）
- 持续集成CI：Jenkins（生态丰富/Groovy脚本）、GitLab CI（一体化内置YAML）、GitHub Actions（生态轻量）、Tekton（K8s原生流水线）
- 持续交付CD：Spinnaker（Netflix开源多云发布/金丝雀/红黑部署）、ArgoCD（K8s GitOps首选/声明式）、Flux（轻量GitOps）、Jenkins X（云原生Jenkins）
- GitOps工作流：应用清单YAML存Git仓库（声明期望态）→ ArgoCD定时同步（Reconciliation调和）→ 集群实际态匹配期望态 → 不一致自动告警+回滚
- 多环境管理：dev开发/uat测试/pre预生产/prod生产四级分离，Helm Values参数化（Kustomize叠加），ArgoCD ApplicationSet应用集批量管理
- 渐进式发布：蓝绿部署（两套环境瞬间切换/0停机回滚快但资源翻倍）+ 金丝雀Canary（5%→25%→100%渐进放量）+ 滚动更新（分批替换/零浪费但回滚慢）
- 特性开关Feature Flag：LaunchDarkly商用/自建Nacos/Flipr，灰度时按用户分群控制开关，无需重新发布
- 文化层面：CFT无指责事后复盘（Postmortem）+ Blameless Culture + 康威定律（系统架构映射组织沟通结构）+ 反向康威逆操作（先定义目标架构再设团队）

## 案例分析题

**题目**：某互联网金融公司核心交易系统面临三方面挑战：（1）原单体架构日处理交易200万笔已达瓶颈，618大促峰值需要支撑500万笔；（2）部署频率低，每月一次大版本灰度，事故频发，回滚需2小时；（3）故障定位困难，链路涉及20+服务，定位时间超30分钟。请从微服务拆分、Service Mesh、CI/CD流水线、可观测性四个维度给出云原生架构升级方案。

要求：
1. 微服务拆分与通信方案（5分）
2. Service Mesh与API网关设计（5分）
3. GitOps与渐进式发布方案（5分）
4. 可观测性与告警体系设计（5分）

**参考答案**：

1. **微服务拆分与通信方案（5分）**
- 拆分原则：按业务能力拆，用户中心/账户中心/交易核心/支付清算/风控决策/营销活动六大微服务，每个服务独立DB（避免分布式事务）
- 注册中心：Nacos集群（CP+AP双模式），namespace隔离环境，Group分组，同机房优先路由，避免跨机房调用
- 同步通信：内部用gRPC（Protobuf序列化/HTTP2多路复用），性能较REST提升3-5倍，交易链路延迟从80ms降至20ms
- 异步通信：Kafka+RocketMQ双轨，RocketMQ事务消息保证资金一致（消息+本地事务+反查机制），Kafka高吞吐营销活动异步解耦
- 分布式事务：账户余额变动用TCC（Try-Confirm-Cancel三阶段），高一致场景用Seata AT模式，弱一致场景本地消息表+对账兜底
- 幂等性：交易接口幂等Token（Redis SETNX+过期时间），防重复支付；消息消费At-least-once + 业务去重表，补偿保证最终一致

2. **Service Mesh与API网关设计（5分）**
- 入口Gateway：Kong或APISIX，南北向入口，统一鉴权（OAuth2+JWT）、限流（Sentinel集群流控/令牌桶算法）、协议转换（HTTPS→gRPC内部）
- Mesh数据面：Envoy Sidecar注入到每个Pod，iptables透明流量劫持，业务代码零侵入，无感获得熔断限流能力
- Mesh控制面：Istio，mTLS自动证书签发（SPIFFE身份+30天轮转），微服务间通信全程加密，满足金融合规
- 流量管理：VirtualService定义路由规则（按Header/Path分流），DestinationRule配置熔断（连续5次错误→隔离30秒）+重试（指数退避，最多3次）
- 灰度能力：Header路由（users-in-test头部走v2版本），Weight权重（金丝雀5%→25%→100%渐进放量），镜像流量Mirror到测试集群引流验证
- 关键策略：故障注入Chaos（ChaosBlade杀Pod/注入延迟验证容错）+ 超时控制（全局默认3秒，按业务分级）+ 重试预算（一分钟内最多重试5次防雪崩）

3. **GitOps与渐进式发布方案（5分）**
- 镜像仓库：Harbor主从复制，签名验证（Cosign/Sigstore/镜像SBOM清单），漏洞扫描（Clair/Trivy），放行策略仅允许CI账号推送
- CI流水线：GitLab CI/GitHub Actions，提交代码→单元测试→SonarQube代码扫描（门禁）→Docker构建→漏洞扫描→镜像推送→自动生成Helm Chart
- GitOps仓库结构：apps仓库存业务应用（每服务一目录+values-{env}.yaml），infra仓库存ArgoCD配置（Application清单），GitOps即文档即审计
- ArgoCD控制：ApplicationSet统一管理50+微服务，自动同步（prune删孤儿+selfHeal自愈），Drift Detection检测偏差并告警
- 发布策略：生产采用金丝雀发布（Canary步骤：1%观察10分钟→10%观察30分钟→50%→100%），失败自动回滚ArgoCD Rollback一键回到上个Stable版本
- 数据库变更：Flyway版本化SQL脚本，禁止直接DDL，灰度期间只读，发布完成后切读写；Switch Traffic功能+K8s Readiness探针保优雅下线

4. **可观测性与告警体系设计（5分）**
- 指标采集：Prometheus Operator管理Prometheus集群，每个微服务暴露/metrics端点（Micrometer SDK），NodeExporter采集基础设施，业务自定义Counter/Gauge
- 链路追踪：OpenTelemetry SDK自动埋点，Jaeger后端存储+展示，关键路径TraceID透传Header（traceparent），串联20+服务全链路
- 日志聚合：EFK栈（Elasticsearch存储+Fluentd采集+Kibana展示），按服务+TraceID索引，结构化JSON日志，敏感信息脱敏（卡号/手机号）
- 告警规则：基础告警（P99>500ms持续3分钟/QPS>容量80%/错误率>1%/JVM FullGC>5次/10分钟），SLO告警（错误预算Burn Rate>14.4倍触发紧急）
- 告警路由：AlertManager按级别分发，P0调用OnCall电话+PagerDuty值班机器人，P1企业微信+钉钉卡片，P2邮件+工单
- SOP应急：每个告警匹配Runbook（常见故障处置手册），值班机器人推送处理步骤，关键事务5分钟OPS工程师介入兜底
- 复盘机制：故障自动归档（PagerDuty报告+会议纪要），月度可靠性报告（MTTR平均恢复时长/MTTF平均无故障时长/可用性SLA达成率），持续改进

**踩分要点**：
- 微服务必答业务拆分 + Nacos注册 + gRPC同步 + MQ异步 + 分布式事务 + 幂等
- Mesh必答Istio + Envoy + mTLS + 灰度 + 熔断 + 故障注入 + 与API网关分工
- GitOps必答Git仓库单一事实源 + ArgoCD + 镜像签名 + 金丝雀发布 + 数据库变更管控
- 可观测必答三大支柱Prometheus+ELK+Jaeger + 告警分级 + SLO错误预算 + 应急Runbook
- 金融场景必答：合规加密mTLS、幂等防重、TCC事务、SLO可用性、敏感信息脱敏
- 避免只列工具名词，必须说明场景适配原因和具体配置参数（如金丝雀比例、熔断阈值）

## 记忆口诀

**K8s四件套**：Pod（最小单位）+ Controller（Deployment/StatefulSet/DaemonSet）+ Service（发现负载均衡）+ Volume（PV/PVC持久化）

**K8s三种探针**：Readiness（就绪接流量）+ Liveness（存活保活）+ Startup（启动慢应用）

**微服务六要素**：单一职责 + 独立部署 + 去中心化数据 + 故障隔离 + 技术异构 + 团队全栈（小团队吃下整个服务生命周期）

**Service Mesh价值**：Sidecar模式数据面Istio控制面，业务零侵入解耦通信基础设施

**Istio四件套**：VirtualService（路由）+ DestinationRule（熔断负载均衡）+ Gateway（入口）+ ServiceEntry（外部服务）

**南北东西**：API网关南北（外部→内部）+ Mesh东西（服务间）

**可观测三大支柱**：Metrics（Prometheus时序聚合）+ Logs（ELK离散事件）+ Traces（OpenTelemetry请求链路）

**RED黄金信号**：Rate（请求率）+ Errors（错误率）+ Duration（延迟）

**USE方法**：Utilization（利用率）+ Saturation（饱和度）+ Errors（错误）

**告警分级**：P0电话+ P1企微+ P2邮件+ P3工单，按响应时间SLA分级

**DevOps三利器**：CI持续集成 + CD持续交付 + GitOps以Git为唯一事实源

**渐进发布三策略**：蓝绿切换（瞬间切流回滚快但费资源）+ 金丝Canary（渐进放量验证）+ 滚动（分批替换零浪费）

**GitOps工作流**：Git声明期望态→ArgoCD调和Reconciliation→差异告警Diff→手动/自动同步Sync

**金融科技三高**：高可用（多活容灾）+ 高一致（分布式事务TCC Seata）+ 高安全（mTLS加密+审计追溯）

**可观测与告警闭环**：观测发现（Metrics/Logs/Traces）→ 告警触发（AlertManager分级）→ 应急响应（Runbook SOP）→ 事后复盘（Blame-less Postmortem）
