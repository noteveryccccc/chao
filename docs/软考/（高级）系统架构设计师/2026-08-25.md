## 今日核心概念
### 1. 负载均衡分层与算法
定义：负载均衡(Load Balancing)将请求按策略分发到多台服务器以提高吞吐量、可用性与伸缩性的机制；按网络层级分DNS层(GSLB全局负载均衡)、网络层(LVS四层)、应用层(Nginx七层)、客户端层(Ribbon)；算法分静态(轮询/加权轮询/随机/哈希)与动态(最少连接/最快响应/加权最少连接/观察模式)。
关键要点：
1. DNS负载均衡实现地理位置就近接入，TTL切换慢；LVS基于IP转发性能高百万QPS；Nginx基于URL/Header七层路由灵活
2. 加权轮询按服务器性能分配权重；加权最少连接避免长连接堆积；一致性哈希用于缓存集群减少数据迁移
3. 健康检查分TCP端口探测、应用层探活(GET /health)、主动业务验证三档
4. 负载均衡自身高可用：Keepalived主备+LVS、HAProxy双主+VRRP、AWS ALB自管
5. GSLS策略：地域级→机房级→集群级→实例级四级调度

### 2. 高可用架构模式
定义：通过冗余设计消除单点故障的架构范式，使系统在部分节点失效时仍能持续提供服务；核心模式分主备(Active-Standby)、主主(Active-Active)、集群(Cluster)、读写分离(Read-Write Splitting)、分库分表(Sharding)、单元化(Unit/Shard-Based)。
关键要点：
1. 主备模式冷备(Warm Standby)与热备(Hot Standby)；切换依赖心跳检测+Lease租约防脑裂
2. 主主模式双写冲突：时间戳向量、CRDT、版本号、最终一致路由
3. 集群模式无状态服务通过负载均衡横向扩展；有状态服务需Session共享(Redis/Sticky Session)
4. 读写分离主库写入+从库读取，需注意主从延迟与读写路由判断
5. 分库分表按业务键(用户ID/订单号)哈希或范围分片，需解决分布式主键、跨库Join、全局排序问题
6. 单元化架构以用户维度为单位封闭部署，异地多活天然支持

### 3. 限流算法与策略
定义：限流(Rate Limiting)在高并发场景下限制单位时间请求量，保护系统不被流量击垮的技术；算法分令牌桶(Token Bucket)、漏桶(Leaky Bucket)、固定窗口计数器(Fixed Window)、滑动窗口计数器(Sliding Window)、滑动日志(Sliding Log)。
关键要点：
1. 令牌桶允许突发流量，按速率持续生成令牌，请求消耗令牌；Guava RateLimiter/Sentinel FlowRule
2. 漏桶强制匀速输出，平滑流量但无法应对突发；常用于消息消费速率控制
3. 固定窗口实现简单但临界突刺问题(1秒末+下一秒初可双倍流量)
4. 滑动窗口将固定窗口细分为多个小窗口，加权求和更精确；Redis ZSET实现滑动日志
5. 限流粒度：QPS/TPS、并发数、连接数、带宽、用户/IP/接口多维度
6. 限流策略：拒绝策略(快速失败/排队等待/预热冷启动)、降级策略(返回缓存/默认值/兜底页)

### 4. 熔断降级与Sentinel
定义：熔断(Circuit Breaker)在依赖服务故障率超过阈值时快速失败返回降级结果的保护机制；降级(Degradation)在系统压力下牺牲非核心功能保障核心链路；阿里Sentinel是国内主流熔断降级组件。
关键要点：
1. 熔断三状态：CLOSED(正常)/OPEN(熔断拒绝)/HALF_OPEN(探测恢复)；触发阈值如50%错误率或连续10次失败
2. 熔断时间窗10秒，HALF_OPEN放部分请求试探，成功率回升则关闭熔断
3. 降级策略四类——自动降级(超时/异常/限流触发)、人工降级(配置开关)、开关降级(A/B特性开关)、预案降级(预定义脚本)
4. Sentinel核心规则：FlowRule(限流)、DegradeRule(降级)、SystemRule(系统自适应)、ParamFlowRule(热点参数)
5. 熔断降级与限流关系——限流保护入口流量，熔断保护下游依赖，降级保护核心链路
6. 隔离手段：线程池隔离(每个服务独立线程)/信号量隔离(共用线程限并发)/进程隔离(独立部署)

### 5. 容灾等级与两地三中心
定义：容灾(Disaster Recovery)在灾难(地震/火灾/光缆中断)发生时保障业务连续性的能力；核心指标RPO(数据丢失时间)和RTO(服务恢复时间)分级；常见架构分同城双活、两地三中心、异地多活、混合云灾备。
关键要点：
1. 国家级容灾等级：Level 1基本备份、Level 2在线备份、Level 3电子传输+部分恢复、Level 4电子传输+完整恢复、Level 5实时切换、Level 6数据零丢失
2. RPO衡量数据丢失量(秒级/分钟级/小时级)；RTO衡量停机时长(分钟级/小时级/天级)
3. 同城双活机房距离≤50km，时延1ms内；数据库同步复制+应用层双活流量切换
4. 两地三中心：同城两中心(双活)+异地灾备中心(冷备)；金融行业标配
5. 异地多活按地域分单元，每个单元独立服务本地用户；数据跨地域同步挑战大
6. 容灾演练：Chaos Engineering故障注入(Netflix Chaos Monkey/Gremlin)、DR Drill切换演练、业务连续性BCM

## 案例分析题
**题目**：某互联网支付公司核心交易系统日均交易1.2亿笔，峰值5万QPS，可用性要求99.999%(年停机≤5分钟)；系统包含入口网关、风控、账户、支付、清算、账务6个微服务，数据库采用MySQL主从+Redis集群。近期发生过两次生产事故：①2024年大促某机房光缆中断导致全站不可用4小时；②风控服务异常拖垮网关线程池引发雪崩。问：
1. 请设计三层(入口层/服务层/数据层)容灾架构，要求避免单机房故障全站不可用
2. 针对风控服务故障雪崩，请给出具体的熔断降级方案
3. 大促期间入口层流量可能达10万QPS超阈值，请设计分层限流方案
4. 容灾切换RPO与RTO要求？请设计容灾演练计划

**参考答案**：
1. 三层容灾架构：
   - 入口层：双机房GSLB全局负载均衡，DDoS清洗中心前置，DNS TTL 60秒快速调度
   - 服务层：每个微服务同城双机房双活部署，单元化按用户ID取模分单元；服务无状态化改造，Session/Token走Redis
   - 数据层：MySQL同城双主(Keepalived VIP)+异地灾备从库+binlog异步复制；Redis Cluster跨机房双写版本；Kafka MirrorMaker跨机房同步
   - 切换机制：LVS+Keepalived VIP秒级切换；DNS GSLB 1分钟流量调度；数据库GTID延迟从库秒级提升
2. 熔断降级方案：
   - Sentinel熔断：风控服务错误率>30%或RT>200ms持续10秒触发熔断
   - 三策略降级：①风控返回默认通过+事后风控异步审核；②核心交易链路绕过风控直走支付；③账户余额查询返回Redis缓存值
   - 隔离：风控独立线程池(200线程)，与网关共用池物理隔离防雪崩
   - 超时控制：风控调用800ms超时，失败重试2次后触发降级
   - 监控告警：风控错误率/RT/线程池使用率三指标实时告警
3. 分层限流方案：
   - 入口层Nginx limit_req：单IP 100次/秒、突发200
   - 网关层Sentinel：总QPS 8万、用户级1000/分、IP级5000/分
   - 服务层Sentinel：支付8000 QPS、账户5000 QPS、风控6000 QPS
   - 热点参数：用户ID维度单用户限200 QPS防刷
   - 排队等待模式：秒杀场景使用匀速排队(令牌桶10万/秒)避免直接拒绝
   - 熔断保护：下游熔断时上游快速失败，避免请求堆积
4. RPO与RTO及演练计划：
   - RPO：同城双活≈0(同步复制)、异地灾备≤5分钟(异步binlog)；RTO：同城≤30秒(Keepalived)、异地≤15分钟(人工+自动化切换)
   - 演练分四级：①组件级(每月)单服务故障切换；②机房级(每季度)单机房断电演练；③链路级(每半年)核心交易全链路切换；④全站级(每年)双活全量切换+回切
   - Chaos Engineering常态化：Chaos Monkey随机杀Pod、Chaos Blade注入网络延迟/丢包、Toxiproxy模拟依赖异常
   - 演练窗口选择凌晨低峰期，配置自动回滚机制，演练结束后输出RTO实测报告
   - 业务连续性BCM计划：核心交易降级路径、客服应急话术、监管报备预案

**踩分要点**：
1. 容灾架构需明确每层冗余方案与切换机制(2分)
2. 熔断降级需给出具体阈值、降级策略与隔离手段(2分)
3. 限流设计需说明分层粒度与算法选择(2分)
4. RPO/RTO需量化指标与容灾分级匹配(2分)
5. 演练计划需分级别、频率、回滚机制完整(2分)
