## 今日核心概念
### 1. 分布式缓存架构模式
定义：分布式缓存通过将热点数据存储在靠近应用的内存节点中，降低数据库访问压力、提升系统吞吐与响应速度的架构方案。
关键要点：
- 旁路缓存（Cache Aside）：应用先读缓存，未命中回源数据库并回填缓存，写操作直接更新数据库后失效缓存，应用维护缓存逻辑，最常用但有双写不一致窗口
- 读写穿透（Read/Write Through）：应用只与缓存交互，缓存层同步回源数据库，封装性好但实现复杂，依赖同步写入性能
- 异步写入（Write Behind）：写操作直接更新缓存并异步批量落库，性能最高但有数据丢失风险，金融场景慎用
- 缓存预热：系统启动时主动加载热点数据，避免冷启动雪崩，常用方式为启动时拉取+运行时定时刷新
- 适用选型：读多写少用旁路，强一致要求高用读写穿透，可丢失部分写入用异步写入

### 2. 多级缓存架构
定义：通过本地缓存+分布式缓存+数据库形成分层缓存链路，逐层扩大容量、逐层降低访问速度的分级缓存设计。
关键要点：
- 三级架构：Caffeine本地缓存（进程内，纳秒级，几GB上限）+ Redis分布式缓存（跨进程，毫秒级，TB级）+ 数据库（持久化，10毫秒级）
- 命中率模型：L1命中率95%+ L2命中率90%+ DB命中率1%，整体命中率99.99%，DB QPS降低万倍
- 数据同步：本地缓存通过Redis Pub/Sub广播失效消息失效各节点本地缓存，RocketMQ/Kafka兜底保证可靠
- 一致性权衡：本地缓存容忍秒级不一致（设置TTL 60s），Redis容忍毫秒级不一致（失效延迟），DB为强一致基线
- 适用场景：电商详情页、社交Feed流、热点新闻、商品库存展示等超高读QPS场景

### 3. 缓存三大问题及解决方案
定义：缓存穿透、击穿、雪崩是分布式缓存系统的三大典型故障模式，分别对应"无中生有""定点爆破""集体阵亡"三类风险。
关键要点：
- 缓存穿透：查询不存在的数据绕过缓存直击DB。解决方案：布隆过滤器（提前拦截不存在的key）+ 空值缓存（缓存null值短TTL）+ 接口参数校验
- 缓存击穿：热点key过期瞬间海量请求穿透到DB。解决方案：分布式锁（只允许一个线程回源）+ 逻辑过期（不设TTL，后台异步刷新）+ 永不过期+ 单一热点key加锁排队
- 缓存雪崩：大量key同时过期或缓存集群宕机导致DB压力骤增。解决方案：过期时间随机化（基础TTL+随机偏移）+ 多级缓存兜底+ 熔断降级+ 缓存集群高可用（主从+哨兵+Cluster）
- 故障分级：穿透影响特定key、击穿影响单个热点key、雪崩影响全局，防范级别逐级升高

### 4. 缓存一致性策略
定义：在保证数据库与缓存数据一致的多种方案中，根据业务场景权衡一致性强度、性能与复杂度的方法论。
关键要点：
- Cache Aside模式：先更新DB再失效缓存（不是更新），原因：并发更新时"先更新DB后更新缓存"易出现旧值覆盖新值问题
- 延迟双删：更新DB前后各删一次缓存（延迟500ms-1s后二次删除），解决主从同步延迟导致的脏读
- 基于binlog同步：Canal监听MySQL binlog解析后投递MQ，异步服务消费消息失效/更新缓存，毫秒级延迟、最终一致
- 版本号机制：数据带版本号v，更新时CAS版本号匹配才更新，避免ABA问题，实现强一致但牺牲性能
- 强一致场景：金融账户余额、库存扣减必须读DB+分布式锁+事务，不依赖缓存
- 一致性级别选择：会话一致性/用户一致性可用本地缓存，跨用户一致必须读Redis，业务强一致必须读DB

### 5. Redis集群架构模式
定义：通过主从复制、哨兵机制、Cluster分片三种模式解决Redis高可用与水平扩展问题的集群方案。
关键要点：
- 主从复制：1主N从，读写分离+数据冗余，从节点全量同步（RDB）+增量同步（repl_backlog），主节点单点写瓶颈
- 哨兵模式（Sentinel）：2N+1节点监控主从状态，自动故障转移（主观下线SDOWN+客观下线ODOWN+Leader选举+配置传播），RTO<30s
- Cluster分片：16384哈希槽分配到N个主节点，每个主节点配1-N个从节点，Gossip协议通信，客户端智能路由（smart client）或代理层（Twemproxy/Codis）
- 数据分片算法：CRC16(key) % 16384，Hash Tag（{}包裹保证同key同槽）支持多key操作如MGET
- 选型建议：<10GB数据用哨兵，>10GB或高并发写用Cluster，金融级要求用Cluster+异地多活
- 持久化策略：RDB（定时快照，恢复快但可能丢数据）+ AOF（追加日志，最多丢1秒）+ 混合持久化（RDB+AOF兼顾）

## 案例分析题
**题目**：某电商平台在大促期间遭遇严重缓存故障。系统采用Redis Cluster（12主12从）+ Caffeine本地缓存两级架构，承载商品详情页日均20亿次读请求（峰值QPS 50万）。大促开始第1分钟，平台发布10000款秒杀商品到Redis Cluster，活动开始瞬间出现：①首页大量空白（缓存未命中）②部分商品页报"系统繁忙"（服务超时）③Redis节点CPU飙升至95%、连接数耗尽④数据库连接池被打满，订单提交失败。作为架构师，请分析故障原因并给出完整优化方案，要求至少涵盖缓存预热、击穿防护、雪崩防护、Redis保护、数据库保护五个层面。

**参考答案**：
**故障根因分析**：
1. 首页空白=缓存预热缺失，新商品key未提前加载，Caffeine和Redis均无数据，请求穿透到DB
2. "系统繁忙"=击穿效应，10000个热点key同时过期或首次访问，单key瞬间50万QPS穿透到DB
3. Redis CPU 95%连接耗尽=大key查询（秒杀商品详情含图片列表达KB级）+ 大量MGET/KEYS命令阻塞
4. DB连接池打满=雪崩效应，多级缓存全面失效，所有流量穿透到DB，订单与查询互斥争抢连接

**优化方案**：
**1. 缓存预热（三阶段）**：
- 大促前T-7天：定时任务全量加载TOP 10万商品到Redis（分批1000/批，间隔100ms）
- 大促前T-1天：加载预测热点商品（基于历史销量+预售数据）
- 大促开始T-0：消息队列异步接收商品上架消息实时加载，Caffeine通过Redis Pub/Sub失效

**2. 击穿防护（多方案叠加）**：
- 逻辑过期：商品数据不设TTL，存储逻辑过期时间字段
- 后台异步刷新：Cache Aside后台任务检测过期自动刷新，业务线程直接返回旧值
- 分布式锁兜底：本地锁（ConcurrentHashMap分段锁）+ Redis分布式锁（Redisson tryLock），防止并发回源
- 单key互斥：使用SETNX在缓存层加短期互斥锁，只允许一个线程回源

**3. 雪崩防护**：
- 过期时间随机化：基础TTL 30分钟+ 随机0-300秒偏移
- 多级缓存兜底：Caffeine本地缓存保留秒级过期数据，避免Redis故障时全量穿透
- 熔断降级：Sentinel/Hystrix监控Redis和DB响应时间，超过阈值自动熔断返回兜底数据
- Redis Cluster高可用：每个master至少2从，故障自动切换，异地多活

**4. Redis保护**：
- 大key拆分：商品详情拆分为基本信息+图片列表+规格参数三个key，单独MGET
- 禁用危险命令：rename-command KEYS ""、rename-command FLUSHALL ""、rename-command FLUSHDB ""
- 客户端限流：每个应用实例连接池上限50，最大QPS 1万，超限排队
- 慢查询监控：slowlog-log-slower-than 10ms，自动告警

**5. 数据库保护**：
- 连接池隔离：订单库连接池（200）与查询库连接池（300）物理隔离
- 读写分离：读请求路由到5个从库，写请求走主库
- 限流降级：商品查询服务独立限流，超阈值返回缓存兜底数据
- 异步队列：订单写入走RocketMQ异步削峰，DB消费速率恒定

**架构改造**：
- 接入Sentinel实现Redis/DB双端熔断
- 引入Canal监听商品变更binlog自动失效缓存
- 部署Prometheus+Grafana监控缓存命中率（目标>99%）、Redis慢查询、DB慢SQL

**踩分要点**：
1. 故障定位需逐条对应四大现象，分析精准（预热缺失/击穿/雪崩/连接耗尽）
2. 预热方案必须有时间维度（T-7/T-1/T-0三阶段），体现工程落地细节
3. 击穿防护需说明逻辑过期+分布式锁+单key互斥三层防御，不是单一方案
4. 雪崩防护要包含TTL随机化+多级缓存+熔断+集群高可用完整体系
5. Redis保护要提及大key拆分+命令禁用+连接池+慢查询监控实战配置
6. DB保护要分连接池隔离+读写分离+限流+异步削峰四层
7. 强调缓存命中率99%+目标、监控告警、自动化运维的体系化思维
8. 避免只罗列技术名词，必须有具体的配置值（TTL 30min、连接池200/300、慢查询10ms）

## 记忆口诀
**缓存模式三兄弟**：旁路应用管、穿透同步落、异步最危险
**三级缓存链**：Caffeine纳秒+Redis毫秒+DB十毫秒，命中率99.99%
**缓存三大病**：穿透布隆挡、击穿单key锁、雪崩TTL随机+熔断
**缓存一致性**：先更DB再失效，双删延迟兜底，binlog最终一致
**Redis集群演进**：主从读写分、哨兵自动切、Cluster分片16384槽
**Hash Tag妙用**：{}包住同槽位，MGET多key同节点
**大key危害**：带宽阻塞、慢查询、删除阻塞、内存倾斜
**缓存预热三阶段**：T-7全量加载、T-1热点预测、T-0消息实时
**Redis危险命令**：KEYS/FLUSHALL/FLUSHDB必须rename禁掉
**熔断降级三剑客**：Sentinel/Hystrix/resilience4j，超阈值返兜底
