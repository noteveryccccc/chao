## 今日核心概念
### 1. 大数据处理架构（Lambda 与 Kappa）
定义：Lambda 架构通过批处理层提供高吞吐、准确的全量计算，通过速度层提供低延迟、增量近似计算，并对查询结果进行合并；Kappa 架构统一以流处理为主，将历史与实时都视为事件流，借助可重放存储和统一流计算引擎简化系统复杂度。
关键要点：
- Lambda 架构强项是离线与实时结果融合，适合数据量大、对准确性敏感的报表、对账、风控和反欺诈场景。
- Kappa 架构强项是链路简单、迭代快，但要求消息中间件支持长期可重放存储、精确一次语义和状态可恢复。
- 选型核心看延迟容忍度、历史修正频次、计算一致性要求和运维复杂度，不能盲目追随新架构。
- Lambda 演进到 Kappa 通常从批层逐步将历史任务迁移到流处理，并对账与口径进行长期校验。
- 双架构常并存的折中方案是用流批一体的存储与计算引擎，例如 Iceberg/Hudi/Paimon 加 Flink。

### 2. 分布式存储体系
定义：分布式存储系统通过数据分片、多副本与一致性协议，在大规模集群中提供可扩展、高可用、高吞吐的数据存取能力，是大数据平台的底座。
关键要点：
- 三类典型形态包括分布式文件系统（HDFS）、分布式对象存储（S3/OSS/COS）和分布式块与统一存储（Ceph）。
- 数据分片策略有哈希分片、范围分片和一致性哈希，需要结合访问模式、扩容成本和热点倾斜综合选择。
- 副本一致性协议常用 Raft、Paxos 和 Quorum，要区分强一致性、最终一致性和因果一致性。
- 纠删码可显著降低存储开销，但写入与恢复代价更高，常用于冷数据，温热数据仍优先多副本。
- 元数据是性能和扩展的瓶颈，需要独立的元数据服务、缓存与冷热分层，避免把元数据全部塞进主存储。

### 3. 大数据计算模式与引擎选型
定义：大数据计算模式根据数据形态与时效要求分为批处理、流处理、交互式查询、图计算和机器学习训练，不同模式匹配不同引擎，统称为大数据计算生态。
关键要点：
- 批处理引擎（MapReduce/Spark）适合全量离线计算，数据吞吐量高、容错好、但延迟通常分钟级以上。
- 流处理引擎（Flink/Kafka Streams/Spark Streaming）以事件流为基础，强调低延迟、状态管理和精确一次语义。
- 交互式查询引擎（Presto/Trino/ClickHouse/Doris）面向即席分析与 OLAP，强调列存、向量化执行和高并发点查。
- 图计算引擎（Spark GraphX/Graph/TigerGraph）处理关系遍历与复杂网络分析，适合风控反欺诈和知识图谱。
- 机器学习训练（Spark ML/PyTorch/TensorFlow + Parameter Server/Ray）需要数据并行、模型并行和参数同步能力。
- 引擎选型应关注数据规模、延迟要求、一致性、SQL 兼容性、生态成熟度和团队栈匹配，不要追求"全家桶"。

### 4. 大数据治理与数据安全
定义：大数据治理是对数据标准、质量、血缘、安全、生命周期和价值进行持续管理与度量的一套方法与工具组合，确保数据可信、可控、可用。
关键要点：
- 治理对象包括元数据、主数据、引用数据、业务数据和日志数据，需建立统一目录、统一标识和统一口径。
- 数据分级分类是安全治理的基础，至少按敏感度分为公开、内部、敏感和核心四级，并配套脱敏、加密和访问控制。
- 数据血缘要贯穿采集、传输、存储、加工、消费和销毁六个环节，支撑影响分析、问题追溯和合规审计。
- 数据生命周期管理通过冷热分层、保留策略、自动归档与销毁，控制存储成本和合规风险。
- 数据质量需要从完整性、准确性、一致性、及时性、唯一性和有效性六个维度持续度量并设置质量门禁。

## 案例分析题
**题目**：某省级政务大数据平台需整合市场监管、社保、税务和民政等部门数据，建设统一数据底座，支撑秒级指标查询、日级离线报表、实时风控预警和对外共享服务。现有系统使用传统关系数据库集中存储，存在入库慢、查询慢、扩展困难、历史数据缺失等问题。请从系统架构设计师角度回答：
1. 应如何选择大数据处理架构，并对 Lambda 与 Kappa 进行权衡分析；
2. 分布式存储层应如何分层设计，兼顾冷热数据、扩展性和成本；
3. 计算引擎应如何选型和组合，满足不同业务时效需求；
4. 数据治理与数据安全应如何统一规划；
5. 在不影响现有业务的前提下，给出分阶段落地的实施路径。

**参考答案**：
1. 综合延迟要求、数据准确性、历史修正频率和运维复杂度，建议采用 Lambda 向 Kappa 演进的混合架构。秒级指标查询和实时风控使用流处理引擎实现秒级响应；日级报表、对账和监管报送使用批处理引擎保证全量准确；统一消息中间件使用具备长期可重放能力的 Kafka 集群，把批处理和流处理都建立在同一份事实数据上。考虑到监管口径偶尔修正和补数需求，Lambda 仍是中短期可靠选择，并在条件成熟时逐步把离线任务迁移到流批一体引擎，再向 Kappa 收敛。

2. 存储层建议四层架构。贴源层采用对象存储保存原始数据、接口日志和文件材料，支持长期归档和重放；明细层采用列式分布式数据库或数据湖（Iceberg/Hudi/Paimon）保存清洗后的明细和变更日志，支撑即席查询和时间旅行；汇总层采用高性能 MPP 数据库（ClickHouse/Doris/StarRocks）保存多维聚合结果和指标视图；共享层通过 API 网关与数据目录对外提供受控共享和脱敏服务。冷数据进入对象存储并启用纠删码和生命周期策略，热数据保留在三副本的列式存储，SSD 与 HDD 按访问频度分层。

3. 计算引擎按场景组合。离线批处理采用 Spark + 湖仓，承担 ETL、特征回算和监管报送；实时流处理采用 Flink，承担风控事件、指标实时聚合、异常告警和事件驱动；交互式查询采用 MPP 引擎，承担自助 BI、API 查询和即席分析；机器学习训练采用 Spark ML 和 PyTorch 集群，承担模型训练与离线打分；在线推理采用独立模型服务，借助消息中间件和特征库支撑实时风控。引擎之间通过统一数据目录、统一指标口径和统一 ID 主键打通，避免重复计算和指标不一致。

4. 数据治理需要建设元数据平台、主数据平台、数据标准、数据质量和数据安全五条线。元数据统一采集存储、计算和服务血缘，支持影响分析和数据地图；主数据落实权威来源，统一个人、法人和证照编码；数据标准覆盖命名、口径、字典和编码，形成可复用的字段级规范；数据质量在关键链路设置质量门禁并对接告警；数据安全按分级分类执行脱敏、加密、水印、审计和访问控制，关键操作保留不可篡改日志。共享前必须经过授权审批和合规评估，敏感数据不出域、不落地。

5. 实施路径分五阶段。第一阶段完成现状盘点、指标梳理、数据分级和统一标准，搭建元数据平台和数据目录。第二阶段建设统一消息中间件、分布式存储和湖仓底座，逐步将贴源数据迁移到对象存储和湖表。第三阶段先在 1 至 2 个低风险部门试点离线批处理和指标查询，验证准确性和性能，沉淀模板。第四阶段引入流处理引擎，落地实时风控、实时指标和接口开放，并对账与离线口径达成一致。第五阶段逐步扩大接入部门，关闭旧库查询入口，建立统一的运行度量、容量规划和成本治理机制。

**踩分要点**：
- 架构选择要明确"为什么选 Lambda/Kappa/混合"，依据是延迟、准确性、历史回放和运维复杂度，不是简单背定义。
- 存储分层要分清贴源、明细、汇总、共享四层职责和冷热数据控制，不能只说"用分布式存储"。
- 计算引擎组合要说明离线批、流处理、交互式查询和机器学习各自匹配的场景，不能一刀切。
- 数据治理要给出元数据、主数据、标准、质量、安全五条主线，并落到分级、脱敏、审计和门禁。
- 落地路径必须保证业务连续性，体现先试点再推广、先离线再实时、先标准再治理的演进思路。
- 全程要体现架构可演进性，避免一次性大替换，并把"统一口径、统一身份、统一 ID"作为基线。

## 记忆口诀
大数据架构两兄弟：Lambda 双轨 Kappa 单流；先 Lambda 验证再 Kappa 收敛。
分布式存储三层管：贴源对象存、明细数据湖、汇总 MPP 快；冷数据走纠删，热数据三副本。
计算引擎按场景：批 Spark、流 Flink、查 MPP、图 GraphX、学 PyTorch；按需搭配不要全上。
数据治理五条线：元数据、主数据、标准线、质量线、安全线；分级分类是底线。
数据安全四件套：脱敏、加密、审计、水印；敏感不出域，操作可追溯。
实时风控三步走：事件接入、特征计算、规则触发；离线对账兜底，离线和实时口径统一。
湖仓选型三标志：ACID、时间旅行、模式演进；选 Iceberg/Hudi/Paimon 长期更稳。
平台演进五阶段：盘点标准、建湖存算、离线试点、引入实时、扩面下线；业务连续是红线。
