## 今日核心概念

### 1. 云原生架构与运行时设计
定义：云原生架构是基于容器、微服务、服务网格、不可变基础设施与声明式 API 构建的运行时形态，通过弹性、可观测、可恢复、可灰度的运行机制让应用充分利用云平台的能力，是分布式系统上云的标准范式。
关键要点：
- 容器化封装应用及其依赖，配合 OCI 镜像标准实现一次构建多环境运行，配合 init 容器、sidecar、ephemeral 容器满足复杂启动与生命周期需求。
- Kubernetes 作为编排事实标准提供声明式 API、控制器循环、Self-healing、HPA/VPA/Cluster Autoscaler 三级弹性、滚动升级与回滚机制。
- 服务网格 Istio/Linkerd 把通信、安全、可观测、流量治理从应用下沉到基础设施层，通过 sidecar 代理实现无侵入的服务间治理。
- 不可变基础设施强调镜像即环境、临时容器、远程配置，避免 SSH 改环境带来的漂移、不可复现与审计缺失。
- 配合 GitOps、Argo CD/Flux 实现声明式变更与自动同步，把发布从手工运维转为可审计的流水线作业。

### 2. 分布式数据一致性与事务架构
定义：分布式数据一致性是指在多节点、多副本、多地域的数据系统中，读写操作在并发、故障与分区条件下仍能保证业务语义一致的能力体系；事务架构则是在分布式场景下对 ACID 与 BASE 的权衡与落地。
关键要点：
- CAP 三要素一致性、可用性、分区容错性不可兼得，工程上往往在 P 前提下做 C 与 A 的动态权衡，例如电商大促优先 A、资金交易优先 C。
- 一致性级别包含强一致性、线性一致性、顺序一致性、因果一致性、最终一致性五档，按业务语义分层选择避免过度设计。
- 分布式事务三件套两阶段提交 2PC、三阶段提交 3CC、Saga 长事务补偿、TCC 预留确认取消、最大努力通知，各有适用场景与代价。
- 共识算法 Raft/Paxos/Zab 为分布式协调与选主提供强一致保障，etcd、Consul、TiKV 均基于 Raft 实现。
- 工程落地要结合幂等设计、版本号、向量时钟、Quorum 读写、读写分离与冲突合并，把一致性从协议层下沉到业务层。

### 3. 安全架构与零信任体系
定义：安全架构是从身份、网络、应用、数据、运维五个维度建立纵深防御的体系化设计，零信任则以"永不信任、持续验证、最小权限"为核心原则重塑边界，把传统城堡式防护转向以身份为核心的细粒度控制。
关键要点：
- 纵深防御覆盖网络层 WAF/DDoS、主机层 EDR/加固、应用层 RASP/审计、数据层加密/脱敏、运维层堡垒机/审计，避免单点失效。
- 零信任三大原则持续验证、最小权限、动态信任，通过身份、设备、行为、上下文四要素实时计算访问决策。
- 零信任核心组件包含 IAM、SDP 软件定义边界、PAM 特权访问、UEBA 行为分析、IDP 身份提供商，统一策略平面 PEP/PDP/PaP。
- 身份治理结合 SSO、MFA、ABAC、RBAC 与 SCIM/Just-In-Time 权限提升，把权限做成可申请、可审批、可过期的生命周期。
- 落地路径分三步走：先盘点资产与身份、再统一策略与网关、最后用微分段与持续验证收敛残余风险，避免一锅端式重造。

### 4. 可观测性体系与 SRE 实践
定义：可观测性是通过指标、日志、链路追踪三大支柱理解系统内部状态并回答未知问题的能力体系；SRE 实践则是把可靠性工程化、产品化、可持续化的运维方法论，强调用工程手段解决运维问题。
关键要点：
- 三大支柱 Metrics、Logs、Traces 互不可替代：指标回答趋势与告警、日志回答细节与排障、链路回答调用与依赖。
- SLO/SLI/SLA 三层指标体系：SLI 是测量、SLO 是目标、SLA 是对外承诺，形成研发、运维、业务的共同语言。
- 错误预算 Error Budget 把可靠性决策从主观变为可量化：预算耗尽即冻结非必要发布，倒逼工程改进。
- AIOps 用机器学习做异常检测、根因分析、日志聚类、告警降噪与智能扩缩容，把运维从经验走向数据驱动。
- On-call 轮值、运行手册 Runbook、事后复盘 Postmortem、变更评审 CAB 是 SRE 文化落地四件套。

### 5. 架构治理与技术演进
定义：架构治理是把架构原则、技术选型、安全合规、风险控制通过制度、流程、工具沉淀到组织的方法；技术演进则是用 ADR、技术雷达、技术债务清单与渐进式重构持续逼近目标架构的持续工程。
关键要点：
- 架构治理三要素原则、流程、工具：原则定方向、流程保落地、工具提效率，三者缺一不可，否则沦为文档摆设。
- ADR 架构决策记录把上下文、方案、后果结构化，便于评审、追溯与传承，避免"决策在邮件、知识在口头"。
- 技术雷达把技术按采用、试验、暂缓、弃用四档分级，配合季度评审让团队对技术选型形成共识。
- 技术债务登记、评估、清理、复盘四步走，避免债务积压拖垮系统，把重构从应急变成常态。
- 架构评审、变更评审、安全评审、容量评审四类评审把治理嵌进流程，确保重大决策有据可依、有责可追。

## 案例分析题

**题目**：某大型股份制银行正在推进"核心系统现代化"工程，把运行 18 年、承载 4.2 亿客户、日均交易量 6.8 亿笔的 COBOL 大机核心系统迁移到分布式开放平台。新核心需同时支撑账户、存款、贷款、支付、清算、理财、信用卡、对公 8 大业务线，承接手机银行、网上银行、自助终端、柜面、开放银行、银企直连 6 类接入，日终批处理时间窗从原 4 小时压缩至 2 小时内，7×24 业务连续性可用率不低于 99.999%。工程由行领导挂帅，14 个业务部门、9 个技术中心、3000 余名研发人员参与，分三批 36 个月完成。当前面临五大挑战：一是主机时代遗留的 6000 万行 COBOL 代码、8000 多个批处理作业、12 万个文件存储路径改造工作量巨大；二是核心交易强一致性与资金零差错要求极高，分布式事务在跨地域多活场景下难以兼顾性能与一致性；三是新核心必须符合金融行业监管要求，等保 2.0 三级、金融行业网络安全等级保护、数据安全法、个人金融信息保护等合规要求交织；四是 14 个业务部门诉求各异、8 大产品线迭代节奏不同，如何在统一架构下兼顾标准化与灵活性；五是工程周期 36 个月、技术栈全面切换、人员流动率 8%，如何避免半成品上线、避免架构走样、避免技术债务堆积。请从系统架构设计师角度回答：
1. 云原生架构与运行时如何设计，容器编排、服务网格、可观测性、GitOps 如何选型与落地；
2. 分布式数据一致性与事务架构如何权衡，强一致场景、最终一致场景、跨地域多活场景分别如何设计；
3. 安全架构与零信任体系如何构建，覆盖网络、应用、数据、运维、监管合规五个维度；
4. 可观测性体系与 SRE 实践如何支撑 99.999% 可用率与 2 小时日终窗口；
5. 架构治理与技术演进如何覆盖 14 个业务部门、3000 多人、36 个月长周期。

**参考答案**：
1. 云原生运行时按"两地三中心 + 微服务网格 + GitOps"落地。两地三中心按同城双活 + 异地灾备设计，主机房上海、副机房深圳、灾备成都，分别承接 50%/50% 流量与冷备切换。Kubernetes 集群分核心交易区、清算批处理区、对公接入区、互联网接入区四个大区，每个大区独立升级、独立弹性。服务网格统一 Istio 提供 mTLS、流量染色、熔断限流、A/B 测试、灰度发布，让 8000 多个批处理作业与 4.2 亿客户的实时交易共用一套治理。镜像仓库 Harbor、密钥管理 HashiCorp Vault、配置中心 Apollo 配合 Argo CD 实现 GitOps，声明式变更自动同步，避免手工改环境带来的漂移。CI/CD 流水线分金丝雀发布与蓝绿发布两类：交易类业务走金丝雀按 1%→5%→25%→100% 灰度，批处理类作业走蓝绿切流确保断点可回滚。不可变基础设施、临时容器、镜像签名、内容寻址存储 CotStore 全程配套，确保上线即可回滚。
2. 分布式数据一致性按"账户强一致、记账最终一致、对账定时一致"三层设计。账户层核心数据采用分布式数据库 TiDB/OceanBase 提供强一致与水平扩展，单笔交易在 50ms 内完成，资金差错零容忍。记账层通过 Saga 模式拆解扣款、记账、通知、清算四个子事务，配合幂等表与补偿任务保证最终一致，跨行清算延时不超过 5 分钟。对账层每日凌晨跑批对账，自动核对明细与余额，差异自动告警并人工处理。跨地域多活按"单元化 + 数据分区"设计：客户按身份证/手机号哈希分片，每个单元服务本地读写、跨单元只走异步复制与对账；强一致交易路由到主单元，最终一致业务允许就近读写。共识算法统一 Raft，账户集群三副本部署、Paxos 兜底用于跨集群协调；冲突解决用向量时钟与最后写入胜出结合业务优先级，避免无脑覆盖。
3. 安全架构与零信任体系按"五层纵深 + 零信任收敛"落地。网络层 WAF、抗 DDoS、BGP 高防、SDN 微分段覆盖南北向与东西向流量；应用层 RASP 注入运行时防护，结合 SAST/DAST/SCA 把漏洞拦在流水线；数据层透明加密 TDE、字段级加密、动态脱敏、KMS 密钥分级管理，备份加密与异地容灾；运维层堡垒机、特权操作审批、命令审计录像、零信任 PAM 与 JIT 临时提权；监管层等保 2.0 三级要求落地、个人金融信息分级、跨境数据评估、监管报送自动化。零信任三层落地：第一步盘点资产、身份、设备、接口，建立统一身份目录；第二步部署 SDP 软件定义边界、ZTNA 零信任网络访问、身份代理网关，覆盖研发、运维、合作方；第三步引入 UEBA、IDP、持续验证、动态信任评估，收敛残余风险。密钥管理统一 HashiCorp Vault + HSM 集群，密钥不落代码、密钥不出现明文、密钥双人轮换。
4. 可观测性体系与 SRE 实践按"三支柱 + SLO + 错误预算"构建。三大支柱：指标 Prometheus + VictoriaMetrics、日志 Loki + ES、链路 Jaeger + SkyWalking，统一采集、查询、告警。SLO 按业务分层：实时交易成功率 99.999%、日终批处理完成率 100%、跨行清算成功率 99.99%、接口可用率 99.95%，配套 SLI 测量与 SLA 对外承诺。错误预算按月度统计：实时交易月度可用率低于 99.999% 即冻结非必要发布，倒逼研发优先解决可靠性。日终窗口 2 小时约束下，批处理作业并行化、增量计算、数据预加载、断点续跑、跨地域并行调度，把原 4 小时压缩至 2 小时，剩余 1 小时做容错与对账。AIOps 用于异常检测、根因分析、日志聚类、容量预测、告警降噪，把告警噪声降低 80%。On-call 7×24 轮值、Runbook 脚本化、Postmortem 闭环、CAB 变更评审四大文化配套，确保运维知识持续沉淀。
5. 架构治理与技术演进按"治理三要素 + 演进四件套"覆盖。治理三要素：原则定方向——核心强一致、对外可用、数据零差错、合规零容忍；流程保落地——架构评审、变更评审、安全评审、容量评审四类评审嵌进流程；工具提效率——ADR 平台、技术雷达系统、技术债务登记簿、架构资产可视化平台。架构决策通过 ADR 结构化记录，季度架构例会评审与复盘；技术雷达按季度发布，标记采用、试验、暂缓、弃用四档；技术债务按 P0/P1/P2 三档登记，每月预留 20% 容量做重构。渐进式演进四件套：防腐层隔离主机与开放平台、绞杀者模式逐步替代老接口、特性开关按业务线灵活启用、双跑并行直到完全退役。跨部门协同设三层：架构委员会决策、领域架构师落地、影子架构师备份，确保 3000 人队伍不因人员流动而失能。36 个月三批切换按"先外围后核心、先查询后交易、先非实时后实时"顺序，第一批切换网银与查询类、第二批切换对公与清算、第三批切换核心账户，全程灰度、可回滚、可审计。

**踩分要点**：
- 云原生运行时必须写明 Kubernetes + Istio + GitOps 三件套，给出"两地三中心"和"四类发布"具体策略，不能笼统说"上云"。
- 分布式一致性需明确区分账户强一致、Saga 最终一致、对账定时一致三层场景，给出共识算法、单元化、幂等设计。
- 安全架构要点出"五层纵深 + 零信任收敛"路径，给出 RASP、KMS、PAM、SDP、UEBA 等具体组件与合规对接。
- 可观测性需落到 SLO/SLI/SLA + 错误预算，给出 AIOps、日终压缩 4→2 小时的具体技术与四类文化配套。
- 治理与演进要写出治理三要素、四类评审、技术雷达、技术债务、防腐层绞杀者特性开关四件套，给出 36 个月三批切换顺序。
