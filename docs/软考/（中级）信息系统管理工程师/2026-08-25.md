## 今日核心概念
### 1. 项目范围管理
定义：项目范围管理是确保项目包含且只包含为成功完成项目所需的工作的管理过程，核心解决"做什么"与"不做什么"的问题。
关键要点：
- 六大过程：规划范围管理、收集需求、定义范围、创建WBS、确认范围、控制范围
- 范围蔓延（Scope Creep）：未经控制地扩大项目范围，必须走变更控制流程
- 范围镀金（Gold Plating）：未经批准擅自添加额外功能以求"更好"，同样属于违规
- 产品范围 vs 项目范围：前者描述最终产品特性，后者描述为交付产品需做的工作
- 范围基准 = WBS + WBS词典 + 范围说明书，经CCB批准后成为绩效测量基线

### 2. WBS工作分解结构
定义：WBS是以可交付成果为导向，对项目团队实施的工作进行层次化分解的结构，将项目总工作分解为更小、更易管理的部分。
关键要点：
- 100%原则：WBS必须包含项目全部范围工作，不多也不少
- 分解方法：自上而下、可交付成果导向、可管理性原则（8/80原则：工作包不小于8小时、不大于80小时）
- 工作包（Work Package）：WBS最底层，是进度、成本、质量等估算的基础
- WBS词典：对每个工作包的详细说明，包含责任人、资源、验收标准等
- 分解层次通常4-6层，建议3层结构：项目→阶段→工作包

### 3. 项目进度管理
定义：项目进度管理是保证项目能够在规定时间内完成各项工作的管理过程，核心解决"何时做"的问题。
关键要点：
- 七大过程：规划进度管理、定义活动、排列活动顺序、估算活动资源、估算活动持续时间、制定进度计划、控制进度
- 关键路径法（CPM）：网络中持续时间最长的路径，决定项目最短完工时间
- 关键活动：关键路径上的活动，总时差为零，延误则项目延误
- 进度压缩技术：赶工（增加资源，缩短关键活动时长，成本↑）vs 快速跟进（并行执行原本串行的活动，风险↑）
- 资源优化技术：资源平衡（调整开始/结束日期平衡资源，可能改变关键路径）vs 资源平滑（不改变关键路径，调整非关键活动）

### 4. 网络图与关键路径
定义：网络图是表示项目活动之间逻辑关系的图形工具，关键路径是网络图中最长的路径。
关键要点：
- 节点表示法（PDM/前导图法）：方框表示活动，箭头表示逻辑关系（FS/FF/SS/SF）
- 最早开始（ES）/最早完成（EF）：顺推计算，从起点开始
- 最晚开始（LS）/最晚完成（LF）：逆推计算，从终点倒推（终点LF=EF）
- 总时差（TF = LS-ES = LF-EF）：不影响总工期的可延误时间
- 自由时差（FF）：不影响紧后活动最早开始的可延误时间
- 帕累托图识别关键路径：总时差=0的活动串联即为关键路径

### 5. 范围确认与范围控制
定义：范围确认是干系人验收已完成的可交付成果，范围控制是监控范围状态并管理范围变更的过程。
关键要点：
- 范围确认 vs 质量控制：前者关注干系人接受（结果验收），后者关注可交付成果正确性（技术验证）
- 范围确认贯穿项目始终，每个可交付成果完成时都需确认
- 范围控制工具：偏差分析、趋势分析、变更控制系统、配置管理系统
- 范围变更必须走变更控制流程：申请→评审→CCB审批→实施→验证→归档
- WBS是范围控制的基准，所有变更必须与WBS对应分析

## 案例分析题
**题目**：
某政务信息化项目于2026年3月1日启动，工期6个月，预算280万元。项目范围包括需求调研、系统设计、开发、测试、部署上线5个阶段。项目经理小王采用关键路径法编制了进度计划，关键路径为：需求调研(20天)→系统设计(30天)→开发(60天)→测试(30天)→部署上线(10天)，总工期150天。

项目执行到第60天时，小王盘点进度：
- 需求调研已按时完成
- 系统设计已完成28天工作量（计划30天）
- 开发活动原本计划第51天开始，已于第53天开始，目前完成15天工作量（计划30天）

与此同时，业务部门提出新需求：增加移动端适配、政务数据共享接口、数据大屏可视化三项功能。客户方领导口头同意"先做着"，但未走变更审批流程。

问题：
1. 计算项目当前进度偏差（SV）和进度绩效指数（SPI），并判断进度状态。
2. 分析小王在范围管理方面存在哪些问题？针对业务部门提出的新需求，应如何处理？
3. 若必须按原定工期完工，可采取哪些进度压缩措施？请说明赶工和快速跟路的区别。

**参考答案**：
1. 挣值计算：
   - 计划值PV：需求调研20天 + 系统设计30天 + 开发（已完成15天工作量，按计划前30天）= 20 + 30 + 30 = 80天工作量
   - 挣值EV：实际完成的工作量 = 20（需求调研）+ 28（系统设计）+ 15（开发）= 63天工作量
   - 进度偏差SV = EV - PV = 63 - 80 = -17天（落后17天工作量）
   - 进度绩效指数SPI = EV/PV = 63/80 = 0.79
   - SPI < 1，项目进度落后，需要采取纠正措施。

2. 范围管理问题：
   - 范围蔓延：业务部门新增三项功能未走变更控制流程，客户口头同意"先做着"属于重大违规
   - 缺乏范围基准管控：没有用WBS和范围说明书明确"做什么/不做什么"
   - 缺乏变更控制流程：CCB（变更控制委员会）未发挥作用
   - 缺乏需求收集与评审机制：需求变更未走正式流程
   正确处理方式：
   - 立即停止新功能开发，恢复执行原范围基准
   - 由项目经理提交变更请求，组织CCB评审
   - 评估三项新功能对范围、进度、成本、质量的影响
   - CCB审批后，必要时签订补充协议或调整进度/预算基准
   - 在配置管理系统中记录变更

3. 进度压缩措施：
   - 关键路径上：开发（60天）、测试（30天）有压缩空间
   - 赶工（Crashing）：投入更多资源或加班，缩短关键活动工期。例如增加开发人员从4人扩至6人，可能将开发从60天压缩至45天。成本上升，质量风险增加。
   - 快速跟进（Fast Tracking）：将原本串行的活动并行执行。例如开发与测试并行、模块化开发分批测试。进度加快，但返工风险增加，需要更多协调工作。
   - 两者区别：赶工是"加速关键路径"，增加资源换时间；快速跟进是"并行关键路径"，压缩逻辑关系换时间。两者都增加项目风险。

**踩分要点**：
- SV/SPI计算公式必须准确，SPI<1判定为落后，>1为提前，=1为按计划
- 范围蔓延、范围镀金两个概念要区分清楚，范围蔓延是干系人加需求，范围镀金是团队擅自加
- 变更控制五步流程：申请→评审→CCB决策→实施→验证
- 赶工增加成本、快速跟进增加风险，这是核心区别
- 关键路径只压缩关键活动，非关键活动压缩无效

## 记忆口诀
项目范围六过程：**规需定确控收尾**（规划范围管理、收集需求、定义范围、创建WBS、确认范围、控制范围）

WBS分解三原则：**百八零**（100%原则、8/80原则、零层项目名）

进度管理七过程：**规定义排估制控**（规划、定义活动、排列顺序、估算资源、估算历时、制定计划、控制进度）

网络图双代号：**节点活动、箭头逻辑**（FS/FF/SS/SF四种依赖关系）

关键路径判定：**总时差为零**（TF=0即为关键路径）

挣值四指标：**PV计划、EV挣值、AC实际**（CV=EV-AC、SV=EV-PV；CPI=EV/AC、SPI=EV/PV）

偏差判读口诀：**CV正省负超、SPI正快负慢**（CV>0成本节约，CPI>1成本节约；SV>0进度提前，SPI>1进度提前）

进度压缩两招：**赶工加资源、快速并行走**（赶工增本、快速跟进增险）

范围变更五步走：**申评决实验归档**（申请、评审、CCB决策、实施、验证、归档）

范围蔓延vs镀金：**蔓延客户加、镀金团队加**（前者干系人提，后者团队擅自做）

范围基准三件套：**WBS、词典、说明书**（工作分解结构、WBS词典、范围说明书）

资源配置两策略：**平衡改关键、平滑不动关**（资源平衡可能改变关键路径，资源平滑不改变关键路径）

8/80原则：**不小八、不大八十小时**（工作包最小8小时、最大80小时）
