## 今日核心概念

### 1. 配置管理
定义：配置管理是通过技术和管理手段，对项目产品及其组成部分的功能特性、物理特性和变更情况进行标识、控制、记录、审计的过程，目的是保证项目交付物在整个生命周期内完整、一致、可追溯。

关键要点：
- 配置管理的主要活动包括制订配置管理计划、配置标识、配置控制、配置状态报告、配置审计和发布管理。
- 配置管理对象不仅包括源程序，还包括需求文件、设计文件、测试用例、接口文件、数据库脚本、部署文件、用户手册等。
- 配置管理员负责配置库管理、版本维护、状态记录和配置审计，但配置项变更仍需按规定履行审批程序。
- 配置管理贯穿项目全生命周期，不能等到开发完成后再集中补做。

### 2. 配置项与配置标识
定义：配置项是为配置管理目的而选定，并在配置管理过程中作为一个整体进行管理的工作成果。配置标识是识别配置项及其版本、属性和相互关系的活动。

关键要点：
- 典型配置项包括项目计划、需求规格说明书、系统设计说明书、源程序、测试报告、运行维护手册和软硬件环境参数。
- 每个配置项应具有唯一标识，至少记录名称、编号、版本、责任人、存放位置、当前状态和变更历史。
- 配置项一般分为受控配置项和非受控配置项；正式纳入配置库并需要履行变更控制的属于受控配置项。
- 配置项之间的依赖关系也应记录，避免只修改接口文件而遗漏相关程序、测试用例和用户手册。

### 3. 配置库与配置基线
定义：配置库是集中存放、管理和保护配置项的受控环境；配置基线是经过正式评审和批准，作为后续开发、测试及变更比较依据的一组配置项。

关键要点：
- 配置库可按管理要求划分为开发库、受控库和产品库，分别保存开发过程成果、已受控成果和正式发布成果。
- 基线一经建立，不能由开发人员自行修改，任何调整都必须提出变更申请并履行评估、审批、实施、验证和归档程序。
- 常见基线包括需求基线、设计基线、测试基线和产品基线。
- 建立基线应满足内容完整、评审通过、版本明确、责任清晰和可恢复等条件。
- 基线能够为范围确认、变更比较、版本回退、质量审计和责任追溯提供依据。

### 4. 配置变更控制
定义：配置变更控制是对配置项变更进行申请、分析、审批、实施、验证和关闭的全过程管理，目的是防止未经授权的修改破坏项目成果的一致性。

关键要点：
- 标准流程为提出变更申请、记录变更、分析影响、审批变更、安排实施、验证结果、更新配置状态并关闭变更。
- 影响分析应覆盖范围、进度、成本、质量、风险、合同以及相关配置项，不能只分析技术可行性。
- 变更批准后，应同步更新配置项版本、基线、项目计划、测试材料和相关文档。
- 紧急变更可以采用预先批准的快速通道，但不能免除登记、测试、授权和事后复核。
- 未经批准直接修改受控配置项，属于典型的配置管理失控问题。

### 5. 配置状态报告与配置审计
定义：配置状态报告是对配置项当前版本、变更过程和基线状态进行记录与报告；配置审计是检查配置项是否符合规定要求，以及配置记录与实际产品是否一致的活动。

关键要点：
- 配置状态报告应回答配置项当前是什么版本、处于什么状态、发生过哪些变更、由谁批准以及何时发布。
- 功能配置审计重点检查配置项是否实现经批准的功能和性能要求。
- 物理配置审计重点检查实际交付物与技术文件、版本标识、介质内容是否一致。
- 发布前应确认变更已关闭、测试已通过、文档已同步、版本可追溯、安装包完整且具备回退方案。
- 配置审计发现问题后，应形成记录并跟踪整改，不能只口头提醒。

## 案例分析题

**题目**：某市建设政务数据共享交换平台。项目组将需求文件、源程序、数据库脚本和部署说明分别存放在开发人员个人电脑及共享文件夹中，没有统一编号，也没有建立配置基线。开发人员发现接口超时后，未经审批便直接修改程序并部署到测试环境，但未同步更新接口设计文件和测试用例。系统上线前，项目经理临时从多个文件夹中收集程序打包，结果将旧版数据库脚本装入发布包，造成上线失败。事后检查发现，项目组无法说明各文件的当前版本、修改人和审批记录。

请回答：
1. 指出该项目在配置管理方面存在的主要问题。
2. 说明项目组应如何建立并管理配置基线。
3. 对接口超时问题引发的配置变更，应执行哪些控制活动？
4. 系统正式发布前应开展哪些配置审计工作？

**参考答案**：

1. 该项目存在的主要问题：
- 未制订和执行配置管理计划，配置管理职责不明确。
- 配置项分散存放，未建立统一配置库，存在丢失、覆盖和泄露风险。
- 需求文件、源程序、数据库脚本等未统一编号，配置项缺少唯一标识。
- 未记录配置项版本、状态、责任人和变更历史，无法实现追溯。
- 未建立需求基线、设计基线、测试基线和产品基线。
- 开发人员未经审批直接修改受控成果，配置变更控制失效。
- 程序变更后未同步修改接口文件和测试用例，相关配置项不一致。
- 发布包由项目经理临时拼装，缺少受控的构建和发布流程。
- 发布前未进行配置审计，导致旧版数据库脚本进入正式发布包。
- 缺少版本备份和回退方案，上线失败后的恢复能力不足。

2. 配置基线的建立与管理：
- 首先识别应纳入管理的配置项，统一规定名称、编号、版本和存放位置。
- 将经过评审并批准的需求、设计、程序、测试材料和发布材料纳入相应配置库。
- 在阶段成果通过正式评审后建立需求基线、设计基线、测试基线或产品基线。
- 记录基线包含的配置项、版本、批准人、建立日期和适用范围。
- 对基线进行访问权限控制，未经批准不得修改或替换。
- 基线变更必须履行申请、评估、审批、实施、验证和归档程序。
- 变更完成后更新基线及配置状态记录，并保留旧版本，以支持比较和回退。
- 定期开展配置审计，确认基线记录与实际成果保持一致。

3. 接口超时问题对应的配置变更控制活动：
- 由相关人员提交正式变更申请，说明问题、原因、修改内容和紧急程度。
- 配置管理员登记变更申请并识别受影响的程序、接口文件、测试用例、部署说明等配置项。
- 项目组分析变更对范围、进度、成本、质量、风险和其他模块的影响。
- 将变更申请及影响分析结果提交有权限的人员或变更控制机构审批。
- 批准后安排责任人实施修改，并从受控版本建立新的配置项版本。
- 对修改结果开展代码检查、接口测试、回归测试和必要的性能测试。
- 验证通过后同步更新接口设计文件、测试用例、部署说明和相关基线。
- 更新配置状态记录，形成完整的申请、审批、实施和验证证据，并正式关闭变更。
- 如果属于紧急变更，可走快速审批通道，但仍需登记、授权、测试和事后复核。

4. 正式发布前的配置审计工作：
- 开展功能配置审计，检查系统是否实现已经批准的需求、功能和性能指标。
- 开展物理配置审计，核对发布程序、数据库脚本、配置文件、安装说明和用户手册的版本是否一致。
- 检查所有纳入本次发布的变更是否已经批准、实施、验证并关闭。
- 核对发布包清单、配置项编号、版本号、生成时间和完整性校验信息。
- 确认测试报告、验收材料、部署方案和回退方案齐全且与本次版本对应。
- 验证发布包来源于产品库，而不是开发人员个人电脑或临时共享文件夹。
- 对审计发现的问题形成记录，完成整改和复核后方可批准发布。

**踩分要点**：
- 配置管理问题要围绕“无计划、无标识、无基线、无审批、无记录、无审计”展开。
- 基线必须先经过正式评审和批准，建立后不能由个人直接修改。
- 变更控制必须答出“申请、评估、审批、实施、验证、更新、关闭”的完整闭环。
- 程序修改后要同步更新接口文件、测试用例和部署说明，体现配置项之间的一致性。
- 配置审计要区分功能配置审计与物理配置审计。
- 紧急变更只是缩短审批路径，不等于可以绕过配置管理。

## 记忆口诀

配置管理六活动：
“计标控报审发”——制订计划、配置标识、配置控制、状态报告、配置审计、发布管理。

配置项七要素：
“名编版责位态史”——名称、编号、版本、责任人、位置、状态、历史。

三类配置库：
“开发随时改，受控审批改，产品发布用”——开发库服务开发，受控库保存已批准成果，产品库保存正式发布成果。

基线建立口诀：
“成果先评审，批准成基线；修改必申请，旧版要保全”。

变更控制七步：
“申记评批实验关”——申请、记录、评估、审批、实施、验证、关闭。

配置审计口诀：
“功能查实现，物理查一致”——功能配置审计检查是否满足批准的功能和性能要求，物理配置审计检查交付物、文件和版本是否一致。

发布前五查：
“变更已关闭、测试已通过、文档已同步、版本可追溯、回退有方案”。

紧急变更原则：
“流程可加速，控制不能少；事前有授权，事后要复核”。
