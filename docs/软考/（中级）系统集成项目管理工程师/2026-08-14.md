# （中级）系统集成项目管理工程师 · 2026-08-14

## 今日核心概念

### 1. 项目资源管理与团队建设

**定义**：资源管理是有效分配与利用人力、物质、设备等资源，确保项目目标实现的过程。系统集成项目以"人"为核心，团队管理是核心难点。

**关键要点**：

1）**资源管理六过程**

| 过程 | 输出 | 工具 |
|------|------|------|
| 规划资源管理 | 资源管理计划、团队章程 | 专家判断、数据分析 |
| 估算活动资源 | 活动资源需求、资源日历 | 专家判断、自下而上 |
| 获取资源 | 实物资源分配单、项目团队分派 | 多标准决策分析、谈判 |
| 建设团队 | 团队绩效评价、变更请求 | 培训、团建、激励 |
| 管理团队 | 变更请求 | 冲突管理、绩效评估 |
| 控制资源 | 工作绩效信息、变更请求 | 数据分析、问题解决 |

2）**冲突管理五种方法（高频必考）**

| 方法 | 含义 | 适用 |
|------|------|------|
| 撤退/回避 | 退出冲突、推迟解决 | 情绪激烈、暂不适合 |
| 缓解/包容 | 强调一致、淡化分歧 | 维护关系、长期合作 |
| 妥协/调解 | 双方各让一步 | 时间紧迫、双方实力对等 |
| 强迫/命令 | 以权力强制解决 | 紧急情况、纪律要求 |
| 合作/解决问题 | 直面冲突、共同解决 | **最佳方案**，利益冲突根本解决 |

考试口诀：**"回避包容妥协强迫合作"**，合作（直面冲突）效果最好，强迫只在紧急时用。

3）**马斯洛需求层次 vs 赫茨伯格双因素**

| 理论 | 层次 | 应用 |
|------|------|------|
| 马斯洛 | 生理→安全→社交→尊重→自我实现 | 理解员工需求层级 |
| 双因素 | 保健因素（防不满）+激励因素（促满意）| 工资是保健、成就感是激励 |

考试陷阱：**加薪只消除不满，不带来满意；成就感才是激励**。

4）**领导者vs管理者（高频）**

| 维度 | 领导者 | 管理者 |
|------|--------|--------|
| 关注 | 人、愿景、变革 | 事、流程、控制 |
| 风格 | 变革型、服务型 | 事务型、指挥型 |
| 产出 | 方向、激励、共识 | 秩序、稳定、可预测 |

5）**团队建设五个阶段（塔克曼阶梯）**

> **形成→震荡→规范→成熟→解散**

- 形成期：相互认识、试探；
- 震荡期：冲突显现（最困难）；
- 规范期：规则建立、协作顺畅；
- 成熟期：高效协作、默契；
- 解散期：项目结束、人员释放。

考试口诀：**"形震规成解"**，震荡期是项目经理干预关键期。

6）**权力类型五种（必背）**

| 类型 | 来源 | 例 |
|------|------|-----|
| 法定/职位 | 组织任命 | 项目经理职权 |
| 奖励 | 奖励能力 | 加薪、晋升、表扬 |
| 惩罚/强制 | 惩罚能力 | 批评、解雇 |
| 专家 | 专业能力 | 技术专家 |
| 参照/感召 | 个人魅力 | 团队信任 |

考试陷阱：**专家权力和参照权力是"非正式权力"**，最持久。

### 2. 项目沟通管理与干系人参与

**定义**：沟通管理是确保信息及时、适当生成、收集、分发、存储、检索、管理、控制、监控和处置的过程。系统集成项目涉及多干系人、多系统对接，沟通是核心难点。

**关键要点**：

1）**沟通管理三过程**

| 过程 | 输出 | 工具 |
|------|------|------|
| 规划沟通管理 | 沟通管理计划 | 沟通需求分析、沟通模型 |
| 管理沟通 | 项目沟通记录、变更请求 | 沟通模型、沟通方法 |
| 监督沟通 | 工作绩效信息、变更请求 | 监督方法 |

2）**沟通模型与公式**

- **编码→信息→解码→反馈**是基本模型。
- 信息传递 = 编码 + 信息本身 + 解码，**任何环节都可能出现噪音**。
- 沟通渠道数公式：**N(N-1)/2**
  - 例：4个干系人有 4×3/2 = 6条潜在沟通渠道。
  - 例：8个干系人有 8×7/2 = 28条潜在渠道。

考试陷阱：**增加干系人→沟通渠道数爆炸式增长**。

3）**沟通方式五维度**

| 维度 | 选项 |
|------|------|
| 正式程度 | 正式/非正式 |
| 时机 | 计划/临时 |
| 内容 | 内部/外部 |
| 形式 | 书面/口头 |
| 媒介 | 推式（邮件）、拉式（看板）、交互式（会议）|

4）**干系人参与级别（必背）**

| 级别 | 含义 | 项目经理策略 |
|------|------|--------------|
| 不了解 | 不知道项目 | 告知 |
| 抵制 | 反对项目 | 重点沟通 |
| 中立 | 不支持不反对 | 引导参与 |
| 支持 | 支持项目 | 利用 |
| 领导 | 全力支持 | 委以重任 |

5）**干系人分析矩阵**

- **权力/利益矩阵**：分4象限，重点管理"高权力高利益"干系人。
- **权力/影响矩阵**：分4象限。
- **影响/作用矩阵**：分4象限。
- **凸显模型**：基于学习、立即行动、权力、合法性、紧急性五属性。

6）**干系人参与计划**

- 当前参与级别 vs 期望参与级别。
- 差距大的干系人 → 重点管理。
- 每个干系人需明确**沟通频率、方式、内容**。

7）**会议管理（高频）**

| 维度 | 措施 |
|------|------|
| 会前 | 明确议程、提前通知、准备资料 |
| 会中 | 控制时间、引导讨论、记录决议 |
| 会后 | 整理纪要、分发跟进、跟踪落实 |

考试陷阱：**会议必须"有议程、有纪要、有跟进"**，三要素缺一不可。

### 3. 项目采购管理与合同类型

**定义**：采购管理是从外部获取项目所需产品、服务或成果的过程。系统集成项目常涉及外包采购、外协开发、第三方设备采购，合同管理是核心。

**关键要点**：

1）**采购管理三过程**

| 过程 | 输出 | 工具 |
|------|------|------|
| 规划采购管理 | 采购管理计划、采购文件 | 市场分析、自制外购分析 |
| 实施采购 | 选定卖方、协议、变更请求 | 投标人会议、建议书评估 |
| 控制采购 | 工作绩效信息、变更请求 | 绩效审查、索赔管理 |

2）**采购合同类型对比（高频必考）**

| 合同类型 | 风险承担 | 适用场景 |
|---------|---------|---------|
| 固定总价合同（FFP）| 卖方承担成本风险 | 范围清晰、工期短 |
| 总价加激励费用（FPIF）| 分担 | 有绩效激励 |
| 总价加经济价格调整（FP-EPA）| 分担 | 长周期、通货膨胀 |
| 成本加固定费用（CPFF）| 买方承担成本 | 工作范围模糊 |
| 成本加激励费用（CPIF）| 分担 | 有绩效激励 |
| 成本加奖励费用（CPAF）| 分担 | 有奖励机制 |

考试口诀：**"固定总价卖方控风险，成本加成买方控风险"**。

3）**采购工作说明书SOW**

- 详细描述采购项的规格、数量、质量、交付物、验收标准。
- 是招标文件、合同附件的核心。
- 与WBS工作包对应。

4）**自制外购分析**

| 决策 | 适用 |
|------|------|
| 自制 | 核心能力、保密要求、培养团队 |
| 外购 | 非核心、成本更低、紧急、缺乏能力 |
| 租赁 | 临时、短周期使用 |

5）**投标人会议**

- 招标方与潜在卖方的**正式会议**。
- 目的是让所有投标人**平等理解招标要求**。
- 投标前的答疑、澄清环节。
- 会上回答必须**形成书面补遗**并分发所有投标人。

6）**合同变更控制**

- 任何合同变更必须**走变更控制流程**。
- 变更需双方书面同意（合同条款规定）。
- 单方面变更合同是违约。

7）**采购关闭与合同收尾**

| 内容 | 措施 |
|------|------|
| 合同验收 | 按SOW验收所有交付物 |
| 文件归档 | 合同、变更、发票、验收记录归档 |
| 经验教训 | 总结采购过程教训 |
| 合同审计 | 审计合规性、识别可改进项 |

### 4. 项目变更管理与配置管理

**定义**：变更管理是处理项目基准变更请求的全部过程；配置管理是识别、记录、控制、审核、验证项目可交付成果与基准的学科。系统集成项目范围广、变更多，变更与配置管理是质量与范围控制的关键。

**关键要点**：

1）**整体变更控制流程（六步走）**

> **申请→评估→决策→实施→验证→归档**

| 步骤 | 内容 | 责任方 |
|------|------|--------|
| 申请 | 提交变更请求（含影响分析）| 变更申请人 |
| 评估 | 评估影响（范围/进度/成本/质量/风险）| 项目经理+专家 |
| 决策 | CCB审查批准/拒绝 | CCB |
| 实施 | 更新基准、执行变更 | 执行团队 |
| 验证 | 验证变更正确实施 | QA/QC |
| 归档 | 记录到变更日志、配置库 | 配置管理员 |

考试口诀：**"申评决验归"**，决策前必须做影响分析。

2）**变更控制委员会CCB**

- **组成**：项目经理、客户代表、技术负责人、商务代表等。
- **职责**：审查变更请求、批准/拒绝变更。
- **决议类型**：批准、拒绝、推迟、补充信息后重审。
- **特例**：紧急变更可走快速CCB流程。

考试陷阱：**项目经理无权擅自批准变更，必须CCB决定**。

3）**配置管理四大活动**

| 活动 | 含义 |
|------|------|
| 配置识别 | 确定哪些项纳入配置管理 |
| 配置控制 | 变更申请、批准、实施的控制 |
| 配置状态记录 | 记录每个配置项的状态 |
| 配置审计 | 审计配置项的完整性和正确性 |

4）**配置项识别**

| 类型 | 例 |
|------|-----|
| 产品配置项 | 设计文档、源代码、可执行文件 |
| 过程配置项 | 计划、合同、报告 |
| 基准 | 范围基准、进度基准、成本基准 |

5）**配置库三层结构**

| 层 | 内容 | 权限 |
|----|------|------|
| 开发库 | 程序员本地代码 | 程序员 |
| 受控库 | 已纳入基线的可交付物 | 配置管理员 |
| 产品库 | 已发布的产品 | 用户 |

考试口诀：**"开发受控产品"**，配置项从开发→受控→产品的过程。

6）**基线管理**

- 基线 = 通过正式评审、批准、可作为后续变更参考的快照。
- 变更前：基于当前基线工作。
- 变更后：产生新基线，旧基线归档保留。
- 三类基准：**范围基准、进度基准、成本基准**。

7）**变更与配置管理的关系**

> **变更是"为什么要改"，配置是"改什么、怎么改、记录什么"**。

变更管理负责流程，配置管理负责内容。
两者协同：变更前 → 识别配置项；变更后 → 更新配置库。

### 5. 项目绩效度量与报告

**定义**：绩效度量是评估项目绩效与基准的差异、识别改进机会的活动。绩效报告是向干系人传达项目状态、进展、问题、趋势的过程。

**关键要点**：

1）**绩效度量维度**

| 维度 | 指标 |
|------|------|
| 进度绩效 | SPI、SV、关键路径偏差 |
| 成本绩效 | CPI、CV、TCPI、EAC |
| 范围绩效 | 已完成工作包数、WBS完成率 |
| 质量绩效 | 缺陷密度、缺陷率、测试通过率 |
| 风险绩效 | 已触发风险数、新增风险数、储备消耗 |

2）**挣值指标综合判断（再强调）**

| CPI | SPI | 状态 |
|-----|-----|------|
| >1 | >1 | 双好 |
| >1 | <1 | 节支但滞后 |
| <1 | >1 | 提前但超支 |
| <1 | <1 | 双重失控 |

3）**绩效报告类型**

| 类型 | 频率 | 受众 |
|------|------|------|
| 状态报告 | 周/月 | 项目团队 |
| 进展报告 | 月/季 | 项目管理层 |
| 预测报告 | 阶段 | 高级管理层 |
| 完工报告 | 完工 | 所有干系人 |

4）**预测报告的关键内容**

- 当前CPI/SPI。
- EAC完工估算。
- VAC完工偏差。
- TCPI完工绩效指数。
- 风险预警与储备消耗。
- 下阶段计划与重大变更。

5）**趋势分析**

- 连续3-5个周期观察CPI/SPI变化趋势。
- 上升趋势 → 绩效改善。
- 下降趋势 → 需立即纠偏。
- 平稳趋势 → 维持现状。

6）**问题日志与升级机制**

| 级别 | 处理人 |
|------|--------|
| L1 低级 | 团队内部解决 |
| L2 中级 | 项目经理介入 |
| L3 高级 | 上级管理层、CCB |
| L4 紧急 | 高层决策、应急响应 |

7）**项目状态会议**

| 时机 | 内容 |
|------|------|
| 周例会 | 进度、本周完成、下周计划、问题 |
| 月度评审 | EVM指标、风险、变更、干系人 |
| 阶段评审 | 阶段交付物验收、下一阶段启动 |
| 紧急会议 | 重大问题、风险触发、变更决策 |

## 案例分析题

**题目**：

某市"政务一网通办"系统集成项目，总投资 1800 万元，工期 12 个月，由市政务办牵头，整合 12 个委办局的 38 个政务系统（含公安、人社、医保、民政、住建等），建设市级一体化政务服务平台。项目采用"总集成商+行业分包"模式，A 公司中标作为总集成商，负责统一门户、统一身份认证、统一电子证照、统一支付四大基础平台；B、C、D 等 5 家公司分别承担各委办局系统改造。

项目实施过程中发生以下事件：

（1）**资源与团队阶段（第1-2月）**：项目启动后，A 公司任命项目经理小张，组建 35 人项目团队（含 8 名高级工程师、12 名中级工程师、10 名初级工程师、5 名业务分析师）。因高级工程师稀缺，多个项目争抢，公司副总裁口头指定"小张为项目经理"但未发正式任命书。小张采用"职能型"组织结构管理团队，每周例会，但第 2 个月就出现团队冲突：高级工程师老李认为方案应该由他决定，小张无权干预；某分包商代表指责小张不懂业务、强加进度。小张决定"立即将老李开除"以维护权威。第 2 个月底，公司奖励小张 3 万元以表彰"领导力"。

（2）**沟通与干系人阶段（第3-4月）**：项目共涉及 12 个委办局、5 家分包商、政务办领导、最终用户（市民+企业）、运维团队等多类干系人，干系人总数超过 200 人。小张制定了沟通管理计划，规定"所有变更通过邮件通知"。第 3 个月公安局要求"优先接入身份认证接口"，人社局要求"先做医保接口"，住建局要求"优先实现电子证照"，三家委办局同时施压。小张召开紧急会议，要求三方"按工作量轮流开发"，三方代表当面争吵，会议无果而终。第 4 个月，小张发现"沟通渠道数已达 19900 条"，但部分关键决策"邮件发了没人看"。

（3）**采购与合同阶段（第5-6月）**：项目签订 5 份分包合同，其中 3 份为"固定总价合同（FFP）"，2 份为"成本加固定费用（CPFF）"。第 5 个月，B 公司（承担公安系统改造）提出"接口复杂度超预期，需追加 200 万元"。小张口头同意"先做后补签变更"。第 6 个月，C 公司（承担医保系统改造）建议"采用总价加激励费用（FPIF）合同，更能激励双方"，C 公司项目经理与 A 公司采购经理私下达成一致，开始按 FPIF 执行但未签补充协议。

（4）**变更与配置阶段（第7-8月）**：第 7 个月，政务办领导口头要求"增加'一窗受理'功能模块"，领导说"特事特办、加快推进"。小张立即启动开发，未走变更流程。第 8 个月，"一窗受理"模块与现有"统一支付"模块出现严重接口冲突，导致全市 5 个委办局的支付功能异常；同时因某次代码部署未走配置管理流程，导致 2 个委办局的接口代码被覆盖丢失，需 1 周时间恢复。

（5）**绩效与收尾阶段（第9-10月）**：第 9 个月关键绩效数据如下：
- BAC（完工预算）= 1800 万元
- PV（计划值）= 1100 万元
- AC（实际成本）= 1280 万元
- EV（挣值）= 950 万元

第 10 个月，项目部分模块验收，政务办对"统一门户"和"统一身份认证"评价"基本满意"，但要求"统一电子证照"必须返工。分包商 B 公司因"项目延期 2 个月、累计亏损 100 万元"，向 A 公司发出索赔通知，要求赔偿 150 万元；A 公司副总裁电话回复"会妥善处理"但未签任何书面文件。

**参考答案**：

**问题 1：资源与团队管理失误**

组织结构失误：
- **项目组织结构选择不当**：35 人跨部门跨公司的复杂集成项目，应采用**矩阵型**或**项目型**组织，而非职能型。
- **项目经理任命不规范**：公司副总裁口头任命但未发正式任命书，导致**法定权力不足**，"老李不服从"是必然结果。
- **跨公司协调缺乏机制**：5 家分包商属于不同公司，矩阵型才能统筹资源，职能型无法有效协调。

权力类型分析：
- 小张的权力基础主要是**法定权力（职位）**和**奖励权力**。
- 但缺乏**专家权力**（不懂业务被指责）和**参照权力**（开除老李、独占奖励削弱信任）。
- 老李的优势是**专家权力**（技术强），导致小张权威受挑战。
- 改进：小张应建立**专家权力**（深入业务学习）和**参照权力**（公平公正）。

冲突管理失误：
- **小张采用"强迫/命令"方式开除老李**：属于最差冲突管理策略，破坏团队关系。
- 正确做法应是**合作/解决问题**（直面冲突、共寻方案）：
  - 召集老李 + 业务专家 + 小张共同讨论方案决策机制。
  - 明确"技术细节由老李决定，整体方向由小张决策"的权限划分。
- 考试口诀：**合作（直面冲突）效果最好，强迫只在紧急时用**。

激励失误：
- **加薪3万元给项目经理小张**违反双因素理论：
  - 加薪属**保健因素**，只能消除不满，不带来满意。
  - 团队整体士气提升需要**激励因素**（成就感、认可、晋升、培训）。
- 正确激励应是**面向团队整体**：
  - 团队表彰、优秀个人奖、培训机会、晋升通道。
  - 月度评优、项目里程碑庆祝。

团队建设阶段（塔克曼）：
- 项目第 2 个月处于**震荡期**（冲突爆发期），正是项目经理关键干预期。
- 小张不仅未化解冲突，反而用"开除"加剧震荡，**团队可能长期停留在震荡期**，难以进入规范期。
- 改进：建立团队章程、明确角色与职责、定期团建活动。

**问题 2：沟通渠道计算与沟通管理失误**

沟通渠道计算：
- 公式 **N(N-1)/2 = 200×199/2 = 19900条**，与小张计算一致。
- 考试陷阱：**200个干系人有19900条潜在渠道**，这是问题根源。

沟通管理问题：
- **"所有变更通过邮件通知"过于单一**：
  - 重大变更应采用**交互式沟通**（会议、面对面）。
  - 紧急变更应采用**即时通讯+电话**。
  - 例行通知可采用邮件。
- **"邮件发了没人看"是典型推式沟通失效**：
  - 应改用**交互式沟通**（关键决策必须会议确认）。
  - 应配套**沟通确认机制**（邮件回执、会议纪要签字）。

干系人参与失误：
- **公安局、人社局、住建局同时施压**：三个都是高权力高利益干系人，应**分而治之**：
  - 分别召开一对一沟通，了解各自优先级理由。
  - 用**权力/利益矩阵**识别"高权力高利益"干系人重点管理。
  - 通过**干系人参与级别分析**，把"中立"提升到"支持"，把"抵制"转化为"中立"。
- **"按工作量轮流开发"是错误决策**：
  - 应基于**依赖关系和优先级**排序，而非轮流。
  - 关键路径上的系统优先。
  - 涉及法律法规强制要求的优先（如公安部身份认证有强制性）。

改进方案：

| 维度 | 改进措施 |
|------|---------|
| **干系人分类** | 用权力/利益矩阵分4类，重点管"高权力高利益"12个委办局 |
| **沟通分层** | 高层决策用面对面会议；中层协调用周例会；基层通知用邮件+企业微信 |
| **沟通模板** | 关键决策采用"决策模板"（决策背景、方案对比、建议、请示）|
| **沟通渠道** | 关键决策必须**会议+纪要+签字确认**，不能只发邮件 |
| **定期校准** | 月度干系人满意度调研，及时调整沟通策略 |
| **冲突调解** | 跨委办局冲突由政务办领导牵头协调，避免总集成商单方面决策 |
| **升级机制** | 跨公司、跨部门冲突走L3升级流程，由政务办高层决策 |

**问题 3：采购与合同管理失误**

合同类型选择分析：

| 合同 | 已签项目 | 适用性 |
|------|---------|--------|
| FFP（固定总价）| 公安、医保、住建 | 范围清晰时合适，但范围模糊时卖方风险大 |
| CPFF（成本加固定费用）| 人社、民政 | 工作范围模糊时合适，但买方成本风险大 |

本项目失误：
- 公安系统改造范围**不清晰**（接口复杂），签 FFP 把风险全推给卖方，导致 B 公司追加费用。
- CPFF 应在范围模糊时使用，但 A 公司选择错误。

合同类型适用场景：

| 范围清晰度 | 推荐合同 |
|----------|---------|
| 范围非常清晰 | FFP 固定总价（卖方担风险）|
| 范围基本清晰 | FPIF 总价加激励 |
| 范围部分清晰 | FP-EPA 经济价格调整 |
| 范围模糊 | CPFF 成本加固定费用（买方担风险）|
| 紧急/探索 | CPIF 成本加激励 |

追加费用失误：
- **B 公司追加 200 万元未签补充协议**：
  - 违反合同变更控制流程。
  - 任何合同变更必须**双方书面同意**。
  - 小张"口头同意"无效，属违约风险。
- **C 公司私下变更合同类型**：
  - 重大合同变更（FFP→FPIF）必须走**正式变更流程**，签补充协议。
  - 私下变更违反合同法，可能导致合同无效。
  - 还涉及**道德风险**（项目经理与采购经理利益关联）。

索赔处理失误：
- **B 公司索赔 150 万元**：
  - A 公司副总裁电话回复"会妥善处理"，**无书面承诺、无索赔评估**。
  - 应启动**索赔管理流程**：
    1. 收到索赔通知 → 7天内书面回应。
    2. 成立索赔评估小组（项目经理+法务+合同专家）。
    3. 审查合同条款、事实证据、损失计算。
    4. 与 B 公司协商赔偿方案。
    5. 双方签订和解协议。
  - 电话回复无法律效力，错过书面回应时限可能败诉。

改进措施：
1. **合同类型选择**：B 公司改造应签 FPIF 或 CPIF，激励双方控制成本。
2. **变更书面化**：所有合同变更必须签**补充协议**，双方授权代表签字盖章。
3. **索赔流程标准化**：制定索赔管理 SOP，明确时限、责任、流程。
4. **采购人员培训**：采购经理与分包商项目经理的私下协议属严重违规，应建立利益冲突申报制度。
5. **采购审计**：每季度审计分包合同执行情况。

**问题 4：变更控制与配置管理失误**

变更控制失误：
- **"领导口头要求特事特办"违反变更流程**：
  - 任何变更必须**走整体变更控制流程**（申请→评估→决策→实施→验证→归档）。
  - 领导口头授权**不代替 CCB**，不能跳过影响分析。
  - "一窗受理"涉及 12 个委办局、5 家分包商，影响范围广，未评估就启动导致后续接口冲突。

正确流程：
1. **变更申请**：政务办提交书面变更请求。
2. **影响分析**：项目经理组织专家评估范围、进度、成本、质量、风险影响。
3. **CCB 决策**：CCB 审查变更请求，批准/拒绝/推迟。
4. **实施方案**：制定详细实施方案，含回退方案。
5. **执行变更**：按方案实施变更。
6. **变更验证**：QA/QC 验证变更正确实施。
7. **变更归档**：记录到变更日志、配置库、相关基准更新。

配置管理失误：
- **代码部署未走配置管理流程**：
  - 部署前必须从**产品库**提取代码，经过**受控库**审批。
  - 不能直接从开发库部署，否则版本混乱、覆盖丢失。
  - 丢失 2 个委办局接口代码是因为**配置库三层分离**未严格执行。

正确配置管理流程：

| 阶段 | 工具 | 输出 |
|------|------|------|
| 配置识别 | 配置项识别清单 | 配置项清单 |
| 配置控制 | 变更请求→CCB审批 | 变更请求记录 |
| 配置状态记录 | 配置状态报告 | 配置状态数据库 |
| 配置审计 | 配置审计报告 | 完整性确认 |

**"一窗受理"导致5个委办局支付异常**的原因：
- "一窗受理"与"统一支付"均涉及支付流程，模块边界未充分定义。
- 接口规范未在变更前评审。
- 缺乏**接口兼容性测试**。

改进措施：

| 维度 | 措施 |
|------|------|
| **流程** | 1. 任何变更（含领导口头要求）必须走整体变更控制流程。2. 紧急变更走快速CCB（24小时内），普通变更走标准流程（5-7天）。3. 变更实施必须有回退方案。 |
| **工具** | 1. 引入版本控制工具（Git+SVN），强制走合并请求流程。2. 自动化部署（CI/CD），自动从产品库提取代码。3. 接口兼容性自动化测试。 |
| **制度** | 1. 配置管理三项制度（识别、控制、审计）。2. 配置库三层权限分离（开发、受控、产品）。3. 变更影响分析模板（含接口影响）。 |
| **人员** | 1. 配置管理专员（专职）。2. 变更评审委员会（含架构师、测试负责人、分包商代表）。3. 变更管理培训。 |

**问题 5：挣值计算与绩效分析**

挣值计算（第 9 个月）：
- CV = EV - AC = 950 - 1280 = **-330万元**（成本超支 330 万）
- SV = EV - PV = 950 - 1100 = **-150万元**（进度滞后 150 万）
- CPI = EV / AC = 950 / 1280 ≈ **0.742**（<1，超支严重）
- SPI = EV / PV = 950 / 1100 ≈ **0.864**（<1，进度滞后）

完工预测：
- EAC = BAC / CPI = 1800 / 0.742 ≈ **2426万元**（典型公式）
- VAC = BAC - EAC = 1800 - 2426 ≈ **-626万元**（完工超支 626 万）
- TCPI = (BAC - EV) / (BAC - AC) = (1800-950) / (1800-1280) = 850 / 520 ≈ **1.635**
  - TCPI > 1.5：未来必须极高效率才能完成原预算，**几乎不可能**。
  - **建议：申请追加预算或调整范围基准**。

绩效状态判断：

| CPI | SPI | 状态 |
|-----|-----|------|
| 0.742 (<1) | 0.864 (<1) | **双重失控** |

改进措施：
1. **立即启动重大纠偏**：申请追加预算 700-800 万元。
2. **范围调整**：与政务办协商砍掉部分非核心功能（如某些委办局的非关键接口）。
3. **进度压缩**：对关键路径活动谨慎采用赶工，避免再引发次生风险。
4. **加强变更控制**：禁止"特事特办"、所有变更走 CCB。
5. **储备审视**：检查应急储备、管理储备余额，必要时动用管理储备（须 CCB 批准）。
6. **责任追究**：对违规口头变更、未走流程的当事人追责，避免后续违规。

**"统一电子证照"必须返工的影响**：
- 已投入成本沉没，但返工将增加额外 50-100 万元。
- 进度再延后 1 个月，影响整体验收。
- 需与住建局（电子证照责任方）共同制定返工方案。

- 整体变更控制六步：申请→评估→决策→实施→验证→归档。

- 配置库三层：开发、受控、产品，权限分离。
- 重大变更必须有影响分析和回退方案。

**问题 5（挣值绩效）——必写"四指标 + EAC/VAC/TCPI + 状态判断"**
- CV/SV/CPI/SPI四指标必算，CPI<0.85属严重失控。
- TCPI>1.5几乎不可能完成原预算，需追加预算或调范围。
- CPI<1且SPI<1属双重失控。

1. 每问先写"问题/失误"再写"理由/措施"，一问一段，编号分条。
2. 凡涉及数字必须写出（沟通渠道19900、CPI=0.742、TCPI=1.635、亏损100万等）。
3. 措施类回答统一"**流程 + 工具 + 制度 + 人员**"四维度。
4. 案例细节（副总裁口头任命、开除老李、特事特办、5个委办局支付异常、丢失2个委办局代码、统一电子证照返工、索赔150万）为采分点。
