# （中级）系统集成项目管理工程师 · 2026-08-10

## 今日核心概念

### 1. 项目立项管理与可行性研究

**定义**：项目立项管理是从识别业务需求、论证项目价值、做出投资决策到正式授权启动的全过程，是项目生命周期的"入口关卡"。可行性研究则是用技术、经济、管理、法律、社会等维度对方案进行系统论证，避免"拍脑袋上项目"。

**关键要点**：

1）**项目立项的典型流程**
业务需求提出 → 初步可行性研究（预可研）→ 详细可行性研究（可研）→ 项目论证与评估 → 项目决策与审批 → 签发项目章程/下达项目任务书 → 项目启动。

2）**可行性研究五大维度**（必背）

| 维度 | 核心问题 |
|------|----------|
| 技术可行性 | 技术路线、关键技术成熟度、技术风险、人员能力是否支撑 |
| 经济可行性 | 投资估算、收益测算、投资回收期、净现值NPV、内部收益率IRR、ROI |
| 运行环境可行性 | 场地、电力、网络、配套设施是否符合系统运行要求 |
| 社会可行性 | 是否符合政策法规、行业规划、社会效益、用户接受度 |
| 管理可行性 | 组织架构、领导支持、变革管理、运维能力是否到位 |

3）**项目论证 vs 项目评估（易混淆）**
- **项目论证**：项目**承建单位（乙方）**主导，从技术方案角度论证"能不能做、怎么做"，产出可研报告。
- **项目评估**：项目**投资方/审批方（甲方或上级主管）**主导，从投资价值角度评估"值不值得做、有没有必要"，产出评估意见。
- 考试陷阱：让承建方做项目评估、让甲方写技术论证——都是角色错位。

4）**立项申请与立项审批**
- 立项申请书（乙方）/项目建议书（甲方）的核心内容：项目必要性、需求初步分析、总体方案、投资估算与资金来源、进度计划、经济和社会效益、风险初步识别。
- 立项审批重点：**必要性、可行性、合理性、合规性、可控性**五性审查。

5）**招投标与立项的衔接**（案例常考）
立项批复是开展招标采购的**前置条件**；先立项、后采购、再签订合同，不得"先施工后立项"或"边设计边施工边立项"。

### 2. 项目采购管理与供应商选择

**定义**：采购管理是从外部获取项目所需产品、服务或成果的全过程，包含采购规划、供应商选择、合同签订、合同管理、合同收尾五个子过程。系统集成项目普遍存在"自主开发 + 外购 + 集成"混合模式，采购管理能力直接影响项目成败。

**关键要点**：

1）**采购管理五个过程**（与五大过程组对应）

| 过程 | 过程组 | 核心输出 |
|------|--------|----------|
| 规划采购管理 | 规划 | 采购管理计划、采购文件、供方选择标准 |
| 实施采购 | 执行 | 选定的卖方、协议（合同）、采购文件包 |
| 控制采购 | 监控 | 工作绩效信息、采购审计、采购关闭、采购变更 |
| 合同收尾 | 收尾 | 合同档案、最终产品/服务移交、经验教训 |

2）**采购方式选择矩阵**（必背）

| 方式 | 适用场景 | 关键特点 |
|------|----------|----------|
| 公开招标 | 政府采购限额以上、必须招标项目 | 公开公平、竞争充分、周期长 |
| 邀请招标 | 受限领域、特定供应商范围 | 不少于3家、邀请对象具备能力 |
| 竞争性谈判 | 招标失败、技术复杂需谈判 | 不少于3家、可对技术方案谈判 |
| 竞争性磋商 | 技术方案不明确、政府购买服务 | 综合评审、磋商可改实质性内容 |
| 单一来源 | 只能从唯一供应商、紧急添购≤10% | 需公示、专家论证、不得规避招标 |
| 询价采购 | 货物规格统一、货源充足、价格透明 | 不少于3家、比价择优 |
| 直接采购 | 紧急、小额、专属 | 仅限小额零星采购 |

3）**供方选择标准**（规划采购的输出）
- **必备项**（一票否决）：资质许可、合法合规、关键业绩门槛。
- **评分项**：技术方案、价格、交付能力、售后服务、信誉财务。
- 权重需在采购文件中事先约定，**事后加权无效**（案例陷阱）。

4）**采购文件与SOW**
- 采购文件包：招标文件 / RFP / RFQ + 评估标准 + 合同条款草案。
- 工作说明书SOW：详细描述拟采购的产品/服务的范围、性能、接口、验收要求，是合同的技术附件。

5）**采购合同的关键条款**（与合同管理衔接）
总价/单价/成本补偿三种计价方式 / 付款节奏 / SLA与违约罚则 / 知识产权与源代码 / 变更与索赔 / 验收标准 / 不可抗力 / 争议解决。

### 3. 组织级项目管理OPM与成熟度模型

**定义**：组织级项目管理（OPM）是组织通过战略对齐、项目组合、项目集、单项目三层治理，**系统化、可持续地交付价值**的框架。成熟度模型（OPM3、CMMI、PMMM等）用于评估并提升组织项目管理能力。

**关键要点**：

1）**OPM三大治理层次**（组织结构对项目治理）

| 层次 | 关注点 | 核心产出 |
|------|--------|----------|
| 项目组合 | **战略对齐**：做不做、做什么、优先级 | 组合管理计划、组合章程 |
| 项目集 | **收益交付**：跨项目协调、共用资源 | 项目集章程、项目集管理计划 |
| 项目 | **范围/进度/成本/质量交付** | 项目章程、项目管理计划、可交付成果 |

2）**项目组合、项目集、项目的关系**（选择题高频）
- **项目组合 = 战略层**，强调与业务战略对齐、组合价值最大化。
- **项目集 = 战术层**，强调协调管理以获取单一项目无法获得的**额外收益**。
- **项目 = 作战层**，强调范围、进度、成本、质量的平衡。
- **三者的共性**：都以"项目"为组成单元；**区别在于范围、周期、收益视角**不同。

3）**OPM3（组织项目管理成熟度模型）**
PMI发布的成熟度框架，包含**最佳实践（Best Practices）+ 能力（Capabilities）+ 成果（Outcomes）+ KPI** 四个组件，覆盖项目、项目集、组合三个领域；成熟度分级支持分阶段提升。

4）**CMMI五个等级**（与系统集成直接相关，必背）

| 等级 | 名称 | 关键特征 |
|------|------|----------|
| L1 | 初始级 | 过程随意、依赖个人英雄 |
| L2 | 已管理级 | 项目已策划、受控、跟踪 |
| L3 | 已定义级 | 组织级标准化过程、文档化 |
| L4 | 定量管理级 | 数据采集、定量分析、过程受控 |
| L5 | 优化级 | 持续优化、技术创新、缺陷预防 |

5）**项目办公室PMO的四种类型**
- **支持型**：提供模板、培训、工具，**不直接管控**项目。
- **控制型**：通过治理流程对项目施加**合规约束**。
- **指令型**：直接**管理**项目，项目经理向PMO汇报。
- PMO的影响力由弱到强、承担风险由小到大；考试陷阱是混用PMO职能与项目经理职责。

6）**价值交付系统**（PMBOK第七版导向）
不再以过程驱动，而以**原则 + 价值流**驱动：价值 → 价值流 → 组织治理 → 运营环境。强调"原则而非过程，结果而非产出"。

### 4. 信息系统架构与典型集成模式

**定义**：系统集成项目的本质是把不同厂商、不同技术栈、不同生命周期的子系统组合为一个有机整体。架构选型决定了系统的可扩展性、可维护性、性能与安全水平。

**关键要点**：

1）**典型集成架构模式**

| 模式 | 核心思想 | 典型场景 | 优劣 |
|------|----------|----------|------|
| 点对点集成 | 系统两两对接 | 系统少、调用简单 | 紧耦合、复杂度爆炸 |
| 共享数据库 | 共享一张中心库 | 主数据分发 | 易形成性能瓶颈、单点故障 |
| 消息中间件 | MQ解耦、异步 | 高并发、解耦 | 需保证消息可靠投递 |
| 企业服务总线ESB | 协议转换+路由+编排 | 多协议异构系统 | 重型、投资大 |
| API网关/微服务 | RESTful + 服务治理 | 互联网+政务云 | 灵活但需配套治理 |

2）**SOA vs 微服务（高频对比）**

| 维度 | SOA | 微服务 |
|------|-----|--------|
| 粒度 | 粗（业务服务） | 细（单一职责） |
| 通信 | ESB + SOAP | 轻量HTTP/RPC + 消息 |
| 治理 | 集中式（契约、注册） | 去中心化 |
| 部署 | 共享部署多 | 独立部署 |
| 适用 | 大型传统企业集成 | 互联网+云原生 |

3）**RESTful API设计原则**（系统集成常考）
- 资源命名用名词复数、HTTP方法语义化（GET查、POST增、PUT/PATCH改、DELETE删）。
- 状态码语义化：2xx成功、3xx重定向、4xx客户端错、5xx服务器错。
- 无状态、自描述消息、缓存友好、HATEOAS可选。

4）**中间件分类与作用**
- **消息中间件**（RocketMQ/Kafka/RabbitMQ）：异步解耦、削峰填谷、可靠投递。
- **应用服务器**（Tomcat/WebLogic）：Web容器、事务、连接池。
- **缓存**（Redis/Memcached）：热点加速、会话共享。
- **数据库中间件**（MyCat/Sharding-JDBC）：读写分离、分库分表。
- **负载均衡**（Nginx/LVS）：流量分发、高可用。

5）**集成项目关键技术指标**
可用性（多个9）、TPS/QPS、平均响应时间、并发用户数、数据一致性等级（强一致/最终一致）、可扩展性、可维护性指数。

### 5. 法律法规专项：民法典合同编与著作权法

**定义**：系统集成项目的合同行为受《民法典》合同编调整，交付物的知识产权归属受《著作权法》《专利法》《计算机软件保护条例》调整。考试近年侧重合同编实质性条款与软件著作权归属的判定。

**关键要点**：

1）**民法典合同编的八大合同类型（与系统集成最相关的三类）**
- **承揽合同**（开发/建设）：交付工作成果，**标的物所有权自交付时转移**；可约定知识产权归属。
- **建设工程合同**：勘察、设计、施工、监理；适用优先于承揽合同。
- **技术服务合同 / 技术开发合同**：技术成果归属**默认按约定 → 无约定按补充协议 → 无补充按合同有关条款 → 仍无约定则按公平原则**，且委托开发**默认归受托方**、合作开发**默认共同所有**。

2）**技术开发合同成果归属规则**（核心考点）

| 情形 | 成果归属 |
|------|----------|
| 委托开发有约定 | 按约定（**约定优先**，考试陷阱：不是法定归甲方） |
| 委托开发无约定 | 申请专利权归**受托方**，但**委托人可免费实施** |
| 合作开发有约定 | 按约定 |
| 合作开发无约定 | **共同所有**，行使需一致同意；份额不明等分 |
| 职务作品（履行本职工作任务） | 著作权归**单位**，个人仅享署名权 |
| 利用单位物质条件创作 | 单位有优先使用权 |

3）**计算机软件著作权归属**（软件属于"作品"）
- 软件著作权自软件开发完成之日起产生，登记并非生效要件（自愿登记）。
- 委托开发：合同**未明确约定**则归**受托方**，但委托方按约定享有使用权。
- 合作开发：未约定则**共同所有**。
- 职务作品：员工为完成本职工作开发的软件归**单位**，个人仅享署名权。
- 委托/合作完成的软件，著作权权属发生变化的，应**订立书面合同**。

4）**侵犯软件著作权的行为**（识别点）
未经许可复制、发行、修改、翻译、注释、网络传播、出租、通过信息网络向公众传播；故意避开或破坏技术保护措施；故意删除/改变权利管理信息；复制或传播修改版。

5）**违约责任与侵权责任的择一**
合同违约与侵权**可竞合**，权利人可择一主张；但**知识产权侵权不以过错为前提**（特殊侵权归责）。

## 案例分析题

**题目**：

某市政务服务管理局拟建设"一网通办"综合服务平台升级项目，项目总预算 1800 万元，全部使用财政资金，建设周期 12 个月。项目目标是把现有的市政务大厅、社保、医保、公积金、不动产登记 5 个独立业务系统统一接入新平台，实现 200 个高频事项"一窗受理、一次办结"。

项目实施过程中发生以下事件：

（1）立项阶段：局信息处委托某 IT 咨询公司编制可行性研究报告，报告侧重技术方案，对经济可行性仅给出定性描述"投资合理、效益显著"。报告未经独立专家评审即由局领导签批立项。立项批复文件中未明确投资估算与资金来源。

（2）采购阶段：项目采用公开招标，招标文件 4 月 1 日发出，规定投标截止时间为 4 月 22 日。招标文件中要求"投标人须具有本省政务类系统建设业绩不少于 3 项"。评标委员会由 6 人组成，其中招标人代表 3 人，技术经济专家 3 人。共有 B、C、D、E、F 5 家单位投标，中标候选人公示 2 日后即发出中标通知书。4 月 28 日发出中标通知书，双方于 5 月 22 日签订合同。

（3）合同与变更阶段：合同中约定"乙方按甲方需求完成平台升级并通过验收"，未约定项目范围明细、可交付成果清单、知识产权归属、源代码与接口文档交付。开发过程中，业务部门先后提出增加人脸识别认证、电子证照共享、对接市"雪亮工程"视频监控等 15 项新需求，承建方项目经理小王认为"用户提出的都是合理需求"，全部安排开发，未办理书面变更手续，未评估对进度与成本的影响。

（4）组织治理阶段：局里同时启动政务大数据、城市运行指挥中心、智慧社区等 5 个信息化项目，各项目分别由不同部门牵头，缺乏统筹管理，资源争夺严重。小王同时被抽调支持其他项目，导致"一网通办"项目关键岗位缺人，进度滞后约 2 个月，成本已使用预算的 78%。

（5）知识产权与成果归属阶段：项目上线前，业务部门要求承建方在合同外另签一份《软件著作权转让协议》，将平台软件著作权全部转让给市政务服务管理局，并要求不支付额外费用。承建方拒绝，双方产生争议。

**问题**：

1. 指出本项目在立项阶段存在的问题，并给出改进建议。
2. 指出本项目在招投标与采购阶段存在的问题，并说明理由。
3. 分析本项目在合同管理与变更管理方面存在的缺陷及风险。
4. 结合组织级项目管理（OPM）理论，分析局里同时启动 5 个信息化项目带来的问题及治理建议。
5. 针对软件著作权争议，依据《著作权法》《民法典》分析著作权归属，并给出处置建议。

---

**参考答案**：

**问题 1：立项阶段的问题与改进建议**

存在的问题：
- **可行性研究报告论证不充分**。报告仅给出定性结论，缺乏定量的投资估算、收益测算、投资回收期、NPV/IRR 等经济可行性分析数据；技术、经济、运行环境、社会、管理五维度论证失衡。
- **未组织独立专家评审**。立项可行性研究报告应通过专家评审会或第三方评估机构论证，形成评审意见，作为立项决策依据；本项目"未经评审即签批"违反项目论证程序。
- **立项批复内容缺失**。立项批复文件应明确投资估算、资金来源、进度计划、考核指标等内容；案例中"未明确投资估算与资金来源"导致后续招投标预算与合同价款缺乏法定依据。
- **项目论证 vs 项目评估角色混淆**。咨询公司（受托方）做的是"项目论证"，但本项目缺少投资方/审批方组织的"项目评估"环节。

改进建议：
- 重新组织第三方专业机构或专家组对可行性研究报告进行评审，从技术、经济、运行环境、社会、管理五维度系统论证，特别补充**经济可行性定量分析**（NPV、IRR、回收期、敏感性分析）。
- 由局领导决策层（投资方）牵头组织**项目评估**，重点评估投资价值、风险承受度、合规性与可持续性，形成评估意见。
- 完善立项批复文件，明确投资估算、资金来源、里程碑计划、绩效考核指标，将立项批复作为招投标的前置条件。

**问题 2：招投标与采购阶段的问题**

（1）**招标文件发出至投标截止时间不足 20 日**。4 月 1 日发出、4 月 22 日截止仅 21 日（实际跨期不足 20 个日历日，依法必须招标项目不少于 20 日）。即使按 21 日计算，仍需核查是否含法定节假日或是否低于"自发出之日起至截止之日止最短不得少于 20 日"的硬性要求；存在被认定为不足 20 日的风险。

（2）**以不合理条件限制排斥潜在投标人**。要求"本省政务类系统建设业绩"，以特定行政区域业绩作为资格条件，构成对潜在投标人的差别待遇与歧视待遇，违反《招标投标法实施条例》第三十二条。

（3）**评标委员会组成不合法**。评标委员会应为 5 人以上单数，且**技术经济专家不得少于成员总数的 2/3**。本项目 6 人中专家仅 3 人，仅占 1/2（不足 2/3），违反法定比例。

（4）**中标候选人公示期不足**。中标候选人公示期**不得少于 3 日**，案例仅公示 2 日，违反法定时限，可能导致中标结果无效。

（5）**未在 15 日内提交招投标情况书面报告**。中标通知书发出后未在 15 日内向行政监督部门提交招投标情况书面报告。

（6）**超期签订合同**。中标通知书 4 月 28 日发出，应在 30 日内即 5 月 28 日前签订书面合同，5 月 22 日在期内；若按公告期不足导致中标无效的情形，则全链条失效。需结合公示期整改后重新计算。

**问题 3：合同管理与变更管理的缺陷及风险**

合同管理缺陷：
- **合同条款严重缺失**：未约定项目范围明细、可交付成果清单、验收标准、知识产权归属、源代码与接口文档交付、变更处理机制与计价方式、付款节奏、SLA、违约责任。
- "按甲方需求完成"属**范围约定不明**，为后续范围蔓延与争议埋下隐患。
- 未约定**里程碑验收**与**阶段付款**机制，质量与成本风险全部留在甲方。

变更管理缺陷：
- 15 项新增需求全部未经书面变更申请、未做影响分析、未报 CCB 审批、未更新三大基准、未保留变更日志，是典型的**范围蔓延 + 镀金**。
- 未对进度、成本、质量、风险进行综合影响评估，导致进度滞后 2 个月、成本超支风险已现（成本已用 78% 而工期仅过约 67%）。
- 缺乏**需求跟踪矩阵（RTM）**，需求—设计—开发—测试无法双向追溯。

风险：
- 验收风险（无明确标准极易导致验收争议）、知识产权归属风险（未约定易引发纠纷）、超支风险（变更未重新核定成本基准）、进度违约风险、争议解决无机制（无仲裁条款则只能诉讼）。

改进建议：
- 立即签订**合同补充协议**，明确范围明细、验收标准、知识产权、源代码与文档交付清单、变更计价规则、付款节点、SLA。
- 建立 CCB 与**整体变更控制六步流程**：变更申请 → 影响分析 → CCB 审批 → 实施 → 验证 → 归档更新。
- 引入**挣值分析**重新核定 EAC，必要时向甲方提出工期与费用索赔。
- 建立**配置管理库**与**变更日志**，实现可追溯。

**问题 4：组织级项目治理问题及建议**

暴露的问题：
- **缺乏项目组合（Portfolio）治理**。5 个信息化项目分散在不同部门，各项目独立运行、无统一战略对齐、无统一优先级排序、无统一资源调度，形成"项目孤岛"。
- **资源争夺与关键人员单点**。小王被同时抽调支持其他项目，导致"一网通办"关键岗位缺人，进度滞后，说明组织未做项目集层面的资源平衡与关键人员储备。
- **缺乏 PMO/项目治理办公室**。没有统一的 PMO 进行集中协调、监控与汇报，5 个项目的状态、风险、收益各管一摊。
- **战略与项目脱节**。5 个项目与局"一网通办"核心战略的关联度、资源占用、阶段性收益未做组合分析，可能存在"局部合理但整体不优"。
- **OPM 三层架构失位**：组合层（做不做）、项目集层（如何协同）、项目层（如何交付）三个层次未贯通。

治理建议：
- 成立**局信息化项目治理委员会**（类似 PMO 升级），承担项目组合治理职能：对所有信息化项目进行战略对齐度评估、优先级排序、资源平衡、阶段性价值评审。
- 引入**项目集管理**，把"一网通办、大数据、指挥中心、智慧社区"等高度关联的项目纳入一个项目集，统一治理；项目集经理协调跨项目的资源、风险、变更、依赖。
- 建立**统一的项目管理方法论**（过程裁剪指南、模板、工具），统一立项审批、招投标、合同、变更、验收、收尾流程。
- 实施**关键岗位 AB 角与资源池机制**，避免关键人员单点；项目间借调需经过项目集经理审批。
- 建立**组合级仪表盘**：里程碑、挣值、风险、收益实现率、用户满意度等可视化指标，定期向治理委员会汇报。
- 推行**阶段性关口评审（Gate Review）**：立项/招标/需求/设计/上线/运维各关口评审，不通过即不进入下一阶段。

**问题 5：软件著作权争议的归属判定与处置建议**

依据《著作权法》《计算机软件保护条例》《民法典》合同编：

（1）**本案软件属于"委托开发的计算机软件"**。市政务服务管理局（甲方、委托方）委托承建方（乙方、受托方）开发平台软件。

（2）**归属判定**：
- 软件著作权归属**首先看合同约定**。本案合同中**未约定软件著作权归属**，按民法典技术开发合同条款处理。
- 《民法典》合同编规定：委托开发**未约定归属的**，软件著作权归**受托方（承建方）所有**，但**委托方（甲方）享有免费使用权**。
- 因此，**本案软件著作权当前归属于承建方**，而非市政务服务管理局。

（3）**争议焦点澄清**：
- 甲方主张"在合同外另签零对价转让协议"无法律依据：**著作权转让属于权利的让渡，必须是有偿或约定的对价安排**，且应**订立书面合同**；零对价转让承建方可主张显失公平或拒绝履行。
- 即便双方同意转让，也应通过**合同补充协议或单独的著作权转让合同**约定转让价款、范围、交付物、交付方式、违约责任等，且转让合同应**自登记之日起对抗善意第三人**（软件著作权转让登记为对抗要件，非生效要件）。

（4）**处置建议**：
- 双方协商签订**软件著作权（使用权）许可或转让合同**，明确：
  - 甲方需要的核心权利：**永久、独占、可转让的使用权**（含复制、修改、发行、信息网络传播等），**源代码与接口文档交付**。
  - 转让对价：按市场价或双方协商定价，纳入项目预算或追加预算。
- 若仅需使用权，建议采用**独占许可**方式，成本低于整体转让；许可应明确许可期限、地域、是否允许转许可、是否允许修改。
- 在原始合同中已明确约定"按甲方需求完成平台升级并通过验收"但**未约定源代码交付与著作权**，构成合同重大遗漏；甲方应吸取教训，未来合同模板中**强制约定知识产权与源代码归属条款**。
- 完善项目管理：**技术合同必须审查知识产权条款**，并由法务/知识产权部门会签。

**踩分要点**：

**问题 1（立项）——必拿"可行性五维度 + 项目论证vs评估角色 + 评审程序"**
- 必写关键词：**技术/经济/运行环境/社会/管理可行性五维度**、**项目论证（乙方/咨询方）vs 项目评估（甲方/投资方）角色区分**、**专家评审与立项批复必备内容**。
- 改进建议要落到"补充经济可行性定量分析 + 重新组织专家评审 + 完善立项批复内容"三步。

**问题 2（招投标）——逐条数字怼**
- 采分点：**20 日截止期**、**公示不少于 3 日**、**评标专家不少于 2/3**、**特定区域业绩限制排斥潜在投标人**、**15 日提交招投标情况书面报告**。
- 答题模板：**"存在问题 + 违反的具体规定/理由"**，漏一条丢一条。
- 注意区分"投标人 5 家"本身合法，**评标委员会组成才是考点**（6 人中专家 3 人未达 2/3）。
- 中标候选人公示期**不少于 3 日**是高频陷阱题。

**问题 3（合同与变更）——分"合同缺陷"与"变更失控"两块**
- 合同缺陷必写：**范围/验收标准/知识产权/源代码与文档/变更机制/付款节点/SLA/违约责任**。
- 变更失控必写：**无书面申请、无影响分析、无 CCB、无变更日志、未更新基准、范围蔓延与镀金**。
- 加分项：用挣值分析点明 CPI<1、SPI<1，需重新核定 EAC。

**问题 4（OPM 治理）——抓住"组合-项目集-项目"三层架构**
- 必写关键词：**项目组合（战略对齐）、项目集（额外收益）、PMO 治理委员会、关键岗位 AB 角、组合仪表盘、关口评审（Gate Review）**。
- 注意区分**OPM 三层与 PMO 三种类型**（支持型/控制型/指令型），不要混用。
- 措施按"治理机构 + 方法论 + 资源机制 + 监控仪表盘 + 关口评审"五层写。

**问题 5（著作权）——抓住"合同约定优先 → 无约定按法定 → 委托开发归受托方"**
- 采分点：**委托开发无约定归受托方、委托方享免费使用权**、**著作权转让必须书面 + 对价 + 登记对抗**、**许可 vs 转让的法律后果不同**。
- 案例陷阱识别：甲方主张"零对价转让"无法律依据，需以合同编与著作权法两套法条交叉论证。
- 改进建议要落到"重新签订许可/转让合同 + 完善合同模板强制约定知识产权条款"。

**通用踩分纪律**
1. 每问先写"存在问题"再写"原因/措施"，一问一段，编号分条。
2. 凡涉及数字的地方必须写出具体数字（**20 日、3 日、5 人单数、2/3、30 日、15 日**），只写"时间太短"不得分。
3. 措施类回答统一套用"**流程 + 工具 + 制度 + 人员**"四维度。
4. 案例细节（5 人评标、本省业绩、零对价转让、5 个项目同时启动、抽调小王）均为采分点，必须逐一回应。
