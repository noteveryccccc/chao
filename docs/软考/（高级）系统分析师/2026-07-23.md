## 今日核心概念

### 1. 企业应用集成分层架构
定义：企业应用集成通过连接、共享和协作机制，将分散的应用系统、数据和业务流程整合为协同工作的整体，通常按层次划分为界面集成、数据集成、控制集成和流程集成。
关键要点：
- 界面集成又称表示集成，通过统一门户、聚合页面和单点登录将多个系统入口整合，对源系统侵入最小但价值有限。
- 数据集成通过数据复制、ETL、数据虚拟化和主数据管理实现跨系统数据共享，是数据中台和报表分析的基础。
- 控制集成通过应用接口和业务逻辑调用实现功能复用，紧耦合但灵活性差，适合核心业务系统。
- 流程集成通过工作流和编排引擎串联多系统业务节点，实现端到端业务流程贯通，是 OA 和 BPM 的核心。
- 系统分析师应在需求分析阶段判断集成层次，避免一上来就做控制集成导致系统耦合过重。

### 2. 集成架构风格与总线模式
定义：集成架构风格决定系统间通信的拓扑与协议模式，常见风格包括点对点、中心辐射和企业服务总线。
关键要点：
- 点对点集成简单直接，但系统数量增加时接口呈指数级膨胀，难以维护。
- 中心辐射式通过单一中心节点转发所有调用，降低耦合但中心节点成为性能与可用性瓶颈。
- 企业服务总线通过统一消息路由、协议转换、消息增强和编排能力解耦服务提供方与消费方。
- ESB 核心能力包括服务注册、消息协议转换、数据格式转换、安全控制、监控管理和异常处理。
- 现代微服务架构在很多场景下替代了 ESB，但跨企业、跨协议、跨安全域的集成场景仍以 ESB 为主。

### 3. 消息中间件与可靠消息
定义：消息中间件通过异步消息传递实现系统解耦与流量削峰，可靠消息机制保证消息不丢失、不重复、有序可达。
关键要点：
- 消息传递模式包括点对点模型与发布订阅模型，前者一条消息被一个消费者消费，后者一条消息可被多个订阅者接收。
- 消息可靠投递的关键环节包括生产者确认、Broker 持久化、消费者手动 ACK、幂等处理和死信队列。
- 至少一次投递结合消费者幂等是最常见的可靠语义，相比恰好一次实现复杂度更低且更易落地。
- 消息顺序性适用于单分区单消费者的场景，跨分区顺序需借助业务键路由或全局序号。
- 系统分析师应在设计评审中明确消息可靠性等级，避免业务方误以为消息中间件天然可靠。

### 4. 主数据管理与数据治理
定义：主数据是跨系统共享的核心业务实体数据，如客户、产品、供应商和组织机构，数据治理通过制度、流程和技术保障主数据质量与一致性。
关键要点：
- 主数据管理强调单一权威来源，从源头系统统一分发，避免在多个系统中重复维护。
- 数据质量维度包括完整性、准确性、一致性、唯一性、及时性和有效性，是数据资产化的前提。
- 数据治理组织通常由数据所有者、数据管理员、数据使用者和技术支撑团队组成，通过数据资产管理流程闭环。
- 主数据平台应提供数据建模、采集、清洗、发布、订阅、版本管理和血缘追踪能力。
- 系统分析师在系统设计时应明确哪些实体属于主数据，避免在多个系统重复建模导致数据漂移。

### 5. 数据交换模式与一致性
定义：数据交换模式决定系统间数据同步的方式与一致性保证，常见模式包括同步调用、异步消息、文件传输和共享数据库。
关键要点：
- 同步调用实时性强但耦合高，适合强一致性场景；异步消息解耦但需考虑最终一致性。
- 文件交换适合大批量、低频、容忍延迟的数据同步，如夜间批量下载对账文件。
- 共享数据库通过统一数据源避免数据复制，但跨团队协作易出现表结构冲突与权限争议。
- 一致性策略包括本地事务、分布式事务、可靠消息、本地消息表和事后对账，应按业务容忍度选择。
- 最终一致性是分布式集成的常态，系统分析师应让业务方明确一致性窗口与补偿机制。

## 案例分析题

**题目**：
某大型集团已完成核心 ERP、财务共享、HR、CRM 和供应链系统的建设，计划实施集团级集成平台，统一打通各系统数据与流程。现有方案如下：
① 各业务系统直接通过点对点接口与上下游对接，目前接口数量已超过 200 对；
② 客户、供应商、组织机构等主数据在多个系统中分别维护，存在大量重复和冲突；
③ 销售订单创建后通过 MQ 异步通知财务系统生成凭证，但偶发消息丢失导致业务投诉；
④ 集团报表通过 ETL 每晚从各业务系统抽取数据，但报表口径不一致引发业务部门争议；
⑤ 计划引入 ESB 替换点对点接口，但 ESB 厂商只支持 HTTP 和 SOAP，不支持现有 Kafka 消息协议；
⑥ 集团未设立数据治理组织，主数据归属不清，标准不统一。

请从集成架构、主数据管理、消息可靠性、报表一致性、技术选型和数据治理六个方面指出问题，并提出改进方案。

**参考答案**：

1. 集成架构方面，点对点接口超过 200 对，调用关系错综复杂，新增和修改接口成本高、风险大。应引入 ESB 与 API 网关相结合的统一集成平台，统一服务注册、协议转换、流量控制和监控告警；将核心业务接口优先迁移到 ESB，遗留接口逐步替换并形成统一的服务目录。

2. 主数据管理方面，客户、供应商、组织机构在多系统分别维护会导致数据漂移、统计口径冲突和业务决策失真。应建设集团级主数据平台，确定每类主数据的权威来源系统，统一数据模型、编码规则和变更流程；下游系统通过订阅方式获取主数据，禁止绕过平台直接修改。

3. 消息可靠性方面，销售订单到财务凭证的消息偶发丢失说明缺少可靠投递保障，可能导致账务不一致。应启用生产者本地事务表 + 定时回查确保消息一定发出，Broker 开启持久化和多副本，消费者改为手动 ACK 并保证幂等处理；对账系统定期核对订单与凭证，发现差异及时补偿。

4. 报表一致性方面，ETL 抽取口径不一致说明缺乏统一指标管理。应建设指标管理平台，明确每个指标的名称、业务定义、计算口径、数据来源和责任部门；所有报表按指标平台统一口径开发，并在 BI 工具中标注指标版本和变更记录。

5. 技术选型方面，ESB 不支持 Kafka 协议会限制现有异步消息体系的接入。应要求 ESB 厂商补充适配器或采用适配器网关代理 Kafka 协议；或者引入 API 网关 + 轻量级消息桥接组件，由消息桥接完成 Kafka 与 ESB 协议互转，避免大规模业务改造。

6. 数据治理方面，主数据归属不清、标准不统一导致治理工作无人牵头。应建立集团数据治理委员会和数据管家团队，明确主数据所有者、管理员和技术支撑职责；制定主数据标准、数据质量规则和考核机制，将数据质量纳入业务系统考核。

**踩分要点**：
- 指出点对点接口膨胀问题，提出 ESB 与 API 网关统一集成方案。
- 指出主数据多头维护问题，提出权威来源 + 订阅分发方案。
- 指出消息丢失问题，提出本地消息表 + 幂等 + 对账方案。
- 指出报表口径不一致问题，提出指标管理平台 + 统一口径方案。
- 指出 ESB 协议不支持问题，提出适配器或消息桥接方案。
- 指出数据治理组织缺失问题，提出治理委员会 + 主数据所有者方案。

## 记忆口诀

集成四层：界面数据控制流程，由浅入深看耦合。

集成风格：点对点会爆炸，中心辐射有瓶颈，ESB 解耦最常用。

消息模式：点对点单一消费，发布订阅多消费，可靠靠确认持久化和幂等。

主数据：单一权威来源，六性完整准确一致唯一及时有效，治理三件套制度流程技术。

数据交换：同步实时强，异步解耦终一致，文件适合大批量，共享库易冲突。

一致性：本地事务强一致，分布式事务贵而难，可靠消息加对账是工程常态。
