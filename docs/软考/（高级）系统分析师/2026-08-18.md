## 今日核心概念
### 1. 系统架构设计方法论
定义：在系统分析阶段，基于需求与约束，选择架构风格、划分组件、定义交互关系并论证质量属性的系统性方法学，是连接需求与实现的关键桥梁。
关键要点：
架构四阶段：需求分析→架构设计→详细设计→实现，架构设计承上启下
架构设计四视角（4+1）：逻辑视图、开发视图、进程视图、物理视图，加场景视图
IEEE 1471-2000 / ISO/IEC/IEEE 42010：架构文档化国际标准的三大核心元素（架构、视图、视点）
架构决策记录（ADR）：四要素——背景、决策、状态、后果，用于沉淀与追溯架构决策
架构演进四模式：绞杀者模式（Strangler Fig）、防腐层（Anti-Corruption Layer）、特性开关（Feature Toggle）、重构窗口
架构治理三要素：架构原则、架构流程、架构工具，确保架构在组织中持续落地

### 2. 经典架构风格
定义：描述系统组织结构、组件交互模式的典型范式，是架构选型的"模式库"，每种风格有适用场景、优势与局限。
关键要点：
管道—过滤器（Pipeline-Filters）：组件独立、可并发、易扩展，典型编译器、日志处理
层次风格（Layered）：分层隔离、依赖单向向下，典型 OS、Web 三层、ERP
面向对象（Object-Oriented）：封装+继承+多态，典型企业应用、Java/Spring
事件驱动（Event-Driven）：消息异步、解耦，典型 Kafka、MQ、CQRS
微服务（Microservices）：独立部署、独立团队、API 契约，典型 Spring Cloud、政务云
客户端-服务器（C/S）、B/S、SOA、服务网格（Service Mesh）各有取舍
选择原则：匹配质量属性（性能/可伸缩/可维护/可演进），无万能风格

### 3. 架构评估方法（ATAM / SAAM / ARB）
定义：通过结构化方法对架构质量属性（性能、可用性、安全性、可修改性等）进行系统化评估，识别风险与敏感点，是架构决策的依据。
关键要点：
ATAM（架构权衡分析）：识别质量属性场景、架构决策、敏感点/权衡点/风险/假设
SAAM（软件架构评估方法）：关注可修改性，单场景驱动
ARB（架构复审）：检查架构是否符合需求
质量属性九维度：性能、安全性、可用性、可修改性、可测试性、互操作性、可靠性、可移植性、可伸缩性
质量属性场景六要素：来源、刺激、响应、度量、制品、触发条件
评估输出：敏感点（对某属性影响最大）、权衡点（两属性冲突）、风险（未来威胁）、假设（前提条件）

### 4. 架构文档化与可视化（C4 / 4+1）
定义：用统一、分层、可演进的图与文档体系描述架构，使干系人（开发、运维、领导、用户）都能理解系统。
关键要点：
C4 模型四层：Context（系统上下文）→ Container（容器）→ Component（组件）→ Code（代码）
4+1 视图：逻辑视图（组件与接口）、开发视图（包与模块）、进程视图（并发与通信）、物理视图（部署）、场景视图（用例与质量属性映射）
UML 架构视图：类图（逻辑）、组件图（部署）、部署图（物理）、时序图（交互）、活动图（流程）
架构图原则：单一视角聚焦单一关注点，避免"一图打天下"
文档化输出：架构图 + ADR + 质量属性场景 + 接口契约 + 部署图 + 运维手册

### 5. 微服务架构关键设计
定义：将单体系统拆分为多个独立部署、独立演进、API 契约通信的小型服务，是互联网与政务云主流架构范式。
关键要点：
拆分原则：按业务能力/领域边界拆分（DDD 限界上下文）、团队自治（康威定律）、独立部署独立扩缩
关键组件：服务注册（Nacos/Eureka）、网关（Spring Cloud Gateway/Kong）、熔断（Sentinel/Hystrix）、链路追踪（SkyWalking/Jaeger）、配置中心（Apollo/Nacos）
数据管理：服务自治数据库 + 数据访问层（DA）+ 事件驱动最终一致
分布式事务：2PC/3PC、Saga、TCC、最大努力通知，避免强一致
API 契约：OpenAPI/AsyncAPI、Pact 契约测试、版本号管理
可观测性：Metrics/Logs/Traces 三支柱 + 全链路 traceId + 黄金信号告警
部署：容器化（Docker/K8s）+ 蓝绿/金丝雀/滚动发布 + 灰度策略

## 案例分析题
**题目**：
某市政务云"一体化审批服务平台"上线 18 个月后出现以下架构层面问题：
1. 系统仍为单体架构，单次发版需 6 小时全量回归，缺陷修复周期超过 30 天，业务部门频繁要求加需求，开发团队疲于应付。
2. 架构文档缺失，新入职员工需 2 个月才能理解系统，"祖传代码"难以改造，技术债累积。
3. 性能瓶颈集中在审批核心模块，数据库慢 SQL 频发，高峰期响应时间超过 5 秒，无法水平扩展。
4. 安全事件频发：曾出现越权访问、SQL 注入、敏感数据泄露，缺乏统一的鉴权与审计。
5. 团队缺乏架构决策记录，每次重大改动"拍脑袋决定"，决策无法追溯，导致回退困难。
6. 微服务拆分尝试过两次，但"按表拆分"和"按页面拆分"均失败，服务间强耦合、分布式事务混乱。

问题：
1. 请分析该系统架构层面的主要问题，并给出架构演进总体方案。
2. 针对单体架构与发版慢的问题，应如何设计架构拆分策略？请给出拆分原则与边界划分建议。
3. 架构文档缺失问题应如何治理？请设计 C4 + 4+1 双轨文档化方案。
4. 性能瓶颈应如何优化？请从架构层（缓存/异步/分库分表/读分离）给出方案。
5. 安全事件应如何从架构层面根治？请设计统一鉴权、审计、加密、脱敏的安全架构。
6. 架构决策混乱应如何治理？请设计 ADR 决策记录机制与架构评审流程。

**参考答案**：
1. 架构层面主要问题与演进方案：
问题集中在"架构陈旧、文档缺失、性能瓶颈、安全失控、决策无追溯、拆分失败"。
演进方案：采用绞杀者模式（Strangler Fig），不推翻重建，逐步把单体系统按业务域拆分为微服务，新业务用微服务承载、老业务逐步迁移；建立"架构治理三要素"（原则/流程/工具），设立架构委员会（CCB 类似组织）评审重大决策；建立 ADR 决策记录机制，所有重大架构决策入库；按 C4 + 4+1 双轨重构架构文档；安全左移，把安全能力下沉到架构层。
演进节奏：36 个月分三批切换——先外围（门户/查询）后核心（审批/支付）、先查询后交易、先非实时后实时。

2. 架构拆分策略：
拆分原则：按业务能力/领域边界（DDD 限界上下文）而非按表/按页面；团队自治（康威定律）——按团队规模与职责拆服务；独立部署独立扩缩；API 契约先行。
边界划分：审批核心域（审批、流转、时限）、用户域（身份、组织、权限）、材料域（材料、上传、归档）、支付域（缴费、退缴）、监督域（投诉、评价、监察）、门户域（首页、查询、公示）共 6 大域 20+ 微服务。
防腐层（ACL）：保留老单体作为"黑盒"，新微服务通过防腐层调用，避免直接耦合。
事件驱动：跨域交互用消息（RocketMQ/Kafka）异步解耦，最终一致。
分布式事务：核心业务用 TCC/Saga，非核心用最大努力通知，避免 2PC 强一致。
契约测试：Pact 保障消费方/提供方接口一致，CI 双向校验。

3. C4 + 4+1 双轨文档化：
C4 四层：L1 上下文（业务边界+外部系统）、L2 容器（微服务/数据库/中间件）、L3 组件（服务内部模块）、L4 代码（关键类与接口）。
4+1 五视角：逻辑视图（组件+接口）、开发视图（包+模块）、进程视图（并发+通信）、物理视图（部署+拓扑）、场景视图（用例+质量属性）。
双轨关系：C4 给领导与业务方看（自上而下），4+1 给开发与运维看（自下而上），场景视图连接两者。
工具链：C4Model（PlantUML/Draw.io）、4+1 用 UML + 部署图；所有图入库 Wiki，与代码同步更新。
ADR 机制：每个架构决策生成 ADR 文档（背景/决策/状态/后果），与图版本绑定。
质量属性场景：性能/安全/可用/可修改等关键属性用 ATAM 方法识别敏感点与权衡点，作为架构决策依据。

4. 性能优化架构方案：
缓存层：Redis 多级缓存（本地 Caffeine + 分布式 Redis），热点数据预加载，读写分离。
异步化：非核心操作（短信、邮件、日志）走消息队列（RocketMQ/Kafka）异步处理，主链路只保留核心同步。
分库分表：核心审批表按"审批号哈希"分库分表（ShardingSphere），热点表加缓存。
读分离：主从复制 + 读写分离，读多写少的查询走从库。
弹性扩展：K8s HPA 自动扩缩容，结合 QPS/延迟/饱和度自动调整副本数。
限流降级：Sentinel 限流+熔断+降级，核心接口保活，非核心接口降级。
链路优化：全链路 traceId 打点，慢 SQL/慢接口告警，定位瓶颈。
容量规划：基于历史数据做容量预测，提前扩容，避免高峰雪崩。

5. 安全架构设计：
统一鉴权：OAuth2.0 + JWT + 网关统一鉴权，所有微服务无鉴权逻辑，集中管控；RBAC + ABAC 混合模型，按角色+属性授权。
审计：统一审计日志（操作人/时间/操作/对象/IP/结果），不可篡改，保留 3 年以上；关键操作（删除、导出、审批）单独审计。
加密：传输 TLS 1.3 + mTLS 双向认证；存储敏感字段 AES/SM4 加密，密钥 KMS/HSM 管理；密码 BCrypt/SM3 加盐哈希。
脱敏：敏感字段（身份证、手机号、银行卡）前端展示脱敏，后端按权限返回；日志/链路脱敏。
漏洞治理：CI 集成 SonarQube/Trivy 安全扫描，OWASP Top 10 必检；接口限流+防重放+防 SQL 注入/越权。
零信任：永不信任、持续验证、最小权限；SDP/PAM/SSO 三件套，关键操作 MFA 双因素认证。
数据治理：数据分类分级（公开/内部/敏感/绝密），按级别实施加密/脱敏/访问控制。

6. ADR 决策记录与架构评审机制：
ADR 四要素：背景（为什么做决策）、决策（选了什么方案）、状态（提议/已采纳/已弃用/已替代）、后果（影响、风险、收益）。
ADR 模板：标准模板 + 评审流程，重大架构决策必须生成 ADR。
架构委员会（Architect Board）：3-5 人，每月评审重大架构决策，输出决策记录。
评审四类：架构变更（新增/重构）、安全评审、容量评审、性能评审。
决策追溯：所有 ADR 入库，按时间/主题/领域可检索；老架构文档保留归档，新文档明确版本与演进路径。
演进治理：采用绞杀者模式 + 防腐层 + 特性开关 + 重构窗口四件套，36 个月分三批切换，先外围后核心、先查询后交易、先非实时后实时。
度量：架构决策周期、技术债趋势、架构评审通过率、决策回退率纳入架构 KPI。

**踩分要点**：
1. 架构演进：必答"绞杀者模式+防腐层+36 个月三批切换+先外围后核心"
2. 拆分策略：必答"DDD 限界上下文+康威定律+独立部署+API 契约先行"
3. 文档化：必答"C4 四层+4+1 五视角+双轨+ADR 入库"
4. 性能优化：必答"缓存+异步+分库分表+读分离+弹性扩缩+限流降级"
5. 安全架构：必答"统一鉴权+审计+加密+脱敏+零信任+数据分级"
6. 决策治理：必答"ADR 四要素+架构委员会+评审四类+绞杀者四件套"
