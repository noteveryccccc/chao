## 今日核心概念

### 1. 系统安全基础与CIA三性
定义：信息安全是保护信息与信息系统的保密性、完整性和可用性，使系统在预期条件下稳定可靠运行。
关键要点：
- 保密性要求信息不被未授权访问、泄露或扩散，常用加密、访问控制和最小权限实现。
- 完整性要求信息在存储、传输和处理过程中不被未授权篡改或破坏，常用校验、签名、事务和审计实现。
- 可用性要求授权用户需要时能够及时获得信息服务，常用冗余、容错、备份和应急切换实现。
- 真实性和不可否认性是 CIA 的补充，数字签名、时间戳和操作日志是常用实现手段。
- 系统分析师应在架构设计中明确每一类资产的保护目标，而不是把安全当作部署阶段补的功能。

### 2. 加密算法与数字签名
定义：加密算法通过数学变换保护信息机密性；数字签名通过私钥签名、公钥验签实现身份认证、完整性和不可否认性。
关键要点：
- 对称加密加解密速度快，适合批量数据加密，但密钥分发和密钥管理复杂。
- 非对称加密加解密速度慢，适合密钥交换、数字签名和小数据加密。
- 哈希算法用于生成消息摘要，应具备抗原像、抗第二原像和抗碰撞特性，常见算法有 SHA-256 和 SM3。
- 数字签名由发送方用私钥对摘要签名，接收方用公钥验签，结合证书可实现可信身份认证。
- 工程中通常采用对称加密数据、非对称加密会话密钥、哈希校验完整性的混合方案。

### 3. 身份认证与访问控制
定义：身份认证解决“你是谁”，访问控制解决“你能做什么”，二者共同决定主体对客体的操作权限。
关键要点：
- 认证方式包括口令、生物特征、数字证书、动态令牌和多因素认证，关键系统应使用多因素。
- 访问控制模型包括自主访问控制、强制访问控制、基于角色的访问控制和基于属性的访问控制。
- RBAC 是企业系统最常见的方案，通过角色将权限与用户解耦，便于授权管理和审计。
- 最小权限原则要求用户和进程只获得完成其任务所必需的最小权限集合。
- 特权账号应单独管理、强密码、留痕审计，避免超级管理员账号长期在线或共享使用。

### 4. 网络安全与边界防护
定义：通过网络架构、边界设备、传输加密和入侵检测等措施，防御来自网络层的攻击、渗透和数据窃取。
关键要点：
- 防火墙、入侵检测系统、入侵防御系统和 Web 应用防火墙分别承担访问控制、攻击检测、攻击拦截和 Web 攻击防护职能。
- 网络分区应按业务、安全等级和数据敏感度划分，重要业务系统应部署在独立安全域中。
- VPN、IPSec 和 TLS 用于在公网或跨域场景中建立可信传输通道，防止数据在传输中被窃听和篡改。
- 零信任强调“从不信任、持续验证”，按身份、设备、行为和上下文动态授权，是边界防护的新方向。
- 防御体系应纵深部署，单一防护手段被绕过不会直接导致核心系统失陷。

### 5. 应用安全与安全工程
定义：将安全要求贯穿于需求、设计、编码、测试、部署、运行和运维全生命周期，使系统在生命周期内持续具备抗攻击能力。
关键要点：
- 常见 Web 风险包括注入、跨站脚本、跨站请求伪造、文件上传、权限绕过和敏感信息泄露，应在框架层统一防护。
- 输入校验、输出编码、参数化查询、CSRF 令牌、文件类型白名单和会话超时是基础防护手段。
- 安全开发生命周期要求在需求阶段定义安全要求，在设计阶段进行威胁建模，在测试阶段进行渗透测试。
- 漏洞管理应建立发现、评估、修复、验证、复盘闭环，并按资产重要性和风险等级确定修复优先级。
- 应急响应应明确事件分级、上报流程、处置预案、恢复步骤和事后复盘，避免事件扩大和责任不清。

## 案例分析题

**题目**：
某大型互联网公司计划面向公众提供在线交易服务，年交易额超百亿元，用户量超过五千万。系统采用前后端分离架构，后端部署在多云环境，前端通过 HTTPS 访问，敏感数据存储在自建数据库中。现有安全方案如下：
① 全部内部服务使用同一套共享账号，运维人员通过堡垒机登录；
② 客户端使用用户名加口令登录，未启用多因素认证；
③ 内部服务之间采用 HTTP 明文通信，敏感字段在应用层自行加密；
④ 数据库使用统一 root 账号，业务系统、运维平台、报表系统共用同一连接；
⑤ Web 接口仅部署 Web 应用防火墙，未做输入校验、参数化查询和输出编码；
⑥ 公司未建立漏洞管理流程，安全事件由运维人员临时处置。

请从身份认证、账号管理、传输安全、数据库安全、应用安全和安全管理六个方面指出问题，并提出改进方案。

**参考答案**：

1. 身份认证方面，五千万用户仅使用用户名加口令登录风险过高，一旦口令泄露即可盗号、撞库和大面积账号失窃。应在关键场景启用多因素认证，结合短信、动态令牌、生物特征或设备指纹；登录环节加入风控识别异常登录行为，对异常账号实施二次验证和临时锁定。

2. 账号管理方面，共享账号无法定位具体操作人，审计、追责和最小权限都难以落地。应推行“一人一账号”，按岗位和职责分配账号，清理公共账号和长期不用的僵尸账号；特权账号应单独管理、采用强密码、强制多因素、限制登录来源并开启全程审计。

3. 传输安全方面，内部服务明文通信且敏感字段由应用层自行加密，加密算法、密钥管理和协议升级都难以统一，一旦密钥泄露将造成大规模数据泄露。所有内部服务通信应统一升级为 TLS，关闭不安全的协议和弱加密套件；统一由平台侧管理证书、密钥和协议版本，应用层只负责业务字段。

4. 数据库安全方面，root 账号共用导致权限过大、操作不可追溯，且业务高峰容易因锁表影响报表和运维任务。应按业务系统分配独立数据库账号并授予最小权限，例如只读、只写或字段级脱敏；禁止业务系统使用超级账号操作生产库，敏感数据应进行加密存储和脱敏展示。

5. 应用安全方面，仅依靠 Web 应用防火墙无法覆盖所有漏洞，缺少输入校验、参数化查询和输出编码会带来 SQL 注入、XSS、CSRF 等风险。应在框架层统一封装参数化查询、输入校验、输出编码和 CSRF 令牌；建立白盒代码扫描、灰盒安全测试和黑盒渗透测试的多层检测机制，关键业务上线前必须通过安全测试。

6. 安全管理方面，缺少漏洞管理流程会导致漏洞持续累积，安全事件临时处置难以保证响应质量和复盘改进。应建立覆盖漏洞发现、风险评估、修复、验证和复盘的全生命周期管理流程，按资产重要性和风险等级确定修复优先级；制定安全事件分级标准和应急预案，定期开展演练并形成复盘报告。

**踩分要点**：
- 指出仅用户名口令风险高，提出多因素认证、异常登录识别和风控方案。
- 指出共享账号无法追责，提出一人一账号、特权账号独立管理与审计方案。
- 指出明文通信和自实现加密风险，提出全链路 TLS、统一证书和密钥管理方案。
- 指出 root 账号共用和最小权限缺失，提出分账号、字段级授权和数据加密方案。
- 指出仅靠 WAF 防护不足，提出框架层统一防护与多层测试方案。
- 指出漏洞管理和应急响应缺失，提出全流程漏洞管理与分级应急响应方案。

## 记忆口诀

安全三性：保密性、完整性、可用性，加起来还有真实不可否认。

加密组合：对称快非对称慢，哈希校验做摘要，签名验签靠公私钥。

访问控制：自主强制 RBAC，最小权限是铁律，特权账号单管强审。

网络防护：防火墙 IDS IPS WAF 分层守，零信任持续验证不分内外。

Web 六大风险：注入、跨站、跨站请求伪造、上传、越权、泄露，框架统一防。

安全工程：需求定安全，设计做威胁，测试做渗透，漏洞全闭环，事件有预案。
