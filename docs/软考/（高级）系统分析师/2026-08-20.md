## 今日核心概念
### 1. 系统架构风格
定义：系统架构风格是描述系统组织方式的抽象模式，规定了组件类型、连接件类型、约束关系与组合规则，是指导系统结构设计的方法论。
关键要点：
- 数据流风格：批处理序列、管道-过滤器（如 Unix 管道），适用于数据转换类系统
- 调用-返回风格：主程序-子程序、面向对象、客户端-服务器（C/S）、三层 C/S、B/S，是主流业务系统模式
- 独立组件风格：进程通信、事件驱动（隐式调用）、发布-订阅，松耦合但调试难
- 仓库风格：数据库系统、黑板系统、超文本系统，共享数据存储中心
- 虚拟机风格：解释器、规则系统，业务规则灵活可配置

### 2. 面向服务架构 SOA
定义：SOA 是一种将系统功能封装为独立服务、通过服务接口和契约实现跨平台互操作的架构风格，强调服务复用与松耦合。
关键要点：
- 三大角色：服务提供者（发布服务）、服务注册中心（管理服务目录）、服务请求者（调用服务）
- 核心特性：松耦合、粗粒度、可复用、标准化接口、跨平台互操作
- 关键技术：Web Service（SOAP/WSDL/UDDI 三大件）、ESB 企业服务总线、消息中间件
- 服务编排：编排（Orchestration，由中心引擎驱动）、协同（Choreography，服务间点对点协作）
- 与微服务区别：SOA 强调企业级服务复用、ESB 总线，重型；微服务强调业务域拆分、去中心化，轻量

### 3. 微服务架构
定义：微服务架构是将单一应用按业务域拆分为多个小型独立服务，每个服务运行在独立进程中、通过轻量级通信机制（HTTP/REST、消息队列）协作的分布式架构。
关键要点：
- 核心特征：单一职责、独立部署、技术异构、去中心化、容错隔离、自动化运维
- 服务拆分原则：按业务能力拆分（康威定律）、单一职责、限界上下文（DDD）
- 服务治理：服务注册与发现（Eureka/Consul/Nacos）、负载均衡、熔断降级（Hystrix/Sentinel）、限流、链路追踪（Sleuth/SkyWalking）
- 数据管理：每个服务独立数据库（Database per Service）、最终一致性、CAP 定理取舍
- 部署模式：容器化（Docker）+ 编排（Kubernetes）、服务网格（Istio/Linkerd）、Serverless

### 4. 架构评估方法 ATAM
定义：ATAM（架构权衡分析法）是基于质量属性评估软件架构的方法，通过识别质量属性、分析架构决策、权衡取舍，输出可量化的架构评估结论。
关键要点：
- 四大质量属性：可用性、可修改性、性能、安全性、可测试性、易用性
- 评估步骤：描述 ATAM 业务动机→描述架构→识别质量属性→分析架构决策→权衡敏感点与风险点→形成评估报告
- 关键概念：敏感点（一个组件影响某个质量属性）、权衡点（影响多个质量属性）、风险点（潜在问题）、非风险点
- 评估方法：基于场景（Use Case 驱动）、问卷调查、专家访谈、原型验证、度量分析
- 配套方法：SAAM（场景架构分析法）、CBAM（成本效益分析法）、ARID（主动评审法）

### 5. 架构描述语言 ADL
定义：ADL（Architecture Description Language）是用形式化或半形式化语言描述软件架构的标准工具，支持架构建模、分析、验证与代码生成。
关键要点：
- 三要素：组件（Component）、连接件（Connector）、配置（Configuration）
- 主流 ADL：Acme（通用）、Aesop（风格化）、Darwin、C2（SADL）、Wright（形式化验证）、xADL（可扩展）
- 与 UML 区别：UML 是通用建模语言，ADL 是架构专用描述语言，ADL 更关注组件交互与连接件语义
- 架构视图：4+1 视图（逻辑、开发、过程、物理+场景）、TOGAF  ADM 架构开发方法
- 应用场景：架构一致性检查、代码自动生成、性能仿真、可靠性分析

## 案例分析题
**题目**：
某省级政务服务平台原采用单体架构，承载 38 个厅局的 156 项政务服务事项，日均办理量约 25 万件。系统运行三年后出现以下问题：
1. 每年大促（如高考报名、医保结算）期间系统并发量达日常 8 倍，频繁宕机；
2. 任意模块上线均需全量回归测试，平均交付周期 6 周；
3. 数据库单点，连接池频繁耗尽，OLTP 与 OLAP 查询互相影响；
4. 跨厅局数据共享通过 ESB 集中转发，ESB 成为性能瓶颈且升级困难；
5. 技术栈固化在 J2EE + Oracle，无法引入新框架。
省政务办决定重构系统，要求保留核心业务资产、提升高并发能力、缩短交付周期、支持国产化替代。
请分析该系统架构改造方案的设计要点，并说明采用的技术路线。

**参考答案**：
一、现状问题分析
1. 单体架构耦合度高，所有模块打包部署，资源争抢导致大促宕机，可用性差；
2. 紧耦合导致回归测试范围大、交付周期长，无法满足业务快速迭代需求；
3. 数据库单点承担混合负载（事务型+分析型），OLTP/OLAP 互干扰，性能瓶颈明显；
4. ESB 集中式服务总线形成架构瓶颈，单点故障影响全局，扩展性差；
5. 技术栈与数据库单一，无法适配国产化替代要求（信创）。

二、改造方案设计要点
1. 架构风格：从单体架构演进为微服务架构，按业务域拆分为 38 个独立微服务（用户中心、事项中心、受理中心、审批中心、支付中心等），实现独立部署、独立伸缩。
2. 拆分原则：基于 DDD 限界上下文划分服务边界，每个服务对应一个聚合根，遵循"高内聚、低耦合"原则，单一服务数据库不超过 3 张表。
3. 服务治理：引入 Nacos 作为注册中心与配置中心，Sentinel 实现熔断降级限流，SkyWalking 实现全链路追踪，Spring Cloud Gateway 作为统一入口。
4. 数据架构：实施数据库垂直拆分（按业务域分库）+ 水平分片（按办理流水号），OLTP 与 OLAP 分离（MySQL + ClickHouse），引入分布式事务（Seata AT 模式）。
5. 通信机制：内部同步调用采用 OpenFeign（HTTP/REST），跨服务异步事件采用 RocketMQ，最终一致性通过事件溯源 + 本地消息表实现。
6. 部署运维：全面容器化（Docker）+ 容器编排（Kubernetes）+ 服务网格（Istio），CI/CD 流水线（GitLab + Jenkins + ArgoCD），灰度发布与蓝绿部署。
7. 国产化替代：应用层迁移至国产中间件（TongWeb/Apusic），数据库替换为达梦 DM8 或 OceanBase，操作系统采用麒麟 OS，满足信创要求。
8. 可观测性：Prometheus + Grafana 监控告警，ELK 日志聚合，定期混沌工程演练（ChaosBlade）。

三、关键技术路线
1. 渐进式迁移：采用"绞杀者模式"，新旧系统并存，逐步将流量从单体迁移到微服务，避免一刀切风险；
2. 架构评估：改造前后采用 ATAM 方法评估，关注性能、可用性、可修改性、安全性四大质量属性；
3. 数据迁移：使用 Canal 监听 MySQL binlog 实现双写同步，确保数据一致性，业务验证后再切流；
4. 团队调整：按微服务边界重组团队（Spotify 模 式的小队制），每个小队全栈负责一个服务域。

**踩分要点**：
- 必须明确从"单体"演进到"微服务"，不能笼统说"分布式改造"
- 服务拆分要点出 DDD 限界上下文与单一职责，避免按技术层拆（Controller/Service/DAO 三层）
- 数据架构必须分库分表 + OLTP/OLAP 分离，不能一笔带过
- 服务治理必答注册中心、配置中心、熔断限流、链路追踪四大件
- 国产化要点出具体国产组件（达梦/OceanBase/麒麟/ TongWeb），体现信创合规
- 迁移策略要点出"绞杀者模式"与渐进式，不能一刀切
- 关联方法论：ATAM 评估、4+1 视图、DDD、Spotify 模 式、康威定律

## 记忆口诀
**架构风格口诀**：数流调用独仓虚——数据流、调用返回、独立组件、仓库、虚拟机五大风格

**SOA 三角色口诀**：提供者发布、注册中心管、请求者调用——SOA 三大角色环环相扣

**微服务特征口诀**：单（单一职责）独（独立部署）异（技术异构）去（去中心化）容（容错）自（自动化）——微服务六字诀

**微服务治理口诀**：注（注册中心）配（配置中心）熔（熔断降级）流（限流）链（链路追踪）网（网关）——微服务治理六件套

**CAP 定理口诀**：C 一致、A 可用、P 分区容错——三者只能取其二，分布式系统必取舍

**架构评估口诀**：敏（敏感点）权（权衡点）风（风险点）非（非风险点）——ATAM 四要素

**架构视图口诀**：逻（逻辑视）开（开发视）过（过程视）物（物理视）场（场景视）——4+1 视图五维一体

**国产化替代口诀**：麒麟 OS+达梦 DB+TongWeb 中间件——信创三件套自主可控
