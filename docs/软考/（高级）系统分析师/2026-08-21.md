## 今日核心概念
### 1. 领域驱动设计 DDD
定义：DDD（Domain-Driven Design）是以业务领域为核心驱动软件设计的建模方法论，通过统一语言、限界上下文、领域模型解决复杂业务问题。
关键要点：
- 战略设计：限界上下文（Bounded Context）、上下文映射（Context Mapping）、通用语言（Ubiquitous Language）
- 战术设计：实体（Entity，有唯一标识）、值对象（Value Object，无标识）、聚合（Aggregate，一致性边界）、聚合根（Aggregate Root）
- 上下文映射模式：共享内核（Shared Kernel）、客户-供应商（Customer-Supplier）、防腐层（Anti-Corruption Layer, ACL）、开放主机服务（OHS）
- DDD 与微服务：限界上下文是微服务拆分的最强边界依据，每个微服务对应一个或一组限界上下文
- 贫血模型 vs 充血模型：贫血模型只有 getter/setter、业务逻辑在 Service；充血模型业务逻辑在实体中

### 2. 六边形架构（端口与适配器）
定义：六边形架构（Hexagonal Architecture）由 Alistair Cockburn 提出，将业务逻辑置于核心，通过端口（Port）定义抽象接口、由适配器（Adapter）连接外部世界的架构风格。
关键要点：
- 核心结构：领域内核（Domain）+ 应用用例（Application）+ 端口契约（Port）+ 外部适配（Adapter）
- 端口分类：入站端口（Driving Port，调用方接口）、出站端口（Driven Port，被调用方接口）
- 适配器分类：入站适配器（REST Controller、CLI、消息消费者）、出站适配器（数据库 DAO、消息生产者、外部 API）
- 依赖倒置：外部依赖抽象接口，核心不依赖具体实现，符合 SOLID 依赖倒置原则
- 与传统分层区别：传统分层是水平依赖（UI→BLL→DAL），六边形是"中心-外围"放射状，核心稳定
- 同义别名：端口与适配器（Ports & Adapters）、清洁架构（Clean Architecture）、洋葱架构（Onion Architecture）

### 3. 事件驱动架构 EDA
定义：事件驱动架构（Event-Driven Architecture）是通过发布-订阅事件流实现服务间异步协作的架构风格，事件代表"已经发生的过去事实"。
关键要点：
- 三大角色：事件生产者（Producer）、事件消费者（Consumer）、事件代理（Broker，如 Kafka/RocketMQ）
- 事件分类：领域事件（Domain Event，业务状态变更）、集成事件（Integration Event，跨服务）、通知事件（Notification）
- 事件特性：过去时态命名（OrderCreated 而非 CreateOrder）、不可变、自包含、含事件 ID 与时间戳
- 投递语义：最多一次（At-most-once）、至少一次（At-least-once，推荐）、恰好一次（Exactly-once，难且贵）
- 幂等性：消费者必须幂等（同一事件多次处理结果一致），通过事件 ID 去重表实现
- 配套模式：事件溯源（Event Sourcing）、CQRS、本地消息表（Outbox Pattern）、Saga 分布式事务

### 4. 命令查询职责分离 CQRS
定义：CQRS（Command Query Responsibility Segregation）是将系统的写操作（Command）与读操作（Query）分离为不同模型的架构模式，写模型聚焦业务规则，读模型适配展示需求。
关键要点：
- 写模型（Command）：处理新增、修改、删除，遵循聚合不变量、领域规则，强一致性
- 读模型（Query）：针对查询场景专门设计（宽表、视图、物化视图），可多套并存满足不同查询
- 投影（Projection）：通过事件流将写模型状态异步投影到读模型，断点可重放
- 优势：读写可独立伸缩、读模型灵活适配 UI、性能优化（读库可去范式化）
- 挑战：最终一致性、投影延迟、读模型同步复杂度、多模型维护成本
- 与 CRUD 区别：CRUD 共用一套模型，读写争抢资源；CQRS 读写解耦，但架构复杂度上升
- 适用场景：读写比例悬殊、查询复杂多变、性能要求高、业务规则严谨

### 5. 演进式架构与适应度函数
定义：演进式架构（Evolutionary Architecture）是支持跨环境增量、可逆变更的架构风格，通过适应度函数（Fitness Function）持续评估架构目标达成度。
关键要点：
- 三大原则：增量变更、可逆决策、引导式演进（引导式 = Guided Change + Continuous Validation）
- 适应度函数：客观评估架构质量属性（性能、安全、可维护性）的可执行规则，分必备（Mandatory）与持续（Continuous）
- 五类适应度函数：依赖性、性能、恢复能力、安全性、一致性（如微服务隔离性、API 契约）
- 实施工具：架构守护测试（ArchUnit）、契约测试（Pact）、混沌工程（Chaos Engineering）
- 与传统架构区别：传统架构强调"建成即固化"，演进式架构强调"持续适应"，承认未来不可预测
- 关键实践：模块化边界、契约驱动开发、自动化测试金字塔、特性开关（Feature Toggle）
- 适应度函数组成：触发条件（如提交时）、检查规则（如循环依赖数 ≤ 0）、评分阈值（如响应时间 ≤ 200ms）

## 案例分析题
**题目**：
某跨境电商平台随着业务扩张，原有单体系统逐步暴露出以下问题：
1. 订单、库存、支付、营销四大模块共用一套 MySQL 库，并发量达每秒 8000 笔时频繁死锁与连接池耗尽；
2. 订单详情查询需要 JOIN 8 张表，单次查询平均耗时 1.2 秒，运营报表生成更慢；
3. 每逢黑五大促需将服务器扩容到日常 4 倍，但下个月又得缩容，资源浪费严重；
4. 营销活动上线需全量发版，平均上线周期 7 天，错失多个营销窗口；
5. 业务部门希望快速试错（A/B 测试），但单体架构下任何改动都牵动全局。
CTO 决定引入领域驱动设计与微服务架构对系统进行重构，要求保留核心业务资产、支持弹性伸缩、读写分离、营销活动独立发布。
请分析该电商平台的微服务拆分方案与读写架构设计。

**参考答案**：
一、现状问题分析
1. 单库共用导致 OLTP 与运营报表互相阻塞，并发能力受限于数据库连接池；
2. 复杂 JOIN 查询性能差，单一数据模型无法兼顾事务与查询两类需求；
3. 单体架构无法按模块独立伸缩，营销等高峰模块拖累全系统；
4. 紧耦合导致发布周期长，无法快速响应市场变化；
5. 单体架构下任何模块改动都涉及全量回归测试，试错成本极高。

二、DDD 限界上下文拆分
1. 通用语言建立：与业务专家对齐"订单""库存""支付""营销""用户"五大业务概念，消除歧义；
2. 限界上下文划分：用户中心（UC）、商品目录（PBC）、订单中心（OBC）、库存中心（IC）、支付中心（PC）、营销中心（MC）六大上下文；
3. 上下文映射：订单中心与库存中心采用"客户-供应商"模式（订单调用库存 API），订单中心与支付中心通过 Saga 分布式事务协调；
4. 防腐层 ACL：在订单上下文与遗留 ERP 之间建立防腐层，避免外部模型污染领域模型。

三、微服务架构设计
1. 服务拆分：基于六大限界上下文拆分为 6 个核心微服务，每个服务独立数据库（Database per Service），严禁跨库 JOIN；
2. 服务框架：Spring Cloud Alibaba 套件（Nacos 注册中心/配置中心 + Sentinel 熔断限流 + Seata 分布式事务 + SkyWalking 链路追踪）；
3. 通信机制：同步调用用 OpenFeign（HTTP/REST），异步事件用 RocketMQ（订单创建后异步通知库存与营销）；
4. 部署运维：Docker 容器化 + Kubernetes 编排 + Istio 服务网格，CI/CD 流水线（GitLab + ArgoCD），灰度发布与蓝绿部署；
5. 弹性伸缩：HPA 基于 CPU/自定义指标（订单 QPS）自动扩缩容，营销模块独立伸缩池。

四、读写分离 CQRS 设计
1. 写模型（Command）：订单服务维护聚合根（Order Aggregate），保证业务不变量（如未付款订单不可发货）；
2. 读模型（Query）：构建独立的查询服务（Query Service），订阅订单事件流，通过投影器（Projector）将订单状态写入宽表（订单详情宽表、运营报表宽表）；
3. 读模型存储：订单详情用 Elasticsearch（支持全文检索与聚合查询），运营报表用 ClickHouse（OLAP 列式存储），实时看板用 Redis（热点缓存）；
4. 投影机制：通过 RocketMQ 消费领域事件异步投影，断点可重放，保证最终一致性；
5. 幂等消费：消费者维护事件 ID 去重表（Redis Set），保证重复事件幂等；
6. 一致性权衡：写后读（Read-Your-Writes）通过读模型主动刷新保证，跨服务最终一致性通过 Saga + 补偿事务处理。

五、演进式架构保障
1. 适应度函数：服务循环依赖数 ≤ 0（ArchUnit 检查）、API 响应 P99 ≤ 300ms、单元测试覆盖率 ≥ 80%；
2. 契约测试：Pact 验证消费方契约，CI 流水线阻断破坏性变更；
3. 混沌工程：ChaosBlade 定期演练（杀 Pod、网络延迟、数据库故障），验证容错能力；
4. 渐进迁移：绞杀者模式，旧单体逐步替换为微服务，新旧系统并行运行 6 个月。

**踩分要点**：
- 必须先点出 DDD 限界上下文是微服务拆分依据，不能直接说"按业务拆"
- 微服务要点出 Database per Service + 独立部署 + 服务治理六件套
- CQRS 必须明确写模型（聚合根+不变量）与读模型（投影+宽表）的区别，不能笼统说"读写分离"
- 一致性要点出最终一致性 + Saga 分布式事务 + 幂等消费，不能说"强一致性"
- 弹性伸缩要点出 HPA + K8s + 独立伸缩池，不能只说"K8s"
- 部署要点出 CI/CD + 灰度发布 + 蓝绿部署，不能只说"自动化部署"
- 演进式要点出适应度函数 + 契约测试 + 混沌工程，体现"持续演进"理念
- 关联方法论：DDD、CQRS、Event Sourcing、Saga、Strangler Fig Pattern、绞杀者模式

## 记忆口诀
**DDD 两层设计口诀**：战（战略设计）略（限界上下文）上，谋（战术设计）合（聚合根）实（实体）值（值对象）下——DDD 战略战术两层设计

**DDD 战术四要素口诀**：实（实体有 ID）值（值对象无 ID）合（聚合边界）根（聚合根唯一入口）——DDD 战术四件套

**六边形架构口诀**：领（领域核心）应（应用用例）港（端口接口）配（适配器）——六边形核心加外围

**事件驱动口诀**：过（过去时态）至（至少一次投递）幂（幂等消费）——事件驱动三铁律

**事件溯源口诀**：事件不可变、聚合可重建、快照加速回溯——Event Sourcing 三件套

**CQRS 口诀**：写守规则（聚合+不变量）、读适展示（宽表+投影）——CQRS 读写分离双模型

**CQRS 投影口诀**：断可重放、核（核对）对（对账）幂等——CQRS 投影三要点

**演进式架构口诀**：增（增量）逆（可逆）反（反馈）度（适应度函数）——演进式架构四字诀

**适应度函数五类口诀**：依（依赖）性（性能）恢（恢复）安（安全）一（一致性）——适应度函数五大维度

**Saga 分布式事务口诀**：正（正向操作）逆（补偿操作）状（状态机）超（超时重试）——Saga 四要素
