## 今日核心概念
### 1. 软件过程模型与生命周期模型
定义：在软件开发与维护全过程中，对阶段划分、里程碑、迭代方式与交付节奏所做的结构化抽象，是项目管理与工程实践的总骨架。
关键要点：
- 瀑布模型（Waterfall）：严格按需求→设计→编码→测试→维护顺序推进，阶段间不重叠，强调文档驱动；优点是阶段清晰、易管理，缺点是难以应对变更、后期测试发现缺陷修复代价高
- V 模型：开发活动与测试活动一一对应，左边是开发（需求/概要/详细/编码），右边是测试（验收/系统/集成/单元），强调测试与开发同等重要
- 原型模型（Prototyping）：快速构建可运行原型驱动需求澄清，分抛弃型（Throwaway）与演化型（Evolutionary）；适合需求模糊、用户界面驱动项目
- 增量模型（Incremental）：先交付核心功能再迭代补充，每个增量都是一个完整的瀑布小周期；优点是早期交付可用版本、降低风险
- 螺旋模型（Spiral）：瀑布+风险分析驱动，每圈都做风险评估、原型验证、计划更新；适合大型高风险系统
- 喷泉模型（Fountain）：面向对象开发专用模型，各阶段重叠迭代，体现 OO 分析设计实现的无缝衔接
- 统一过程（RUP/Unified Process）：用例驱动、以架构为中心、迭代增量；二维度（时间 4 阶段：初始/细化/构造/移交；管理 9 核心工作流 6 工程+3 支持）
- 敏捷系列模型：Scrum（角色 PO/SM/Dev、事件 Sprint/站会/评审/回顾、工件 Product Backlog/Sprint Backlog/Burndown）、XP（极限编程 12 实践：结对编程/测试驱动开发/持续集成/重构等）、FDD（特性驱动）、Lean（精益）、SAFe（大规模敏捷）

### 2. 软件能力成熟度模型 CMMI
定义：由美国卡耐基梅隆 SEI 制定的软件组织过程能力评估与改进框架，分 5 级阶梯式成熟度，是软件组织资质评定的权威标准。
关键要点：
- 五个成熟度等级：初始级（Level 1，过程不可预测、依赖英雄）、可重复级（Level 2，基本项目管理、跟踪成本进度）、已定义级（Level 3，过程标准化文档化、聚焦过程族）、定量管理级（Level 4，建立量化目标、用数据管理）、优化级（Level 5，持续过程改进、缺陷预防）
- 18 个过程域（PA）：REQM（需求管理）、PI（项目集成）、PMC（项目监控）、PP（项目计划）、SAM（供应商协议管理）、MA（度量分析）、CAR（因果分析与解决）、DAR（决策分析与解决）、OPF（组织过程焦点）、OPD（组织过程定义）、OT（组织培训）、KPAIV/IPM（集成化产品管理）等
- 关键概念：KPA（关键过程域）、SG（Specific Goal 特定目标）、SP（Specific Practice 特定实践）、GP（Generic Practice 通用实践）、OID（组织革新与部署）
- 评估方法 SCAMPI：标准 CMMI 评估方法，分 A/B/C 三级，A 级最严苛（须有 50 人以上数据采集）
- 两种表示法：阶段性（Staged，5 级映射）与连续式（Continuous，按 22 个过程域成熟度）
- 与 ISO 9001、ISO 27001、ITIL、COBIT 的关系：CMMI 偏向软件过程，ISO 9001 偏向质量管理，ITIL 偏向 IT 服务管理

### 3. 敏捷开发方法学 Scrum 与极限编程 XP
定义：以人为中心、迭代演进、响应变化为核心理念的轻量级开发方法族，覆盖计划、协作、交付全过程。
关键要点：
- Scrum 三角色：Product Owner（产品负责人，确定需求优先级、最大化产品价值）、Scrum Master（敏捷教练，护航流程、移除障碍）、Development Team（开发团队，3-9 人跨职能自组织）
- Scrum 四事件：Sprint 迭代（2-4 周固定时长）、Sprint Planning 计划会、Daily Standup 每日站会（15 分钟内、3 问：昨天做了什么/今天做什么/有什么障碍）、Sprint Review 评审会、Sprint Retrospective 回顾会
- Scrum 三工件：Product Backlog（产品待办清单，含用户故事）、Sprint Backlog（迭代待办清单）、Increment（可交付增量）+ Burndown Chart 燃尽图
- XP 12 核心实践：计划游戏（Planning Game）、结对编程（Pair Programming）、测试驱动开发（TDD）、持续集成（CI）、重构（Refactoring）、小版本发布（Small Releases）、简单设计（Simple Design）、代码集体所有制（Collective Ownership）、系统隐喻（System Metaphor）、可持续节奏（Sustainable Pace）、现场客户（On-site Customer）、编码标准（Coding Standard）
- 敏捷宣言四价值观：个体与互动高于流程与工具、可用软件高于详尽文档、客户合作高于合同谈判、响应变化高于遵循计划
- 敏捷估算与度量：故事点（Story Point，相对估算）、理想人日、Velocity 团队速率、Burndown 燃尽图、Burnup 燃起图、Cycle Time 周期时间、Lead Time 前置时间
- 三大工件流转：需求（User Story）→ 任务（Task）→ 缺陷（Bug）流转于 Product Backlog → Sprint Backlog → Done

### 4. 软件项目计划与进度管理
定义：在软件开发启动前与推进过程中对范围、资源、时间、成本、质量所做的系统性规划与动态调整，是项目经理的核心职责。
关键要点：
- WBS 工作分解结构：将项目可交付成果按层次拆解至工作包，是范围管理核心；100% 原则（包含所有工作）、8/80 原则（每层 8±0 工作包粒度）、可管理/可估算/可分配
- 进度管理六参数：ES（最早开始）、EF（最早结束）、LS（最晚开始）、LF（最晚结束）、TF（总时差）、FF（自由时差）；关键路径总时差为零或最小
- 进度网络图：PDM（前导图法 4 依赖 FS/FF/SS/SF）、ADM（箭线图法）、CCM（条件图法）
- 进度压缩技术：赶工（Crash，进度优先、增加资源）、快速跟进（Fast Tracking，并行执行、增加返工风险）
- 挣值分析（EVM）：PV 计划值、EV 挣值、AC 实际成本；偏差指标 SV = EV-PV、CV = EV-AC；绩效指数 SPI = EV/PV、CPI = EV/AC；趋势预测 EAC = BAC/CPI、ETC = EAC-AC、VAC = BAC-EAC、TCPI = (BAC-EV)/(BAC-AC)
- 资源优化：资源平衡（可能改变关键路径）、资源平滑（不影响关键路径）
- 软件规模估算方法：LOC 代码行、FP 功能点（5 类功能：输入/输出/查询/文件/接口；14 个复杂度因子）、COCOMO 模型（基本/中级/详细三级）、Use Case 点、类比估算、自下而上估算、Wideband Delphi 宽带德尔菲

### 5. DevOps 与持续集成/持续交付（CI/CD）
定义：通过工具链与文化变革打通开发与运维壁垒，实现自动化构建、测试、部署与运维协同的软件交付实践体系。
关键要点：
- 核心原则：CAMS（Culture 文化、Automation 自动化、Measurement 度量、Sharing 共享）；三步工作流（Continuous Integration 持续集成、Continuous Delivery 持续交付、Continuous Deployment 持续部署）
- 持续集成 CI：频繁合并代码到主干（每日至少 1 次）、自动化构建（编译+单元测试+静态分析）、快速反馈（红绿构建）
- 持续交付 CD：自动化测试后产出可随时发布的产物（Release Candidate），发布决策由业务触发
- 持续部署 CD：自动化通过测试后直接部署到生产环境，无需人工干预
- DevOps 工具链：版本控制（Git/GitLab）、构建（Maven/Gradle/npm）、CI 服务器（Jenkins/GitLab CI/GitHub Actions/Argo）、制品库（Nexus/Artifactory）、配置管理（Ansible/Chef/Puppet/Terraform）、容器化（Docker）、编排（K8s）、监控（Prometheus/Grafana/ELK/SkyWalking）、日志（Loki/EFK）、告警（Alertmanager/PagerDuty）
- 蓝绿部署（Blue/Green）、滚动发布（Rolling）、灰度发布/金丝雀（Canary）、A/B 测试部署策略
- DevOps 能力成熟度模型：Google DevOps 四大能力（技术能力、流程能力、测量能力、文化能力）
- CALMS 框架：Culture 文化、Automation 自动化、Lean 精益、Measurement 度量、Sharing 共享

## 案例分析题
**题目**：
某互联网公司启动一款面向 C 端的短视频 App 开发项目，预算 300 万、周期 6 个月，团队 20 人（前端 6/Android 4/iOS 4/后端 4/测试 2）。项目启动前业务方对核心功能需求有较清晰认知，但对版本节奏、运营玩法、算法推荐模型仍存在不确定性；公司同时要求 3 个月内必须有一版可上线试运营（Minimum Viable Product）。
作为系统分析师，请回答以下问题：
(1) 该项目应选择哪种生命周期模型？为什么？可结合瀑布、增量、螺旋、敏捷（Sprint）模型给出对比。
(2) 若采用 Scrum，请设计首期 Sprint 计划：Sprint 周期长度、产品待办清单前 5 项迭代内容、估算与角色分工。
(3) 该项目在过程度量上应建立哪些核心指标？如何通过燃尽图识别项目进度风险？
(4) 若进入运维阶段，CI/CD 流水线应包含哪些关键环节？DevOps 度量指标有哪些？

**参考答案**：
一、生命周期模型选择
1. 不选瀑布模型：需求存在不确定性、C 端产品市场变化快、3 个月 MVP 节点压力大；瀑布模型难以应对需求变更。
2. 推荐采用 Scrum 敏捷开发为主 + 关键里程碑瀑布式管理（Hybrid 混合模式）：
   - 全局仍按瀑布规划阶段：概念→计划→开发→试运行→运维→退役；
   - 开发阶段用 Scrum 迭代：1 个 6 周 Sprint（版本交付 MVP）+ 后续 5 个 4 周 Sprint 持续迭代；
   - 关键技术探索（视频转码/算法推荐）配合 Spike 原型验证 + 探索性编程降低技术风险。
3. 备选方案分析：
   - 增量模型：适合需求分块清晰、每块独立可交付，但短视频需求耦合度高，增量边界不好切分。
   - 螺旋模型：风险驱动适合大型复杂系统（如航空、医保），成本与仪式太重。
   - 纯敏捷 Scrum：最适合 C 端不确定性高、变更频繁的小团队快速验证。
4. 选型依据：业务不确定性 + 团队规模（20 人）+ MVP 时间压力 + C 端市场敏捷需求。

二、首期 Sprint 计划设计（假设 Sprint 周期 4 周）
1. Sprint 长度：4 周（短视频这种 UI 驱动 + 后端 API 项目 4 周最常用，2 周过短、6 周过长导致反馈延迟）
2. Product Owner：业务方代表；Scrum Master：项目经理（兼具）；Dev Team：20 人拆分为 4 个特性小队（短视频播放/UGC 发布/账户体系/推荐 V1）
3. Product Backlog Top 5（按商业价值排序）：
   - US01 账户体系：手机号+微信一键登录、用户主页、关注/粉丝（8 故事点）
   - US02 视频拍摄与上传：录制、滤镜、封面、BGM、特效（13 故事点）
   - US03 视频播放详情页：双击点赞、上下滑切换、评论、分享（8 故事点）
   - US04 智能推荐 V1：基于协同过滤 + 热门兜底的 Feeds 流（13 故事点）
   - US05 性能与稳定性：首屏秒开、弱网降级、H5 错误上报（5 故事点）
4. 容量估算：团队 Velocity ≈ 45 故事点/Sprint（开发+测试总和）；Top 5 共 47 点略超，需拆分 US04 算法调研用 Spike（3 天 +3 故事点）独立并行
5. 角色分工：前端 6 人分组支持播放/UGC/账户，后端 4 人 + Android/iOS 各 2 人做端能力，测试 2 人做 TDD 与自动化
6. DoD（Definition of Done 完成定义）：代码评审通过 + 单元测试覆盖率 ≥ 70% + 接口测试通过 + 用户验收通过 + 部署到预发

三、过程度量核心指标
1. 进度指标：燃尽图（Burndown Chart）横轴时间纵轴剩余故事点；Burnup 燃起图横轴时间纵轴累计完成故事点
2. Velocity 团队速率：本次 Sprint 完成故事点 / 上一 Sprint 完成故事点，观察是否平稳或在 ±20% 内
3. 缺陷指标：缺陷密度（每 KLOC）、缺陷逃逸率（生产缺陷/UAT 缺陷）、缺陷修复平均时长、严重缺陷占比
4. 质量指标：单元测试覆盖率（≥ 70%）、集成测试通过率、SonarQube 技术债务、代码重复率
5. 风险识别：通过燃尽图判断——若剩余工作量曲线斜率小于理想线（理想线从总点降到 0）说明进度滞后；若多日维持水平无下降，说明遇到障碍未解决；若多次下不去，触发 Scrum Master 介入、移除障碍、必要时调整 Sprint 范围
6. 挣值指标：PV 计划值、EV 挣值、AC 实际成本，计算 SPI/CPI 监控成本进度偏差

四、CI/CD 流水线关键环节
1. 提交阶段：Git Commit → Hook 触发静态分析（Checkstyle/SonarQube ESLint Pre-commit Hook）
2. 构建阶段：Maven/Gradle/Node 构建 → Docker 镜像打包
3. 测试阶段：单元测试 → 接口测试 → UI 自动化测试 → 性能冒烟测试 → 安全扫描（OWASP/Dependency-Check）
4. 制品阶段：镜像推送镜像仓库（Harbor/Nexus）、版本号语义化（SemVer）
5. 部署阶段：预发部署 → 自动化回归 → 灰度发布（Canary 5%→25%→50%→100%）→ 蓝绿切换
6. 监控阶段：APM（SkyWalking/Pinpoint）+ 日志（ELK/Loki）+ 指标（Prometheus/Grafana）+ 告警（PagerDuty）
7. 反馈阶段：用户反馈 → 需求池 → 下个 Sprint Backlog 闭环

五、DevOps 度量指标
1. 部署频率（Deployment Frequency）：指标 DORA 四指标之一，精英团队可达每日多次
2. 变更前置时间（Lead Time for Changes）：从代码提交到生产可用时长
3. 变更失败率（Change Failure Rate）：导致生产故障的变更占比
4. 故障恢复时间（MTTR）：Mean Time To Recovery
5. 可用性指标：SLA/SLO/SLI 三角
6. 工程效能：构建时长、测试时长、Pipeline 通过率、Pipeline 平均执行时间

**踩分要点**：
(1) 答出混合 Scrum + 关键里程碑瀑布或螺旋+敏捷，理由完整，10 分；要点：需求不确定 → 选敏捷；MVP 时间压力 → Scrum 短迭代；C 端市场变化快 → 敏捷响应；团队 20 人 → Scrum 标准规模
(2) Sprint 长度合理 + Top 5 用户故事 + 故事点估算 + DoD 定义，10 分；每项 2.5 分
(3) 核心指标答 4 个以上（燃尽图、Velocity、缺陷、覆盖率）+ 风险识别规则，5 分
(4) CI/CD 6 环节（提交→构建→测试→制品→部署→监控）+ DORA 四指标 + MTTR，5 分

## 记忆口诀
**生命周期模型速记**：瀑（瀑布）V（V 模型）原（原型）增（增量）螺（螺旋）喷（喷泉）统一（RUP）敏（敏捷）——七类模型集合
**瀑布 vs 敏捷**：瀑布文档驱动稳扎稳打，敏捷拥抱变化快迭代
**CMMI 五级**：初（初始）重（可重复）定（已定义）量（定量管理）优（优化），从依赖英雄到数据驱动到持续改进
**CMMI 评估三级**：A 最严数据要 50 人月、B 中等、C 速评
**敏捷宣言四价值观**：人（个体互动）胜于流程、软（可用软件）胜于文档、合（客户合作）胜于合同、变（响应变化）胜于计划
**Scrum 三角色**：PO（产品负责人）挑价值、SM（敏捷教练）保流程、Dev（开发团队）做交付
**Scrum 四事件**：Sprint 迭代 + Sprint Planning 计划 + Daily Standup 站会（昨天做了什么今天做什么有什么障碍）+ Review 评审 + Retro 回顾
**Scrum 三工件**：Product Backlog 业务待办 + Sprint Backlog 迭代待办 + Increment 增量
**XP 12 实践**：计（计划游戏）结（结对编程）测（TDD）重（持续集成 + 重构）小（小版本）简（简单设计）集（集体所有）隐（隐喻）持（可持续）客（现场客户）标（编码标准）
**敏捷估算三件套**：故事点（相对估算）+ Velocity 速率 + Burndown 燃尽图
**三种 Backlog 流转**：User Story → Task → Bug → Done
**DoD 完成定义**：代码评审 + 单测覆盖 + 接口测试 + UAT + 上线 — 五步达成
**WBS 80 原则**：8±0 原则从粗到细可管理
**进度六参数**：ES EF（早系列）LS LF（晚系列）TF 总时差 FF 自由时差
**关键路径特征**：总时差为零的活动链，关键路径可能有多条
**挣值三值**：PV 计划值 BCWS、EV 挣值 BCWP、AC 实际成本 ACWP
**挣值四指数**：SV = EV-PV、CV = EV-AC、SPI = EV/PV、CPI = EV/AC
**预测三指标**：EAC = BAC/CPI、ETC = EAC-AC、VAC = BAC-EAC
**进度压缩两招**：赶工加资源串行、快速跟进并行返工高
**COCOMO 三级**：基本（公式估算）、中级（15 个调节因子）、详细（5 类 23 因子分阶段）
**FP 五功能类**：输（输入）、出（输出）、查（查询）、文（文件）、接（外部接口）
**DevOps 三步流**：CI 集成（合并即构建）+ CD 交付（可发布）+ CD 部署（自动化上线）
**DevOps CAMS**：Culture 文化 + Automation 自动化 + Measurement 度量 + Sharing 共享
**CI/CD 五环节**：提（提交 Hook 静态检查）构（构建打包镜像）测（单+接+UI+性能+安全）制（制品入库+版本号）部（预发+灰度+蓝绿）
