## 今日核心概念
### 1. 数据库设计阶段与产物
定义：数据库设计按"需求分析→概念设计→逻辑设计→物理设计→实施运维"五阶段推进，每阶段输出明确的设计产物，形成可追溯、可评审、可演化的设计闭环。
关键要点：
需求分析产出数据流图、数据字典、用户视图与业务规则清单
概念设计用E-R图表达实体、属性、联系，独立于任何DBMS
逻辑设计将E-R转换为关系模式，进行规范化（1NF/2NF/3NF/BCNF/4NF）
物理设计关注表结构、索引、分区、分库分表、存储引擎
运维阶段持续监控慢SQL、锁等待、空间增长并迭代优化

### 2. 关系模式规范化与反规范化
定义：规范化通过分解关系消除数据冗余与更新异常，反规范化在性能压力下有控制地引入冗余以换取查询效率，二者需结合业务读写比权衡。
关键要点：
1NF要求字段原子不可分；2NF消除非主属性对主键的部分依赖；3NF消除传递依赖；BCNF消除主属性对码的部分/传递依赖
范式越高冗余越少但JOIN越多，写多读少场景宜高范式，读多写少场景可适度反规范化
反规范化手段包括增加冗余列、派生列、预计算汇总、宽表化与适度反范式3NF
判断依据：读写比、查询响应SLA、JOIN复杂度、数据一致性容忍度
过度反规范化会带来更新异常风险，应配合触发器、事务或应用层一致性保障

### 3. 索引设计与查询优化
定义：索引是数据库加速查询的核心机制，通过B+树、哈希、位图、全文等数据结构降低数据访问路径代价，需结合查询模式精准设计。
关键要点：
B+树索引适合范围查询与排序，哈希索引适合等值查询，位图索引适合低基数列，全文索引用于文本模糊检索
复合索引遵循最左前缀原则，避免在索引列上做函数运算、类型转换、like左通配
覆盖索引（Covering Index）通过索引本身返回查询所需全部列避免回表
慢SQL优化六步骤：抓慢SQL→看执行计划→识别全表扫描/大JOIN→评估索引缺失→改造SQL或索引→回归验证
索引不是越多越好：每多一个索引就多一份写入开销与存储成本，需建立索引评审与生命周期管理

### 4. 事务管理与并发控制
定义：事务是数据库并发执行的基本单位，需满足ACID特性，并通过锁机制、多版本并发控制、隔离级别等技术保证并发一致性与性能平衡。
关键要点：
ACID指原子性、一致性、隔离性、持久性，是事务正确性的基石
四种隔离级别：读未提交、读已提交、可重复读、串行化，级别越高一致性越强并发越差
常见并发问题：脏读、不可重复读、幻读，对应不同隔离级别解决方案
锁机制分共享锁（S锁）、排他锁（X锁）、意向锁；多版本并发控制MVCC通过版本快照避免读写冲突
分布式事务两阶段提交（2PC）、三阶段提交（3PC）、TCC、SAGA、可靠消息最终一致性等方案各有适用场景

### 5. 大数据环境下的数据分析体系
定义：在关系数据库之外，针对PB级数据、多源异构、实时离线混合场景构建的分布式数据存储与计算体系，包括数据湖、数据仓库、流批一体与数据科学平台。
关键要点：
数据湖存储原始数据（Schema-on-Read），数据仓库面向主题、集成、相对稳定（Schema-on-Write）
Lambda架构分批处理层、加速层、服务层三段；Kappa架构以流式处理统一离线与实时
典型技术栈：HDFS/Hudi/Iceberg存储、Spark/Flink计算、Hive/ClickHouse/Doris查询、Airflow/DolphinScheduler调度
OLTP面向交易高频小事务，OLAP面向分析低频大查询，二者通过HTAP或数据同步分层解耦
分析师需根据一致性、时延、成本、复杂度四个维度选择架构而非盲目追新

## 案例分析题
**题目**：
某市人社局建设"智慧就业服务大数据平台"，整合来自公共就业服务窗口、社保系统、市场监管系统、互联网招聘平台、第三方征信机构等15类数据源，日均增量数据约500GB，平台支撑就业失业登记、就业援助、岗位推荐、技能培训补贴申领、失业保险核发等核心业务。系统上线6个月内出现以下问题：
1. 就业登记和失业登记高频写入导致业务库（MySQL 8.0）主库写压力过大，订单表数据量达8亿行后INSERT响应明显变慢。
2. 业务查询经常涉及"按身份证号+姓名联合检索""按岗位类别+区域统计""近6个月就业趋势分析"，复杂SQL导致查询超时，平均响应时间超过10秒。
3. 月度报表生成依赖在业务库直接执行大查询，占用大量IO与CPU，影响在线业务。
4. 平台曾因人社与市场监管数据交换采用夜间批量同步，因接口字段定义不一致，导致30万条人员信息匹配失败，事后才发现。
5. 失业保险核发涉及社保系统、银行、税务三方的状态联动，偶发因网络抖动导致一笔业务跨系统状态不一致，部分申请人资金延迟到账引发投诉。

问题：
1. 请分析该平台业务库写入性能瓶颈的成因，并给出针对性的分库分表与读写分离改进方案。
2. 针对不同查询场景，请设计索引策略与查询优化方案。
3. 月度报表占库问题应如何解决？请给出离线分析层（数据仓库/数据集市）的设计方案。
4. 针对跨系统数据同步一致性问题，应从哪些方面入手建立治理机制？
5. 失业保险核发的跨系统状态不一致问题，应采用哪些分布式事务方案加以解决？

**参考答案**：
1. 写入瓶颈与分库分表方案：
成因：单库单表数据量过大导致索引膨胀、B+树层级过深、锁等待与日志写入开销剧增。
方案：按身份证号哈希或业务维度（如登记机构、地区）进行水平分库分表，将8亿行单表拆分到N个分片；引入读写分离，写主读从；分片键选择需保证常用查询条件命中分片键；对超大字段、历史归档数据单独建库。

2. 索引策略与查询优化：
身份证号+姓名联合检索：建立联合索引，姓名冗余或使用覆盖索引；姓名脱敏后建立前缀索引；高频查询走ES搜索引擎或分布式缓存。
岗位+区域统计：建立（区域,岗位类别,统计时间）联合索引；引入OLAP引擎（Doris/ClickHouse）做聚合。
6个月趋势分析：按月分区表+时间索引；预计算物化视图或宽表；走离线数仓或时序库。
通用原则：避免SELECT *、避免在索引列做函数运算、大表禁止JOIN超过3张、必要时反规范化。

3. 月度报表离线分析方案：
构建分层数据仓库（ODS→DWA→DWS→ADS），通过Canal/Debezium/Flume CDC增量同步至Hive/Iceberg/Hudi；引入Spark/Flink做ETL；最终汇总层由Doris/ClickHouse支撑交互式分析；调度使用Airflow/DolphinScheduler；业务库零报表压力。

4. 跨系统数据同步治理：
制定统一数据标准与编码规范（身份证、岗位类别、地区编码等）；建立数据字典与元数据管理平台；引入数据质量监控（准确性、完整性、一致性、时效性）；实施数据血缘追踪与字段级映射；建立数据交换接口契约管理与异常告警机制；事后建立数据质量评估与责任追溯机制。

5. 分布式事务方案：
可靠消息最终一致性：通过RocketMQ/Kafka发送事务消息，社保核发成功后发消息驱动银行/税务状态更新，失败则重试+死信告警。
TCC模式：Try-Confirm-Cancel三阶段，适合核心金融业务高一致性场景。
SAGA模式：将跨系统业务流程拆分为多个子事务并提供补偿动作，适合长事务。
本地消息表+定时对账：业务库落地消息表，定时任务扫描推送，配合每日对账机制修正不一致状态。
方案选择需结合一致性强度、性能、复杂度三个维度。

**踩分要点**：
1. 分库分表：必答"水平分片+读写分离+分片键选择"三要素
2. 索引优化：场景对应策略（联合索引/搜索引擎/OLAP/分区物化视图）
3. 离线分析：必答"分层数仓（ODS/DWA/DWS/ADS）+CDC同步+OLAP引擎+调度系统"
4. 数据治理：必答"标准+字典+质量+血缘+契约+追溯"六要点
5. 分布式事务：列举可靠消息/TCC/SAGA/本地消息表至少三种方案并比较

"一原二部三传BC"——1NF原子、2NF部分依赖、3NF传递依赖、BCNF主属性依赖
"范式越高冗余越少，读多写少适度反"——读写比决定反规范化时机

索引设计口诀：
"左前缀不运算、覆盖免回表、最左匹配不可违"
"B树范围哈希等值、位图低基全文文"

"原一隔持"——原子性、一致性、隔离性、持久性
